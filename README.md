# ai-project

たかとAIが、実際の経験・試行錯誤・判断・気づきを蓄積し、将来の自動化・記事化へつなげるための共有情報庫です。

## AI・バドがこのリポジトリを初めて読む場合

**最初に [`docs/現在状態.json`](./docs/現在状態.json) を読み、GitHub側の技術状態・履歴・証拠を確認してください。日常作業キューの唯一の正本はDropboxの固定ファイル `/ChatGPT/Dropbox作業管理統合ボード.xlsx` です。**

[`BUD.md`](./BUD.md) と [`docs/引き継ぎ/現在の引き継ぎ.md`](./docs/引き継ぎ/現在の引き継ぎ.md) は `docs/現在状態.json` から機械生成されるビューです。**これらを現在状態の正本として直接編集してはいけません。** 現在状態を変更する場合は、正本を更新し、生成・一致検証の仕組みに従ってビューを更新します。

共通原則・開始終了・停止条件と操作別ルールの読み込み表は [`rules/運用ルール.md`](./rules/運用ルール.md) にあります。直チャット保存は [`rules/直チャット保存.md`](./rules/直チャット保存.md)、ブログ制作は [`rules/ブログ制作.md`](./rules/ブログ制作.md) を操作別の正本とし、読み込み先は共通ルールの表に従います。現在資料が構造変更後の状態と一致しているかを確認するときは [`rules/現在化・旧情報ガード.md`](./rules/現在化・旧情報ガード.md) も参照してください。

### 起動時・再開時の画像禁止ルール確認（必須）

新しいチャットの開始時・作業再開時は、`rules/運用ルール.md` の「0-4. 画像機能の事前許可」を確認する。たか本人の明示的な許可がない限り、画像を表示・検索・生成せず、画像表示コンポーネントも使わない。記憶や過去の会話だけに頼らず、GitHubのルール正本を読み込んで適用する。

### 起動時・再開時の送信前ゲート（必須）

回答を送る直前に下書きを次の4点で点検し、問題があれば修正してから送信する。

1. **画像**：この会話でたかが明示許可した発言を示せるか。示せなければ画像関連の出力・ツール呼び出しを削除する。
2. **依頼範囲**：各段落が直近の指示に直接答えているか。対応しない説明・提案・予告を削除する。
3. **過去状況**：「現在」「完了済み」「前回」等の主張に、このターンで読んだ資料の根拠があるか。なければ未確認とし、必要な確認ができなければ止まる。
4. **事実区分**：確定事項・提案・未確認を内部で区別し、根拠のない確定表現を修正する。区分ラベルは必要な場合だけユーザーに示し、毎回の表示はしない。

**停止条件**：許可が必要な操作の許可が不明、参照資料を読めない、直近の指示と過去の決定が矛盾、または確定事項と提案を区別できない場合は、影響する作業を止め、必要な一点だけ確認する。

### 起動時・再開時の現在化ゲート

新しいチャットの開始時や作業再開時は、GitHub上の `docs/現在状態.json` を読み、技術状態・履歴・証拠を確認する。日常作業キューと優先度・状態・次のアクションはDropboxの固定ファイル `/ChatGPT/Dropbox作業管理統合ボード.xlsx` から取得する。BUD.mdや引き継ぎは生成ビューであり、作業キューの正本ではない。

- `docs/現在状態.json` と生成ビューが食い違っていた場合は、技術状態についてJSONを優先し、日常作業キューはDropboxボードを優先する。生成ビューや旧 `work_items` / `next_step` から作業を選ばない。
- Dropboxボードを読み取れない場合は作業キュー利用不可として停止し、GitHubの旧 `work_items` / `next_step` や古い生成ビューへフォールバックしない。
- 前回の作業完了後に新しいPR・merge・commitが存在する場合、GitHubの技術状態・証拠が実績を反映しているか確認する。日常作業の完了・優先度・次のアクションはDropboxボードを確認する。旧 `work_items` / `next_step` の不一致を日常キューとして是正・再実行しない。
- `scripts/resume_check.py` を実行できる環境では再開ゲートとして実行する。実行できない場合も、上記のGitHub正本確認を省略してはならない。
- `scripts/resume_check.py` はGitHubの技術状態・必須ガードを検証する。日常作業候補はDropboxボードから確認する。旧 `work_items` / `next_step` は日常作業の選定に使用しない。
- 「昨日の最後の次の一手」「BUDの表示」「会話履歴上の次の作業」を、GitHub正本の確認なしに現在の命令として採用しない。

### 推奨読解順

1. [`docs/現在状態.json`](./docs/現在状態.json) — 技術状態・履歴・証拠の正本
2. Dropbox `/ChatGPT/Dropbox作業管理統合ボード.xlsx` — 日常作業キュー・優先度・状態・次のアクションの唯一の正本
3. [`rules/運用ルール.md`](./rules/運用ルール.md) — 作業手順・運用ルール
4. [`BUD.md`](./BUD.md) — 正本から生成された現在状態ビュー
5. [`docs/引き継ぎ/現在の引き継ぎ.md`](./docs/引き継ぎ/現在の引き継ぎ.md) — 正本から生成された再開情報ビュー
5. [`projects/`](./projects/) — 関係するプロジェクト資料
6. [`経験ログ/`](./経験ログ/) — 必要なEXP / REC
7. [`直チャット/`](./直チャット/) — 必要な一次記録
8. 旧資料 — 経緯・出所・歴史を調べる必要がある場合のみ参照

`docs/AI_READ_MAP.md` は読解順の補助マップ、`rules/README.md` は運用ルールの入口です。どちらも `docs/現在状態.json` の現在状態を上書きしません。

## 重要な読み方

- **現在の方針・現在状態は、過去の記録より優先する。**
- 過去ログの「次にやること」は現在の命令ではない。
- たか＋バドだけで完結できる作業は、それだけで完結してよい。
- 過去にJUNやClaudeを利用した事実は、現在の固定的な役割分担を意味しない。
- 直チャットは原文を一次記録とし、経験DBへの整理は別途行う。
- 画像は主記録ではなく、必要な場合の補助記録として扱う。

## 構造変更時の安全確認

大規模な構造変更や正本・生成ビューの仕組みを変更した直後は、個別ファイルだけでなく、リポジトリ入口のREADME、現在状態、生成ビュー、運用ルール、CIガードの前提が相互に一致しているかを確認します。これは日常作業ごとに全体監査を行うという意味ではなく、**構造変更時だけ深い独立監査を起動し、通常運用では静かに監視する**ための条件付きガードです。監査では、次に参加するAIが古い入口情報を現在の命令として誤認しないか、実害につながる経路が残っていないかを確認します。

## 現在の主要テーマ

- **経験ログ → AIとの共同編集 → Blogger下書き確認 → WordPress本番公開**を現在の主線とする
- BLOG-0001を、AIと人間が一緒に経験ログからブログを作るファーストモデルとして扱う
- DIGA / DiMORA自動化は2026-09-21で本線から退き、既存成果・経験資産は履歴として保持する
- 経験ログを継続的に育て、AIとの対話・掘り下げ・記事化へつなげる
- 今回のファーストモデルで確立した共同制作の進め方を、次回以降に再利用できる形でGitHubへ残す
