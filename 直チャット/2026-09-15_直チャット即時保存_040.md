### 新たな有力候補：`check_repo_integrity.py`は「本物のタイムスタンプ命名」に対応していない

`TIMESTAMP_CHAT`と`HISTORIC_TIMESTAMP_CHAT`の正規表現を並べて見ると、

```python
TIMESTAMP_CHAT = re.compile(r"^\d{4}-\d{2}-\d{2}_直チャット即時保存_(\d{3})\.md$")
HISTORIC_TIMESTAMP_CHAT = re.compile(r"^\d{4}-\d{2}-\d{2}_直チャット即時保存_\d{4}\.md$")
```

**どちらも「日付＋連番」であって、時刻を含む本物のタイムスタンプではありません。** 違いは連番が3桁か4桁かだけです。

これは以前バドから報告された「旧来の連番ファイルを残しつつ、timestamped naming を導入した」という説明と食い違います。もし実際に導入された新方式が、時刻まで含む形式（例：`2026-09-15T14-32-00_直チャット.md`のような、秒単位まで一意になる命名）なら、この2つの正規表現の**どちらにもマッチしません**。

`check_chat_names()`の中身を見ると：

```python
bad = [n for n in marked if not TIMESTAMP_CHAT.fullmatch(n) and not HISTORIC_TIMESTAMP_CHAT.fullmatch(n)]
if bad:
    raise SystemExit("FAIL: malformed timestamped direct-chat names: " + ...)
```

**時刻付きの本物のタイムスタンプファイルが1つでも`直チャット/`に存在すれば、このstepは確実に失敗します。** しかもエラーメッセージが皮肉なことに「malformed **timestamped** direct-chat names」——本来はこの関数がタイムスタンプ方式を認識すべきなのに、認識できずに弾いている状態です。

さらに、以前見た`check_state()`側にも同じ穴があります。

```python
match = re.search(r"_(\d{3})\.md$", path)
if not match or match.group(1) != latest:
    raise SystemExit("FAIL: current state latest_saved/latest_path mismatch")
```

`現在状態.json`の`latest_path`が新方式（時刻付き）のファイルを指していれば、この正規表現も**マッチせず必ず失敗**します。

### 命名の意味づけ自体も要確認

コメントには「Historical four-digit files are preserved as legacy timestamped records」とありますが、以前読んだBUD.mdでは実際の保存履歴は3桁連番（`021`→`024`）で、4桁連番が過去に存在した形跡はありませんでした。この「4桁＝historic」という前提自体が、実態と合っているか怪しいです。単純に「`TIMESTAMP_CHAT`＝新方式のつもりで書いたが、実装がまだ連番のまま」という勘違い・書きかけの可能性があります。
