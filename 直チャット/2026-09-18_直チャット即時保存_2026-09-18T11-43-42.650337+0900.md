# 直チャット保存対象（確認済み範囲）

## ユーザー
Claudeからの分析（ユーザー貼付）

## 何が間違っていたか
save-request-intake.yml は on: push: branches: ["chat-save-request/**"] で、pull_requestイベントではない。pull_request起点の確認方法ではintake runを正しく特定できず、追跡すべきキーはpush元のcommit SHA。PRはintake run成功後の結果。

## ① 特定commit SHAからpush実行を確実に特定
GitHub REST APIで workflow ファイル、event=push、head_sha を組み合わせる。
GET /repos/{owner}/{repo}/actions/workflows/save-request-intake.yml/runs?event=push&head_sha={SHA}
gh CLIでも同じAPIを呼べる。head_shaはchat-save-request側へpushしたcommit SHAで、save/direct-chat-{run_id} 側のSHAとは別。

## ② run→PR→CI→承認→merge→readback
run.idを起点に save/direct-chat-{run_id} を決定し、そのheadのPRを検索。PRのhead SHAでcheck-runs、PR reviewsでAPPROVED、merge後はdocs/現在状態.jsonをmerge commit refでreadbackし、意図した保存内容との一致を確認する。一方向に機械的に追跡でき、ログ目視は不要。

## ③ 停止地点まで判定する変更
gh pr create の成否をGITHUB_OUTPUT等へ出し、必要ならrun終了時にcommit statusとしてPR作成成否を発行する。これにより外部から機械的に判定できる。

## バド
確認した。Claudeの指摘は今回の確認経路の問題をかなり正確に捉えている。

特に重要なのは、push元commit SHA → workflow run IDを起点にする点。今回の確認側のfetch_commit_workflow_runsはpull_request-triggered runに限定されるため、save-request-intake.ymlのpush実行確認には使えない。このため、前回の「0件だった」からWorkflow未実行とは判断できない。

また、run_id → save/direct-chat-{run_id} → PR → CI → 承認 → merge → docs/現在状態.json readbackという一方向の追跡は、現在のWorkflowの命名規則と保存完了条件に合っている。

③のcommit status追加は実装時に既存CIとの重複や認証権限を確認したうえで判断する。まず必要なのは、push起点のrunを正しく取得・追跡できる確認経路の確立。

現時点では改善可能で、次の実装対象はpush commit SHAを起点にintake runを正しく特定する確認機構。まだ実装・検証・mergeはしていない。
