うん。その方針でいい。

今回の件から、**「使わない経路を残さない」こと自体を運用ルールにしたほうがいい**。

具体的には、

1. **現行の正規保存経路を1本だけ残す**
   - 保存要求
   - `save-request-intake.yml`
   - `scripts/save_and_currentize.py`
   - `save/direct-chat-*`
   - PR
   - CI
   - `taka2-dev` 自動承認
   - merge
   - 正本readback

2. **旧自動承認経路を閉じる**
   - GitHub Appによる旧 `ai-project-save-approver` 経路
   - 不要なら関連secretも整理
   - ただし、実際にどこから参照されているか確認してから削除

3. **今回のような `chat-save-request/... → 直接PR` を保存経路として残さない**
   - これは今回の事故原因になった経路なので、明確に「保存PRを直接作る経路ではない」とする。
   - テスト用ブランチ・テスト手順も、もう使わないなら削除対象。

4. **手順書も同時に整理**
   - `rules/運用ルール.md`
   - 必要なら現在状態の保存パイプライン記述
   - 「旧経路」「テスト経路」「以前の方法」を、現行手順として読める状態で残さない。

5. **「正規経路以外では保存完了にならない」を明記**
   - PRが存在しただけでは保存完了ではない。
   - canonical readbackまで確認できた場合だけ完了。

ただし、**いきなり削除はしない**。まず現在のmainを調べて、旧経路が何個残っているかを確定する。そのうえで、不要なものだけを1つの整理PRにまとめるのが安全。

そして今回の #76 は、整理が終わるまで**未保存・未完了のまま**扱う。
