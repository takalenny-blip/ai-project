## 前回回答

間違った報告が来るのは困る、という点はその通り。対処可能です。

今回の誤報は、保存処理そのものではなく、保存経路の途中状態を最終結果として判定したことが原因です。

今回の流れは、

- #553：`chat-save-request/**` のキューPR
- `save-request-intake.yml`：キューを受けて後続処理
- #554：実際の canonical save PR
- #554：merge済み
- `docs/現在状態.json`：readback済み

でした。

それなのに、バドが #553 の「closed / merged=false」だけを見て、後続の #554 と canonical readback まで追わず、「GitHub側でブロック」「未完了」と報告しました。これは誤りです。

今後は保存状態を報告するとき、必ず次のライフサイクルを追って判定します。

1. 保存要求が投入されたか
2. intake workflow が起動・処理したか
3. 後続の canonical save PR が作成されたか
4. canonical save PR のCI・承認・merge状態
5. `docs/現在状態.json` のcanonical readback
6. 未確認の段階が残っているか

特に、`chat-save-request/**` のキューPRが closed で merged=false でも、それだけでは失敗・ブロックとは判定しません。後続のcanonical save PRが生成され、mergeされ、canonical readbackまで確認できて初めて保存完了と判定します。

また、これは文章上の注意だけで済ませるより、#553→#554のような実際の経路を機械的に判定できる仕組みにするのが適切です。

現時点では、この対策自体の実装はまだ変更していません。今回書き込むのは、前回回答の記録です。
