# 直チャット保存要求

## 保存対象種別
会話記録

## 本文

うん。**その方針、かなり合理的だと思う。**  
特に今までの「直チャット保存」はトラブルが起きるたびに本来の作業から脱線していたから、そこを切るのは大きい。

そして問題は、たかが言う

> **作業PCでブラウザ保存 → そのファイルをバドに渡す**

をどれだけ簡単にできるか、だよね。

結論からいうと、**かなり簡単にできる。しかもGitHubよりDropboxのほうが「バドに渡す中継地点」としては向いている**と思う。

### 俺ならこうする

```
作業PC
  ↓
ブラウザで「保存」
  ↓
Markdown / HTML / PDF / TXT などのファイル
  ↓
Dropbox
  ↓
バドがDropboxから取得
  ↓
必要なら内容を整理・要約・EXP/REC化など
  ↓
正式な記録が必要なものだけGitHubへ
```

DropboxはWebからファイルをアップロードできるし、デスクトップアプリを使っていればDropboxフォルダへコピーするだけで同期される。

しかも、**Dropboxについてはすでにバド側の接続がある**ので、ここが大きい。

---

## GitHubは「保存先」、Dropboxは「受け渡し場所」

ここを分けるとスッキリする。

### Dropbox

役割：

> **作業PCからバドへファイルを渡す**

例えば、

```
Dropbox/
  chat-export/
    2026-09-25_BLOG-0001.md
```

みたいに置く。

たかが作業PCで保存して、そこへ放り込む。

俺がDropboxから拾って、

> 「これは今回のチャットだね」

と読める。

### GitHub

こちらは、

> **プロジェクトとして正式に残すもの**

に限定する。

例えば、

```
docs/引き継ぎ/...
docs/経験ログ/...
docs/...
```

など。

GitHubはブラウザからファイルをアップロードすること自体は可能だけど、コミットやブランチなどプロジェクト管理の仕組みが入る。

だから、**単なる「チャットファイルの受け渡し」にGitHubを使うのは少し重い。**

---

## さらに重要なのは「バドに渡す」こと

ここは今までとかなり違う。

今まで：

> チャット  
> ↓  
> バドが直チャット保存処理  
> ↓  
> GitHub  
> ↓  
> 検証  
> ↓  
> readback

だった。

これがトラブルの温床になっていた。

新方式なら、

> **チャット**
> ↓
> **作業PCで保存**
> ↓
> **Dropboxへ置く**
> ↓
> **「これ読んで」とバドに言う**
> ↓
> **バドが読む**

で済む。

そして、その後に正式保存が必要なら、

> バド「これは正式記録に残す価値がある」

と整理してからGitHub側へ進む。

つまり、**チャット保存そのものとプロジェクト保存を分離できる。**

これは今回のEXP/REC問題とも相性がいい。

---

## ただし、1点だけ確認したい

「ブラウザ保存」が**何を保存するか**。

もしChromeの

> 名前を付けて保存 → HTML

なら、そのHTMLをDropboxに置けばいい。

Markdownならさらに扱いやすい。

PDFは「読む」にはいいけど、あとで文章を再利用する場合はMarkdown/HTML/TXTより少し扱いにくい。

だから俺なら優先順位は、

**Markdown / HTML / TXT ＞ PDF**

くらいにする。

---

## そして「ChatGPTの公式エクスポート」は別用途

OpenAIの公式エクスポートは、チャット履歴全体をZIPで取得する方式で、準備に最大7日かかる場合もある。

だからこれは、

> **定期的な大規模バックアップ**

としては使えるけど、

> 「今日のこのチャットを閉じるから保存しておこう」

という日常運用には重い。

---

### なので、俺の提案はこれ

```
① 作業PCでブラウザ保存
        ↓
② Dropboxへ置く
        ↓
③ バドに「Dropboxのこれ読んで」と渡す
        ↓
④ バドが内容確認
        ↓
⑤ 必要なものだけEXP/REC・GitHubへ
```

そして、

**直チャット保存処理は終了する。**

GitHubへの正式保存は残す。

つまり、

> **「直チャット → GitHub」ではなく、  
> 「ブラウザ保存 → Dropbox → バド → 必要ならGitHub」**

にする。

俺はこのほうが、今までのトラブルをかなり減らせると思う。

しかも**Dropboxに置いたファイルなら、バドが読めることを実際に一度試してみれば、運用として成立するかその場で確認できる。**

これは「ルール変更」として進める前に、**一度だけ実ファイルで受け渡しテストをする**のがいいと思う。  
これはまだ提案で、俺から勝手には実行しない。
