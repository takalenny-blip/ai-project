# `rules/運用ルール.md` 3タイミング改定対応表

## 目的

JUN監査で「修正して採用」とされた、上位3タイミング構造を `rules/運用ルール.md` に組み込むための対応表。

上位タイミングは次の3つだけとする。

1. たかから書き込みがあったとき
2. 自分の処理中
3. 終了時

その他の処理は上位タイミングではなく、条件・状態・分岐として配置する。

## 既存項目の配置

| 現行項目 | 配置先 | 扱い |
|---|---|---|
| 通常時の現在化・作業判断 | ① たかから書き込みがあったとき | 受領後の判断ゲートとして統合 |
| 作業対象・完了条件・更新対象の確定 | ① | 処理方針確定のための受領後処理 |
| 意思疎通・状態異常／価値発見インタビューゲート | ①＋② | ①で入力時の強い評価等を検知。②で処理中の異常・価値発見を検知した場合に分岐 |
| 外部提案・レビューの即時アクションゲート | ①＋② | ①で提案を受領・分類し、②で理解→採否→案→提案→実行→検証を進める |
| ルール有効性・行動化ゲート | ② | 処理中にルール不一致・行動化不足を検知した際の分岐として配置 |
| 通常作業の実行 | ② | 自分の処理そのもの |
| エラー・停滞・環境制約・判断不能 | ② | 例外分岐。必要なら停止・確認・インタビュー・ルール再確認 |
| 新しい事実・価値・改善点・方向転換 | ② | 価値発見・方針変更の分岐 |
| EXP/REC化判定 | ③ | 処理結果をクローズ時に整理。ただし②で候補を保持 |
| 直チャット保存 | ③ | 終了時の保存処理。明示的保存指示を受けた場合は①で保存対象を認識し、③で保存・読み戻しまで完了 |
| 「やりとり書き込んで」後処理 | ①→③ | ①で保存合図を検知・対象範囲を確定し、③で保存後のEXP/REC・インタビュー・状態確認を完了 |
| 保存前チェック | ③ | 保存実行直前の必須確認 |
| 保存後チェック | ③ | GitHub読み戻し・忠実性・安全性確認 |
| EXP/REC保存・読み戻し | ③ | 記録のクローズ処理 |
| 引き継ぎ更新 | ③ | 次セッションへのバトンタッチ |
| 完了条件確認 | ③ | クローズ判定 |
| 未完了・保留・未確認 | ③ | 完了扱いにせず、次の処理状態を確定 |

## 3タイミングの実行骨格

### ① たかから書き込みがあったとき

**受領 → 分類 → 現在化・作業判断 → 必要なインタビュー／提案処理への分岐 → 処理方針確定 → ②へ**

ここでは「作業開始時」という別タイミングを作らない。

### ② 自分の処理中

**実行 → 自律検証 → 異常／判断不能／ルール不一致／価値発見の検知 → 必要な分岐 → 処理継続 → 完了条件到達 → ③へ**

ここでは「異常発生時」「提案受領時」「価値発見時」などを独立した上位タイミングにしない。

### ③ 終了時

**完了条件照合 → 保存・記録 → 読み戻し・整合確認 → 引き継ぎ → クローズ → 次の入力待ち → ①へ**

## 重要な設計原則

- 3つの上位タイミング以外を増やさない。
- 既存処理を削除しない。
- 既存処理は3タイミングの内部に条件・状態・分岐として再配置する。
- ①→②→③→次の入力→①のループを明示する。
- ②でたかへの確認が必要になった場合は、確認結果を受けて処理を継続する。
- 「保存合図」は通常作業より優先して処理する既存ルールを維持する。
- 強い否定評価・意思疎通破綻・重要な評価は、既存のインタビュー優先ルールを維持する。
- JUN等の外部提案は「確認しました」で終了せず、既存の即時アクションルールを維持する。
- 変更後は実際にルールが行動を変えることを検証する。

## 反映方法

現行 `rules/運用ルール.md` の細則を削除するのではなく、冒頭の通常運用フローを3タイミングの実行骨格へ置き換え、5章の各横断ゲートについて「どのタイミングから起動するか」を明記する。

直チャット保存の細則（4章）は正本として維持し、3タイミングとの関係だけを明示する。

この対応表を確認したうえで、`rules/運用ルール.md` 本体を変更する。
