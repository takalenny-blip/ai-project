# 運用ルール

## 目的

このファイルは、`ai-project` における現在の作業手順と横断的な運用ルールを一本化する。日常の作業に組み込み、保存・更新漏れや「保存したつもり」を防ぐ。

また、過去ログに残った「次の作業」を現在の命令として機械的に再実行しない。過去の成功・失敗・判断を現在の作業判断へ反映し、同じ条件で同じ失敗を無意味に繰り返さない。

## 1. 運用フロー（通常時）

1. `BUD.md` を読み、現在の目的・現在状態・現在の次の一手を把握する。
2. 必要に応じて `docs/AI_READ_MAP.md`、`rules/README.md`、`docs/引き継ぎ/現在の引き継ぎ.md`、関係する `projects/` 等を確認する。
3. 過去ログを参照する場合は、事実・過去の判断・過去の計画・完了・失敗／破棄・再試行条件・現在有効なルールを区別する。
4. 作業開始前の現在化・作業判断ゲートを通す。
5. 今回の完了条件と、更新・保存が必要な関連ファイルを先に決める。
6. 作業を実行する。
7. 必要な記録・関連資料をGitHubへ保存する。
8. 保存したファイルを読み戻し、内容・整合性・次回への影響を確認する。
9. 必要ならEXP/REC、引き継ぎ、BUD等を更新し、再度読み戻す。
10. 完了条件を満たしたことを確認して完了とする。

## 2. 運用フロー（過去記録調査）

履歴調査・記事化・経緯確認・漏れ確認など、網羅性が目的の場合は通常の段階読み込みではなく、このフローを適用する。

1. 対象EXPを確定する。
2. GitHub上の実ファイルから、対象EXPに属するRECを全件列挙する。
3. 各RECについて、本文にある一次記録・関連資料への明示参照を確認する。
4. 明示的な直チャット参照がないRECは、発生日、タイトル・テーマ、特徴的な語句、直チャットのファイル名、EXP/REC-ID、関連ファイル名、前後の時系列を組み合わせて候補を探索する。
5. 候補となった直チャットを確認する。必要なら対象RECの前後の時系列も確認する。
6. 特定できない一次記録は推測せず、「特定できなかった」と記録する。
7. Coverageとして、対象EXP、REC件数・ID、確認した直チャット、未特定REC、未読候補と理由、追加調査事項を残す。
8. 次のAIがどこまで調査済みか判断できる状態にして完了とする。

**「READMEに載っている」「主要な3ファイルを読んだ」だけでは網羅調査の完了としない。** READMEは入口であり、調査対象のホワイトリストではない。

## 3. 運用フロー（EXP / REC）

### EXP

EXP-IDを発行 → EXPを作成 → ID管理台帳を更新 → GitHubへ保存 → 読み戻し確認。

### REC

所属EXPを確認 → REC-IDを発行 → RECを作成 → ID管理台帳の最終REC-IDを更新 → GitHubへ保存 → 読み戻し確認。

新規RECを作成するときは、可能な限り関連する `直チャット/` のパスを一次記録としてRECに残す。過去RECの原文を書き換えて出所を補うことはしない。

## 4. 運用フロー（直チャット保存）

直チャットに関する保存ルールは、この節を唯一の正本とする。別ファイルへ同じルールを分散させない。

### 4-1. 保存目的

たか↔バドの会話を、議事録・要約・再構成ではなく、後から検証可能な一次記録として確実にGitHubへ保存する。

「保存したつもり」を防ぐため、保存対象の会話本文をAIの整理・要約能力から切り離して扱う。

### 4-2. 保存単位

- 1ターン1ファイル。
- ファイル名：`YYYY-MM-DD_直チャット即時保存_連番.md`
- 連番は会話順序の正本とする。
- 現在の次番号をGitHub上の実ファイルから確認し、推測で欠番を埋めない。
- `[User]`、`[Bud]`、ユーザーが貼った場合の`[JUN]`等を発言者ラベルとして使用する。

### 4-3. 保存タイミング

**各ターンの返答を完成させるたびに、そのターンの原文をGitHubへ保存する。**

「ユーザーから保存指示が来たら保存する」方式は禁止する。

バドの返答については、送信する最終本文をそのまま保存対象とし、保存後のGitHub読み戻し確認を終えてから完了扱いにする。

### 4-4. 原文固定

保存対象は実際に会話へ提示した本文そのものとする。

- 要約しない。
- 言い換えない。
- 読みやすく整形し直さない。
- 議事録化しない。
- 「今回の要点」だけに置き換えない。
- 推測した過去発言を補わない。
- ユーザーが貼ったJUN・Claude等の回答は、取得できた提示本文をそのまま保存する。
- 取得できない部分は推測・再構成して補完しない。

### 4-5. 添付ファイル・画像のテキスト化記録

添付ファイルが提示された場合、原則として添付ファイルそのものをGitHubへバイナリ保存するのではなく、**「何を読み込み、何が読み取れたか」をテキストとして直チャットの一次記録へ残す。**

目的は、リポジトリを軽量に保ちながら、後から「AIが何を認識したか」を検証可能にし、画像・文書から得た事実とバドの解釈を混同しないことである。

#### 4-5-1. 添付ファイルの基本記録

添付を扱ったターンでは、可能な範囲で次の情報を記録する。

- `[添付ファイル] ファイル名.ext を読み込んだ。`
- `種別：Word / PDF / Excel / 画像 / その他`
- 読み取り結果を、対象に応じて以下の項目へ分離する。

#### 4-5-2. 文書・表計算等

Word、PDF、Excel等からテキストを取得できる場合は、要約ではなく**読み取り本文**として、取得できた内容を可能な限り原文に近い形で記録する。

- `読み取り本文`：文書から実際に取得できた文字・数値・表の内容。
- 書式、配置、画像、図形等がテキスト化できない場合は、その事実を明示する。
- 読み取れない箇所は推測で補完せず、`不明／判読不能`として記録する。

#### 4-5-3. 写真・スクリーンショット等

画像を読み取った場合は、次を分離する。

- `表示文字`：画像から実際に読み取れた文字。判読できない文字を推測して補完しない。
- `画像内容`：画面、物体、ボタン、状態、配置など、目視できる事実。
- `不明／判読不能`：文字や状態等で確認できなかったもの。

#### 4-5-4. バドの解釈

画像・文書から得た事実とは別に、バドが推測・判断・原因分析等を行った場合のみ、`バドの解釈`として明確に分離する。

`表示文字`、`画像内容`、`読み取り本文`に、バドの推測や意味づけを混ぜない。

#### 4-5-5. 添付そのものと一次記録の区別

「添付ファイル自体を保存した」ことと、「添付ファイルを読み取り、その内容をテキストとして一次記録へ保存した」ことは別物として扱う。

通常は後者を基本とする。ただし、元のバイナリ自体が後日の検証に不可欠な場合は、別途保存方法を判断し、その必要性と保存場所を明示する。

#### 4-5-6. 読み取り不能時

添付ファイルを開けない、解析できない、文字が判読できない等の場合、内容を推測して記録してはならない。

- 読み込みできた範囲だけを記録する。
- 読み取れなかった範囲は`不明／判読不能`または`読み取り不能`と明示する。
- 添付内容を確認できていないのに、確認したような記録を作らない。

### 4-6. 保存前チェック

GitHubへ書き込む前に、次を確認する。

1. 今回保存するのが「このターン」だけか。
2. `[User]` / `[Bud]` / `[JUN]`等の発言者区分が正しいか。
3. 保存本文が実際の会話本文そのものか。
4. 要約・再構成・追加解釈が混入していないか。
5. 添付ファイルの読み取り結果が、`表示文字`、`画像内容`、`読み取り本文`、`バドの解釈`、`不明／判読不能`の区分を守っているか。
6. 認証情報、Cookie、セッション情報、パスワード、APIキー等を保存対象にしていないか。
7. 連番が既存ファイルと衝突していないか。

### 4-7. 保存後チェック（必須）

保存処理が成功しただけでは完了としない。必ずGitHubから同じファイルを読み戻す。

#### 第1段階：存在確認

- 指定したパスのファイルが存在する。
- ファイル名と連番が正しい。

#### 第2段階：忠実性確認

読み戻した本文を、保存しようとした原文と照合する。

最低限、次を確認する。

- 発言者ラベルが一致する。
- 発言順が一致する。
- 文章、記号、改行、コード、箇条書き等に意図しない欠落・追加・言い換えがない。
- ユーザーが貼った他AI回答が省略されていない。
- 添付ファイルについて記録した読み取り結果が、実際に確認できた内容と一致している。
- 要約文や再構成文になっていない。

**第1段階だけで完了判定してはならない。**

### 4-8. 不一致時の処理

読み戻し結果が原文と一致しない場合は、そのターンを「保存完了」と扱わない。

1. 不一致箇所を特定する。
2. 現在のファイルを読み、SHAを確認する。
3. 完全な原文で更新する。
4. 再度読み戻す。
5. 原文一致を確認するまで完了としない。

原文そのものを取得できなくなった場合は、推測で修復しない。「原文取得不能」と明示して停止する。

### 4-9. 失敗時の扱い

- GitHub保存に失敗した場合、保存済みとは扱わない。
- 同じ条件で無限に再試行しない。原因・条件を確認してから再試行する。
- 連番だけを先に消費したり、欠番を推測で埋めたりしない。
- 保存失敗を隠さない。

### 4-10. 直チャットの役割分離

- **直チャット**：原文一次記録。
- **BUD**：現在の目的・状態・次の一手。
- **引き継ぎ**：セッション結果と次回判断材料。
- **EXP / REC**：経験資産としての整理・分析。

要約や整理が必要でも、直チャット原文を要約版で置き換えない。

### 4-11. バドの実行ルーチン

今後、バドは各ターンについて次の順序を固定する。

`会話ターン発生 → 原文を保持 → 添付があれば読み取り・事実と解釈を分離 → 連番確認 → GitHub保存 → 読み戻し → 存在確認 → 原文忠実性確認 → 完了判定 → ユーザーへ返答完了`

セッション終了時にまとめて保存する運用には戻さない。

### 4-12. 直チャット保存の限界

このルールは、バドが現在のChatGPT会話本文を取得できる範囲で原文保存を保証するための運用手順である。ChatGPT側から取得できない過去会話や、削除済み会話を自動復元する仕組みではない。

また、添付ファイルの読み取り結果についても、実際にバドがアクセス・解析できた範囲を超えて内容を推測することは保証しない。

したがって「取得できない原文を推測して完全ログにする」「読み取れない添付内容を推測して記録する」ことは禁止する。

### 4-13. 直チャット関連資料の位置づけ

直チャット保存に関する現在有効なルールは、この `rules/運用ルール.md` に集約する。

`直チャット/README.md` は管理方針・索引用の補助資料とし、毎ターン更新しない。直チャット保存ルールの正本にはしない。

同一内容の直チャット保存プロトコルを別の現在ルールファイルとして維持しない。

## 5. 運用フロー（GitHub保存・読み戻し）

1. 更新対象と完了条件を確認する。
2. GitHub上の現在ファイルを読み、最新内容とSHAを確認する。
3. 完全な更新内容を保存する。
4. 保存後、同じファイルをGitHubから読み戻す。
5. 変更内容が実際に入っていることを確認する。
6. 関連ファイルとの矛盾がないことを確認する。
7. 次のセッションが古い手順へ戻らないことを確認する。
8. ID台帳が関係する場合は整合を確認する。

**「保存処理を呼んだ」「保存したつもり」だけでは完了としない。**

## 6. 運用フロー（セッション終了・引き継ぎ）

1. 今回の作業結果を棚卸しする。
2. `docs/引き継ぎ/現在の引き継ぎ.md` に、今回やったこと、完了条件、確定、未確定、未着手、失敗・再試行注意、次回判断、次回操作、禁止・手戻り、関連資料を残す。
3. 今回発生した重要情報を、決定／変更／確定事実／失敗／未確定／次回判断／次回操作／相談・依頼／関連ファイル／EXP-REC／禁止・再試行条件／未保存に分類する。
4. 各情報を最も適切な現在資料へ配置する。
5. 直チャットとGitHub上の保存内容に差分がないか確認する。
6. 引き継ぎを保存し、読み戻す。

## 7. 失敗・再試行ルール

失敗は記録し、成功したことに書き換えない。一方で、失敗を一律に永久禁止・無条件再試行とはしない。

失敗記録には可能な限り、発生日、対象環境、操作、結果、失敗理由、再試行可能条件、次に取るべき別手段を残す。

- **同じ環境・同じ条件・同じ方法**：無条件に再試行しない。
- **環境が変わった**：同じ方法を再検証してよい。ただし現在の目的との一致を確認する。
- **条件が変わった**：結果に影響すると説明できる場合に再検証してよい。
- **新しい情報が得られた**：その情報を根拠に再検証してよい。

環境制約・権限・利用できなかった手段も、次の判断に影響する場合は現在状態の一部として引き継ぐ。

## 8. 記録ルール

- 作業上の事実は可能な限りテキストで残す。
- コマンド、入力、出力、エラー、設定値、操作結果は、可能な限りコピー＆ペーストで直チャットへ残す。
- 画像は主記録ではなく、テキストだけでは十分に表せない物理状態・外観・画面状態等の補助記録とする。
- 重要な事実を画像だけに依存しない。
- 過去資料を現在の事実へ勝手に書き換えない。
- 事実と推測を混同しない。
- 過去の「次にやること」は歴史上の計画であり、現在の命令ではない。

## 9. 禁止事項

- 過去ログの次回アクションを、現在化・判断ゲートなしに現在の作業として実行しない。
- 「前回ログにある」「未確認欄に残っている」だけで再実行しない。
- 当時未完了という理由だけで、現在の必要性・優先度を確認せずタスクを実行しない。
- 同じ環境・条件・方法で既知の失敗を無条件に繰り返さない。
- 認証情報、Cookie、セッション情報、パスワード、APIキー等をチャットやGitHubへ記録しない。
- 直チャットを要約・再構成して原文として保存しない。
- ユーザーが貼った他AI回答を省略・要約・再構成して保存しない。
- 網羅性が目的の調査を、少数ファイルを読んだだけで完了扱いしない。
- 過去のAIの固定役割を現在の必須工程として扱わない。

## 10. 現在化・作業判断ゲート

### A. 既知事項

今回すでに確定していることを確認し、目的なく再実行しない。

### B. 禁止事項・手戻り

同じ環境での既知の失敗、既に不要と判断した調査、戻ってはいけない段階を確認する。

### C. 未解決事項

現在の目的を達成するために、まだ必要な確認だけを残す。

### D. 環境差

PC、OS、権限、ブラウザ、ネットワーク、アカウント状態等、過去と現在の条件差を確認する。

### E. 目的・優先度

候補作業が現在の最上位目的に寄与するか、より優先すべき未解決事項がないか確認する。

### F. ゾンビタスク判定

当時未完了でも現在は不要になっていないか確認する。現在の目的・環境・優先度と一致しない古い未完了タスクを自動昇格させない。

### G. 次の一手

A～Fを照合した結果として、**現在初めて必要になる作業を1つ選ぶ。** 根拠を説明できる状態にする。

不明確な場合は、過去タスクを無条件に実行せず、たかへ確認する。

## 10-1. AI判断の相談・エスケープ

バドは原則として自律的に判断して進める。ただし、以下のいずれかに該当する場合は、無理に自己判断せず、たかに相談する。

1. **目的・方向性の衝突**：現在の作業がBUDの現在の目的・優先度と衝突する、または優先順位を決められない場合。
2. **ルール同士の矛盾・重要な曖昧さ**：適用すべきルール同士が矛盾する、または解釈が曖昧で、進めるとルール違反や抜け道を生むおそれがある場合。
3. **不可逆・重大な影響を伴う変更**：データ削除、大規模な構造変更、認証関連の操作など、復旧が難しい、または影響が重大な変更を伴う場合。
4. **たかの意思・優先順位によって選択が変わる重要な分岐**：技術的・合理的に複数の選択肢が成立し、技術的正しさだけでは決められず、たかの判断・好み・優先順位によって選択が変わる場合。

相談は判断放棄ではない。相談時には、**何が起きているか、なぜバドだけで決めないのか、選択肢A/B/C、各選択肢のメリット・デメリット、バドの推奨案**を整理して提示する。

相談によって解決した事項のうち、再発する可能性があるものは、必要に応じて運用ルールとして明文化する。

## 11. 完了条件

作業開始前に、少なくとも以下を明確にする。

- 何が確認できれば完了か
- 何は未確定として残るか
- どのファイルを更新するか
- 保存後に何を読み戻すか

結果確認、必要な記録保存、読み戻しまで終えて完了とする。

## 12. 関連資料の更新判断

作業結果に応じて、次の更新要否を判断する。

- `BUD.md`
- `docs/引き継ぎ/現在の引き継ぎ.md`
- `projects/` の対象資料
- `rules/` の現在ルール
- `経験ログ/` のREC
- `指針等/ID管理台帳.md`
- 必要に応じて `直チャット/`

特に、新しい成功・失敗・禁止事項・判断変更が発生した場合は、次のセッションが同じ判断をしないための記録を残す。

## 13. 運用上の位置づけ

`BUD.md` は現在の目的・現在状態・現在の次の一手を集約する最上位資料である。

このファイルは、**どう動くか**を定義する。手順は「運用フロー」、横断的な制約は「ルール」、禁止する事項は「禁止事項」として明確に区別する。

過去の詳細資料は歴史資料として保持し、現在のルールを過去資料から推測しない。
