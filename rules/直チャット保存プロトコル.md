# 直チャット保存プロトコル

更新日：2026-09-09

## 目的

たか↔バドの会話を、議事録・要約・再構成ではなく、後から検証可能な一次記録として確実にGitHubへ保存する。

このプロトコルは「保存したつもり」を防ぐための実行手順であり、保存対象の会話本文をAIの整理・要約能力から切り離して扱う。

## 1. 保存単位

- 1ターン1ファイル。
- ファイル名：`YYYY-MM-DD_直チャット即時保存_連番.md`
- 連番は会話順序の正本。
- 現在の次番号をGitHub上の実ファイルから確認し、推測で欠番を埋めない。
- `[User]`、`[Bud]`、ユーザーが貼った場合の`[JUN]`等を発言者ラベルとして使用する。

## 2. 保存タイミング

**各ターンの返答を完成させるたびに、そのターンの原文をGitHubへ保存する。**

「ユーザーから保存指示が来たら保存する」方式は禁止する。

バドの返答については、送信する最終本文をそのまま保存対象とし、保存後のGitHub読み戻し確認を終えてから完了扱いにする。

## 3. 原文固定

保存対象は実際に会話へ提示した本文そのものとする。

- 要約しない。
- 言い換えない。
- 読みやすく整形し直さない。
- 議事録化しない。
- 「今回の要点」だけに置き換えない。
- 推測した過去発言を補わない。
- ユーザーが貼ったJUN・Claude等の回答は、取得できた提示本文をそのまま保存する。
- 取得できない部分は`不明`等と勝手に補完せず、未取得として扱う。

## 4. 添付ファイル・画像のテキスト化記録

添付ファイルが提示された場合、原則として添付ファイルそのものをGitHubへバイナリ保存するのではなく、**「何を読み込み、何が読み取れたか」をテキストとして直チャットの一次記録へ残す。**

目的は、リポジトリを軽量に保ちながら、後から「AIが何を認識したか」を検証可能にし、画像・文書から得た事実とバドの解釈を混同しないことである。

### 4-1. 添付ファイルの基本記録

添付を扱ったターンでは、可能な範囲で次の情報を記録する。

- `[添付ファイル] ファイル名.ext を読み込んだ。`
- `種別：Word / PDF / Excel / 画像 / その他`
- 読み取り結果を、対象に応じて以下の項目へ分離する。

### 4-2. 文書・表計算等

Word、PDF、Excel等からテキストを取得できる場合は、要約ではなく**読み取り本文**として、取得できた内容を可能な限り原文に近い形で記録する。

- `読み取り本文`：文書から実際に取得できた文字・数値・表の内容。
- 書式、配置、画像、図形等がテキスト化できない場合は、その事実を明示する。
- 読み取れない箇所は推測で補完せず、`不明／判読不能`として記録する。

### 4-3. 写真・スクリーンショット等

画像を読み取った場合は、次を分離する。

- `表示文字`：画像から実際に読み取れた文字。判読できない文字を推測して補完しない。
- `画像内容`：画面、物体、ボタン、状態、配置など、目視できる事実。
- `不明／判読不能`：文字や状態等で確認できなかったもの。

### 4-4. バドの解釈

画像・文書から得た事実とは別に、バドが推測・判断・原因分析等を行った場合のみ、`バドの解釈`として明確に分離する。

`表示文字`、`画像内容`、`読み取り本文`に、バドの推測や意味づけを混ぜない。

### 4-5. 添付そのものと一次記録の区別

「添付ファイル自体を保存した」ことと、「添付ファイルを読み取り、その内容をテキストとして一次記録へ保存した」ことは別物として扱う。

通常は後者を基本とする。ただし、元のバイナリ自体が後日の検証に不可欠な場合は、別途保存方法を判断し、その必要性と保存場所を明示する。

### 4-6. 読み取り不能時

添付ファイルを開けない、解析できない、文字が判読できない等の場合、内容を推測して記録してはならない。

- 読み込みできた範囲だけを記録する。
- 読み取れなかった範囲は`不明／判読不能`または`読み取り不能`と明示する。
- 添付内容を確認できていないのに、確認したような記録を作らない。

## 5. 保存前チェック

GitHubへ書き込む前に、次を確認する。

1. 今回保存するのが「このターン」だけか。
2. `[User]` / `[Bud]` / `[JUN]`等の発言者区分が正しいか。
3. 保存本文が実際の会話本文そのものか。
4. 要約・再構成・追加解釈が混入していないか。
5. 添付ファイルの読み取り結果が、`表示文字`、`画像内容`、`読み取り本文`、`バドの解釈`、`不明／判読不能`の区分を守っているか。
6. 認証情報、Cookie、セッション情報、パスワード、APIキー等を保存対象にしていないか。
7. 連番が既存ファイルと衝突していないか。

## 6. 保存後チェック（必須）

保存処理が成功しただけでは完了としない。必ずGitHubから同じファイルを読み戻す。

### 第1段階：存在確認

- 指定したパスのファイルが存在する。
- ファイル名と連番が正しい。

### 第2段階：忠実性確認

読み戻した本文を、保存しようとした原文と照合する。

最低限、次を確認する。

- 発言者ラベルが一致する。
- 発言順が一致する。
- 文章、記号、改行、コード、箇条書き等に意図しない欠落・追加・言い換えがない。
- ユーザーが貼った他AI回答が省略されていない。
- 添付ファイルについて記録した読み取り結果が、実際に確認できた内容と一致している。
- 要約文や再構成文になっていない。

**第1段階だけで完了判定してはならない。**

## 7. 不一致時の処理

読み戻し結果が原文と一致しない場合は、そのターンを「保存完了」と扱わない。

1. 不一致箇所を特定する。
2. 現在のファイルを読み、SHAを確認する。
3. 完全な原文で更新する。
4. 再度読み戻す。
5. 原文一致を確認するまで完了としない。

原文そのものを取得できなくなった場合は、推測で修復しない。「原文取得不能」と明示して停止する。

## 8. 失敗時の扱い

- GitHub保存に失敗した場合、保存済みとは扱わない。
- 同じ条件で無限に再試行しない。原因・条件を確認してから再試行する。
- 連番だけを先に消費したり、欠番を推測で埋めたりしない。
- 保存失敗を隠さない。

## 9. 役割分離

- **直チャット**：原文一次記録。
- **BUD**：現在の目的・状態・次の一手。
- **引き継ぎ**：セッション結果と次回判断材料。
- **EXP / REC**：経験資産としての整理・分析。

要約や整理が必要でも、直チャット原文を要約版で置き換えない。

## 10. バドの実行ルーチン

今後、バドは各ターンについて次の順序を固定する。

`会話ターン発生 → 原文を保持 → 添付があれば読み取り・事実と解釈を分離 → 連番確認 → GitHub保存 → 読み戻し → 存在確認 → 原文忠実性確認 → 完了判定 → ユーザーへ返答完了`

セッション終了時にまとめて保存する運用には戻さない。

## 11. この仕組みの限界

このプロトコルは、バドが現在のChatGPT会話本文を取得できる範囲で原文保存を保証するための運用手順である。ChatGPT側から取得できない過去会話や、削除済み会話を自動復元する仕組みではない。

また、添付ファイルの読み取り結果についても、実際にバドがアクセス・解析できた範囲を超えて内容を推測することは保証しない。

したがって「取得できない原文を推測して完全ログにする」「読み取れない添付内容を推測して記録する」ことは禁止する。
