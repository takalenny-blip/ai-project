# 構造変更時・独立監査ガード

## 目的

大規模な構造変更や正本・生成ビューの仕組みを変更した直後に、変更した個別ファイルだけでなく、次に参加するAIが読む入口・現在資料・運用ルール・機械的ガードの前提まで確認し、コンテキスト断絶による誤操作を早期に発見する。

## 発動条件

この監査は**構造変更時だけ**発動する。日常のDiMORA自動化など通常作業のたびにリポジトリ全体を再監査しない。

発動対象の例：

- 現在状態の正本を変更・移行したとき
- 正本から生成するビューの構造や生成方式を変更したとき
- CIガードや保存・現在化スクリプトの責務を変更したとき
- AIが最初に読む入口資料の意味や読解順を変更したとき
- 過去の事故から、新しい構造的な再発防止策を導入したとき

## 監査項目

1. `docs/現在状態.json` が現在状態の唯一の正本として扱われているか。
2. `BUD.md` と `docs/引き継ぎ/現在の引き継ぎ.md` が正本から生成されるビューとして扱われ、手編集前提の説明が残っていないか。
3. ルート `README.md` が現在の正本・ビュー構造と一致しているか。
4. 自然言語で定めた重要ルールと、それを機械的に検査・強制するスクリプト／CIの対応が追跡可能か。
5. 次に参加するAIが古い入口情報や過去の「次の一手」を現在の命令として誤認する経路が残っていないか。
6. 変更によって新しい実害シナリオが生じていないか。
7. CI・生成処理・保存処理の検証を通過しているか。

## ルールと機械的強制の対応

現在の正本・生成ビュー・保存後現在化に関する主要な境界は、`scripts/check_repo_integrity.py` と `scripts/save_and_currentize.py` によって機械的に検査・強制される。自然言語のルールだけでなく、これらのスクリプトとCIによるハードな検証境界を合わせて確認する。

ただし、**スクリプト名が書かれていること自体を安全性の保証とはしない**。実際のスクリプト、CI定義、生成結果、実行結果を確認して判断する。

## 通常運用への復帰

構造変更時の監査と必要な修正・検証が完了したら、監査を常時実行するのではなく通常工程へ戻る。DiMORA本来の作業を進めながら、CIと現在資料の整合性を静かに監視する。

## 完了条件

- 入口資料と現在状態の前提が一致している。
- 正本と生成ビューの関係が明示されている。
- 重要ルールと機械的ガードの対応が確認できる。
- 実害につながるコンテキスト断絶がないことを確認した。
- CI・生成・整合性検証が成功している。
- その後は不要なインフラ変更を続けず、通常工程へ復帰できる状態になっている。
