# 再開・検索ガード

このファイルは、rules/運用ルール.md の運用を補助する、再開・検索時の最小限のガードである。

## 目的

検索失敗やセッション再開を理由に、すでに確認済みの事実・完了事項・既知の失敗条件を無意味に再調査・再実行することを防ぐ。

## 絶対原則

1. 一次記録・ファイルが存在することを確認済みなのに検索でヒットしない場合、「存在しない」「まだ調べていない」と断定しない。
2. 検索に失敗した場合は、可能ならローカルclone、直接ファイル名指定、既知のパスなど、別の到達経路を優先する。
3. 日常作業キューはDropbox固定ボード、技術的な事実は対象の原本とPR・コミット・Actions等の証拠で確認する。検索失敗だけを理由に確認済みの事実を未確認へ戻さない。
4. 旧BUD・引き継ぎ文書・過去の作業説明を、現在状態や作業キューの正本として使わない。
5. 既知の失敗条件が確認済みなら、同じ条件を理由なく再実行しない。
6. ユーザーが現在のGUI状態を明示した場合、その状態を現在状態として扱い、すでに完了したGUI操作をゼロから案内し直さない。
7. VAIO Pでは手入力困難・コピー＆ペースト不安定を前提とし、長文手入力を必要とする手順を基本案として出さない。

## トリガー

- 検索結果が出ない。
- GitHub API・検索サービス等が制限・失敗する。
- セッション再開時に過去資料と実際の成果物・証拠の不一致が疑われる。
- ユーザーが「もう調べた」「そこは開いている」等、現在の状態を明示する。

## 必須行動

- 作業候補・状態・優先度・次のアクションはDropbox固定ボードで確認する。
- 技術的な事実は、対象の実装・設定・文書・PR・コミット・Actionsの原本を確認する。
- 検索経路だけが失敗している可能性を切り分ける。
- 可能なら別経路で一次記録へ到達する。
- 到達できない場合は「未到達」と記録し、「未存在」とは扱わない。
- 新しい事実がない限り、同じ調査を最初から繰り返さない。

## 完了条件

検索失敗時に、(1) データ不存在と断定していない、(2) 既知事項をリセットしていない、(3) 利用可能な別経路を優先した、または到達不能を明示した、の3点を満たす。
