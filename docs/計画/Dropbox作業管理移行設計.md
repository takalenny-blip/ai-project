# Dropbox作業管理への移行設計

更新日：2026-10-16
状態：設計案（未マージ・未適用）

## 1. 目的

日常の作業キュー・状態・優先順位・期限・次の行動をDropboxで一元管理し、古い情報を現在の命令として誤採用する事故と、同一作業の二重管理を減らす。GitHubはコード、技術的事実、正式なプロジェクト文書、運用ルール、原本と変更履歴を管理する。

## 2. 絶対条件

- `直チャット/` の既存原本は無条件で保存する。既存ファイルの変更・削除・改名・上書き・置換は禁止。
- 直チャットの訂正・注釈・解釈は、元ファイルを編集せず、日付と対象を明記した別の補足ファイルに記録する。
- 新しい直チャット原本の追加は許可する。追加と既存原本の変更を機械的に区別する。
- 古い作業情報・重複したキュー項目・陳腐化した手順は積極的に整理する。ただし、履歴原本と技術的証拠は作業キューと同じ扱いで削除しない。
- 既知の保留条件を、古いGitHub項目が残っていることだけを理由に解除しない。特にMarkdown exporterは、実害が確認されるまで再調査しない。
- 外部AIの報告は、変更の事実や承認そのものではない。共有権限の変更、原本復元、削除、既決事項の変更は根拠と影響範囲を確認する。

## 3. 役割と正本

### Dropbox

- 日常の作業一覧、状態、優先度、期限、依存関係、次の行動、ユーザー指示、最終確認日を管理する。
- 完了した作業は証拠を記録してからアーカイブへ移す。作業キューから除外する場合も、直チャット原本や技術的証拠を削除しない。
- 優先度はユーザー指定がない限り「未指定」とする。

### GitHub

- ソースコード、CI、正式な運用ルール、設計・仕様、技術的事実、直チャット原本、PR・commit等の変更証拠を管理する。
- Dropboxへ切り替えた後、`docs/現在状態.json` はDropboxの作業キューを複製する正本としては使わない。必要な技術状態・プロジェクト背景・入口案内だけを保持し、作業キューの旧記述を残さない。
- BUD/引き継ぎの生成ビュー、README、`docs/AI_READ_MAP.md`、運用ルール、入口検査、CI、関連テストを一括で更新し、Dropboxが唯一の日常作業キューであることを一致させる。

## 4. ボードの必須フィールド

- 一意のID
- 作業名／領域
- 状態：未着手、進行中、外部待ち、判断待ち、保留、完了
- 優先度：ユーザー指定値または未指定
- 期限：具体的な日付または未設定
- 目的と完了条件
- 確認済み事実・未確認事項
- 次のアクション（実行可能な粒度）
- 依存関係／再実行禁止条件
- たかの指示・判断待ち事項
- 完了証拠（PR、commit、検査結果、外部サービス結果等）
- 最終確認日・更新者
- 必要に応じて親ID、アーカイブ先

「試みた」だけで完了にしない。外部待ちと保留を「未着手」に丸めない。古い項目は、現行の状態と根拠を照合してからアーカイブする。

## 6. 切替工程とゲート

### Phase A — 現状固定・対応表

1. GitHub正本、関連PR/commit、Dropboxボードを読み取り専用で照合する。
2. GitHubの各作業項目を、Dropboxの既存ID、新規ID、完了証拠、保留、ユーザー判断待ちのいずれかへ対応付ける。
3. 直チャット原本の現存ファイル一覧とGit履歴を別に記録する。過去に削除されたファイルは、内容の重複・保存済みの有無を確認するまで復元しない。
4. ボードの現行版を別名のバックアップとして保全し、原本に対する上書き編集を避ける。

### Phase B — ボード準備・書込み検証

1. 必須フィールドと状態語彙を整える。
2. 既存ボードを直接壊さず、版管理可能な新しい作業ボード案を用意する。
3. 1件の試験項目で書込み、再読込み、表示・型・改行・文字化けを確認する。
4. 成功証拠を記録する。書込み経路が確立するまでは、移行済みと宣言しない。

### Phase C — 原本保護ガード

1. CIで `直チャット/` 内の既存ファイルの変更・削除・改名を失敗にする。
2. 新規追加は許可し、既存ファイルの内容変更は、ファイル名や更新日時だけでなくGit差分で検出する。
3. 保護対象の初期一覧またはハッシュ基準を記録し、変更検出の回帰テストを追加する。
4. 過去の削除14件は、原本の重複有無を照合し、復元対象と証拠を別途提案する。自動復元しない。

### Phase D — GitHub入口・CIの一括切替

1. README、`docs/AI_READ_MAP.md`、`rules/運用ルール.md`、`docs/現在状態.json`、BUD/引き継ぎ生成、入口検査、関連CI・テストの全参照を棚卸しする。
2. Dropboxを作業キューの正本とする入口・再開ルールへ一括変更する。
3. GitHub正本から作業キューを重複生成する経路と旧キュー参照を除去する。ただし、コード・技術状態・根拠・履歴原本は保持する。
4. CIと回帰テストを実行し、旧ルールが残っていないこと、原本保護ガードが機能すること、生成ビューに矛盾がないことを検証する。
5. 切替PRはテスト結果と影響範囲をレビュー可能な状態にし、mainへのマージ前に確認する。

### Phase E — コールドスタート検証・整理

1. 新しいAIセッションを想定し、GitHub入口からDropboxボードへ到達して正しい次の作業を判断できるか確認する。
2. 保留中の項目が勝手に再開されないこと、完了済み工程が巻き戻らないこと、優先度を勝手に設定しないことを確認する。
3. 検証合格後、旧キュー専用の記述・重複ビューを整理する。
4. 削除対象は参照元・依存・代替先を確認し、原本保護の対象外であることを確認してから扱う。

## 7. 完了条件

- Dropboxが日常作業キューの唯一の正本として案内される。
- GitHubのREADME、読解マップ、運用ルール、生成ビュー、CI、テストに旧キューとの矛盾がない。
- 作業項目すべてに移行先または明示的な保留・完了根拠がある。
- 書込みと再読込みが実証されている。
- `直チャット/` の既存原本に変更・削除・改名・上書きがなく、CIで再発を検出できる。
- TASK-005の保留条件、ユーザー未決事項、外部待ちの条件が維持される。
- コールドスタート検証に合格する。

## 8. 判断待ち・確認待ち

- PAT-EXPIRYの認証方式・承認者の選択。期限と影響の確認は進めても、選択は独断で行わない。
- Dropboxの共有リンク権限。実際のリンクの audience と access level を確認し、共有範囲の変更は明示的な承認なしに行わない。
- 過去に削除された直チャット14件の復元。重複確認と復元候補一覧の提示後に扱う。
- Dropboxの既存Excelを直接更新するか、新しい版・形式で切り替えるか。安全な書込み・再読込み経路の検証結果を見て決める。
