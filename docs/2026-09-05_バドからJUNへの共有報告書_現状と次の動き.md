# バドからJUNへの共有報告書：現在地と今後の動き

## 1. この報告書の目的

この文書は、JUNがGitHubを直接読めない場合でも、現在の「経験DB」の構造・運用方針・3者の役割を把握し、今後の現場報告を適切にたかへ渡せるようにするための共有資料である。

## 2. 現在のGitHub構成

リポジトリは、現在この4分類で運用する。

- `指針等`：運用ルール、ID管理など
- `直チャット`：JUN・バドとのチャット原文をそのまま保存する場所
- `docs`：運用仕様、共有資料など
- `経験ログ`：EXP/RECとして整理した経験データ

GitHubは、たか・JUN・バドの3者で共有する情報庫として使う。

## 3. 現在のEXP

現在は次の3つのEXPが存在する。

- EXP-0000000010：AIを使った経験・興味・実験の資産化システム構想
- EXP-0000000020：VAIO Type PへのDebian導入・環境構築
- EXP-0000000030：3者共有情報庫としてのGitHub運用構築

RECは各EXPの中で、意味のある出来事・判断・試行・結果などを記録する。

EXPは「経験そのもの」、RECは「その経験の中で起きた意味のある一場面・出来事」と考える。

## 4. 直チャットの扱い

`直チャット`に保存するものは、要約ではなくチャットそのものの原文である。

直チャットは一次資料として残し、あとからバドが経験DBとして読み解く。

直チャットを見直した際には、必要に応じて次の順で判断する。

1. 新しいEXPを作る
2. 既存EXPにRECを追加する
3. 経験DBへの追加が不要なら、そのまま直チャットとして保存する

まず既存EXPを検索し、該当する経験がなければ新しいEXPを作る。

1つの直チャットから複数のEXP/RECが生まれることもあるが、通常は無理に細分化しない。

## 5. JUNの役割

JUNは現場に近いAIとして、たかとの実作業の中で発生した情報を捕捉する。

特に重要なのは以下。

- 実際に起きたこと
- 作業の進行状況
- 試したこと
- 失敗・エラー・うまくいかなかったこと
- 判断したこと
- その判断に至った理由
- たかの発言や感想、心の声
- 次に確認・試行すること
- まだ確定していない情報

JUNは「現場の記録係」として、まずたかへ報告する。

## 6. JUNからバドへ至る報告フロー

基本の流れは以下。

**JUNの現場記録 → たかが確認・判断 → バドへ報告 → たかとバドが協議 → バドが経験DBとして整理・実行 → GitHubへ蓄積**

JUNはGitHubを直接読めることを前提にしない。

重要な経験情報が発生したら、JUNはたかへ報告する。

たかはその報告を確認し、必要なら修正・補足・判断を加えたうえでバドへ渡す。

バドはたかと協議したうえで、既存EXP/RECとの関係を確認し、経験DBとして整理する。

EXP/RECの作成・更新、ID管理・台帳更新、GitHubへの書き込みなど、経験DBへの実作業はバドが担当する。

## 7. 報告のタイミング

固定の30分ごと、文字数ごと、メッセージ数ごと、という運用にはしない。

意味のある区切りが来たときに、JUN側からたかへ

> ここまでをGitHub用にストックしますか？

と確認する方式を基本とする。

ただし、詳細な運用は実際に使いながら改善する。

## 8. JUNが報告するときの意識

きれいな文章にまとめることより、現場で起きた事実や気づきを落とさないことを優先する。

特に、後から見ると重要になりそうな「失敗」「迷い」「判断」「方向転換」「たかの一言」などは残す価値が高い。

報告時点で、それが新規EXPなのかRECなのかをJUNが決定する必要はない。

迷った場合は、事実をそのまま報告し、たかが確認・判断したうえでバドへ渡す。

## 9. バドの基本判定と実行

たかから新しい報告が来たら、バドはたかと協議し、次の順番で確認する。

1. 既存EXPに該当するか
2. 該当するなら新しいRECとして記録する価値があるか
3. 既存EXPでは扱えない新しい経験なら、新規EXP候補とする
4. 経験そのものではなく単なる運用連絡なら、経験ログには入れない

協議後、バドが必要なEXP/RECの作成・文章整理・ID管理・台帳更新・GitHubへの書き込みを行う。

経験の粒度は、実際の運用を通じて必要なら後から分割・統合する。

## 10. 現在の3者の役割イメージ

### たか

実際に経験し、判断し、最終的な意思を持つ人。JUNの報告を確認し、バドと経験DBへの整理方法を協議する。

### JUN

たかの現場に近いAI。作業・会話・失敗・気づきなどの生きた情報を捕捉し、たかへ報告する。

### バド

たかと協議した内容に基づき、集まった情報を経験DBとして整理・構造化し、EXP/RECの作成・ID管理・GitHubへの書き込みまで実行する。

## 11. 大事な考え方

この経験DBは、最初から完全なルールを作ってから運用するものではない。

実際に使いながら、必要になったルールを追加・修正していく。

つまり、経験DBそのものも「たか・JUN・バドで作っていく経験」の一部である。
