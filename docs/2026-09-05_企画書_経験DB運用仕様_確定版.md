# 経験DB運用仕様 企画書（確定版）

- **策定日**: 2026-09-05
- **更新日**: 2026-09-07
- **対象**: EXP / REC / 直チャットを中心とした経験DB運用
- **位置づけ**: 現時点で合意した運用仕様を記録する確定版

## 1. 目的

日々の作業、試行錯誤、判断、結果、気づきを流さずに記録し、後から検索・再利用できる「経験DB」として蓄積する。

単なる成功事例だけではなく、途中経過、失敗、判断の変化、たかの気持ちを含む実際の経験を残すことを重視する。

## 2. 基本分類

プロジェクト内の情報は、原則として次の4分類とする。

1. `指針等`
2. `直チャット`
3. `docs`
4. `経験ログ`

## 3. EXP（経験）

### 3.1 定義

EXPは「経験そのもの」を表す中粒度の単位とする。

例：

- `VAIO PへのDebianインストール`

EXPは単なる成果物や報告書ではなく、一連の経験をまとめる器である。

### 3.2 粒度

最初から細かく分割しすぎない。

実際に進めながら、ひとつの経験として扱うのが適切か、分割した方がよいかを判断する。必要になった場合は後から分割・統合する。

EXPに「進行中」「完了」などのステータス項目は設けない。経験には明確な終了点がない場合もあるためである。

### 3.3 EXP-ID

EXP-IDは10桁の連番とする。

例：

- `EXP-0000000010`
- `EXP-0000000020`
- `EXP-0000000030`

通常は10刻みで採番する。

新規の基本EXPも末尾0の番号とする。

## 4. REC（経験レコード）

### 4.1 定義

RECは、EXPの中で発生した意味のある出来事・判断・試行・結果を記録する単位とする。

1つのEXPに複数のRECを持つことができる。

原則として、1つのRECは1つのEXPに属する。

### 4.2 REC-ID

REC-IDは10桁の連番とする。

RECの採番はEXPごとに独立する。

例：

```text
EXP-0000000010
  REC-0000000010
  REC-0000000020
  REC-0000000030

EXP-0000000020
  REC-0000000010
  REC-0000000020
```

### 4.3 RECファイル名

REC-IDだけではEXPをまたいで重複するため、ファイル名にはEXP-IDとREC-IDを両方含める。

```text
REC_EXP-0000000010_REC-0000000010.md
```

### 4.4 RECの項目

```markdown
# REC-0000000010

## EXP-ID
EXP-0000000010

## 日時
2026-09-05 12:00

## タイトル
Debianインストールを開始

## 内容
VAIO PへのDebianインストールを開始した。

## 結果
インストールを開始できた。

## 気づき
今回の作業では、〜〜〜が重要だと分かった。
```

項目は以下の7項目とする。

- REC-ID
- EXP-ID
- 日時
- タイトル
- 内容
- 結果
- 気づき

「気づき」には、技術的な学びだけでなく、たかの感想・気持ちも必要に応じて含める。感情専用の別項目は設けない。

## 5. ID採番ルール

- IDは実際にEXPまたはRECを新規作成するときにだけ発行する。
- 事前予約はしない。
- 一度使用したIDは再利用しない。
- IDそのものに日付やテーマなどの意味を持たせない。
- 通常は10刻みで進める。
- 番号の飛び、途中番号、10刻みから外れる採番、EXP分割・統合に伴う番号変更などの特殊ケースは、たかとバドで協議して決定する。

### 5.1 ID発行・管理の役割分担

AIはEXP/RECの作成やID発行を独自に確定しない。AIが利用可能な場合は、現場情報の報告、実装、試行、問題解決などを補助する。

たかは経験の事実関係を確認し、必要に応じてバドとEXP/RECの扱いを協議する。

**バドが、協議結果に基づいてEXP/RECのIDを発行・管理し、ID管理台帳を更新する。**

AIの役割は最初から固定しすぎず、実際の利用を通して得意分野や適切な役割を確認する。AIが利用できない場合でも運用が止まらないよう、たかが直接バドへ直チャットや経験内容を渡し、バドが必要に応じて聞き取りを行って整理する。

## 6. ID管理台帳

保存先：

```text
指針等/ID管理台帳.md
```

ID管理台帳は、単なる採番管理だけではなく、EXPの一覧・検索用インデックスも兼ねる。

EXPごとに次の情報を1行で管理する。

```markdown
| EXP-ID | 経験内容 | 最終REC-ID |
|---|---|---|
| EXP-0000000010 | VAIO PへのDebianインストール | REC-0000000030 |
```

EXPが増えるごとに1行追加する。

独立した `EXP_NEXT` や `REC_NEXT` の項目は設けない。

## 7. 直チャットの正式保存運用

直チャットは、経験DBの一次記録として扱う。

直チャットを登録すると決めた場合は、**要約・編集・再構成をせず、受け取った原文そのものを保存する。** AIが内容を整理した要約文を、直チャットの代わりに保存してはならない。

### 7.1 記録媒体の基本方針

作業上の事実は、可能な限り**テキストを基本記録**とする。

コマンド、入力内容、出力結果、エラーメッセージ、設定値、操作結果などは、クリップボード経由のコピー＆ペーストで直チャットへ残すことを基本とする。

画像は原則禁止ではなく、**テキストでは十分に記録できない情報を伝える必要がある場合の補助記録**として使用する。たとえば、実機の外観、物理的な状態、配線、故障状態、画面に現れた視覚的な状態などが該当する。

直チャットに貼付された画像が、後からGitHub上の直チャット原文として取得・再利用できるとは限らない。そのため、将来の再利用を期待する作業情報は、画像だけに依存せずテキストで記録する。

### 7.2 正式な処理順序

1. たかから直チャットを受け取る。
2. まず原文のまま `直チャット/` に保存する。
3. 保存した直チャットを材料として既存EXPを検索する。
4. 必要に応じて、新しいEXPを作るか、既存EXPにRECを追加する。
5. 経験DBへの追加が不要なら、直チャットの保存だけで完了とする。

ファイル名は原則として次の形式とする。

```text
YYYY-MM-DD_HHMM_直チャット_[発信者]_[日本語トピック].md
```

1つの直チャットから複数のEXP/RECが生まれることもあるが、通常は無理に細分化しない。

直チャットとEXP/RECをIDで正式に相互リンクする仕組みは設けない。ファイル名や内容から追跡できるためである。必要な場合のみREC本文中で出典となるチャットに触れる。

## 8. EXPの分割・統合

EXPの分割・統合については、現時点では詳細な固定ルールを設けない。

実際の運用で事例を蓄積し、必要になった時点でルール化する。

EXPを分割した場合でも、RECの所属変更が必要になれば、そのREC-ID自体は変更しない。

## 9. ブログ化

EXPにはブログ化項目を持たせる。

```text
未
済
```

現時点では、この2値で管理する。

ブログ記事のURLや記事タイトルをEXPに必須項目として持たせる仕様にはしない。必要性が明らかになった時点で追加を検討する。

ブログ作成時は、直チャット・REC・EXPに記録された事実を一次資料として利用する。説明図、概念図、画面イメージ等については、記録された事実に基づいてAIが生成できる。ただし、AI生成画像を実際に撮影された写真であるかのようには扱わず、実写写真とは区別する。

## 10. 運用上の基本方針

- 生の記録を残す。
- 成功だけでなく失敗・試行錯誤・判断過程も残す。
- たかの気持ちや実感も「気づき」の一部として残す。
- 記録を細かくしすぎず、後から使える粒度を優先する。
- **作業上の事実は可能な限りテキストで直チャットに残し、画像は必要な場合の補助として扱う。**
- **コマンド・入出力・エラー・設定値等は、クリップボード経由のコピー＆ペーストを基本とする。**
- **直チャットを受け取った場合、まず原文のまま保存し、その後にEXP/REC化を検討する。**
- **現時点の基本フローは、たか → バドと協議 → バドが実行、とする。**
- AIが利用可能な場合は、それぞれの得意分野に応じて現場情報の捕捉、実装、試行、問題解決などを補助する。ただし、AIが利用できないことを前提にしても経験DBの運用が止まらない構造とする。
- 経験ログの作成・更新、EXP/RECのID管理、ID管理台帳の更新、GitHubへの書き込みはバドが担当する。
- ブログ用の説明図・概念図・画面イメージ等は、記録された事実を基にAI生成できる。AI生成物は実写写真と区別して扱う。
- GitHubを共有・蓄積の中心とする。
- ルールを最初から固定しすぎず、実運用から必要なルールを追加する。
- AIの役割や運用ルールは、実際の利用から得られた経験に基づいて必要に応じて更新する。
