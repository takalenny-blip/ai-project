# 経験DB仕様・現在地

最終更新: 2026-09-05

## 決定済み

### EXP
- EXP = 大きすぎず小さすぎない、ひとまとまりの経験そのもの。
- 進行に応じて分割・統合する。
- 終わりのない経験でもよい。
- 項目: EXP-ID / タイトル / 開始日 / 概要 / ブログ化
- 状態管理は持たない。

### REC
- REC = EXPの中で発生した、意味のある出来事・判断・試行・結果。
- REC = 経験ログの1レコード。
- 1 EXPに複数REC。
- 原則、1 RECは1 EXPに所属。
- EXP分割等でRECを移してもREC-IDは変更しない。
- 項目: REC-ID / EXP-ID / 日時 / タイトル / 内容 / 結果 / 気づき

### ID番号
- EXP-ID、REC-IDとも10桁。
- 基本は10、20、30……と増やす。
- 新しい基準となるEXP/RECは末尾0。
- REC番号はEXPごとに独立する。
- 例:
  - EXP-0000000010 → REC-0000000010, REC-0000000020, REC-0000000030
  - EXP-0000000020 → REC-0000000010, REC-0000000020
- 番号は実際に作成するときに発行する。
- 先行予約しない。
- 一度使用した番号は再利用しない。
- 通常ルール外の番号使用、既存番号間への追加、一桁目の使用、EXP分割・統合など特殊ケースは、たか＋バドで協議する。

### ID管理台帳
- `指針等/ID管理台帳.md` に置く。
- ID管理と経験索引を兼ねる。
- EXP-ID / 経験内容 / そのEXPで現在どこまでRECを発行したか、を1行で管理する。
- 経験が増えたら1行追加する。
- 台帳上部にEXP_NEXT / REC_NEXTを別管理する方式は採用しない。

### 番号発行の役割
- JUNが番号を必要とした場合、JUNからたかへ依頼する。
- たかがGitHubを操作して台帳から番号を取得し、カウントアップする。
- バドはこの通常の番号発行フローには入らない。

### 直チャットから経験ログへの判断
直チャットを確認して、基本的に次の3択。
1. 新しいEXPを作る
2. 既存EXPへRECを追加する
3. 経験ログには落とさない

- 1つの直チャットから複数のEXP/RECが発生してもよい。
- 基本は既存EXPがあればそこへ、なければ新EXP。
- 直チャットとEXP/RECはIDで明示的には紐づけない。
- 直チャットは生データとして保存する。

### ファイル名
RECはEXP-IDとREC-IDをファイル名に含める。

`REC_EXP-0000000010_REC-0000000010.md`
