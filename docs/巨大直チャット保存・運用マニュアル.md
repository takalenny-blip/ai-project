# 巨大直チャット保存・運用マニュアル

更新日：2026-10-06

## 1. 目的

DropboxからGitHubへ直チャットを保存するとき、通常サイズと巨大ファイルで入口が異なる場合でも、既に成功した正規経路を再発明せず、同じ手順で再現できるようにする。

このマニュアルは、巨大直チャットの受け渡し・キュー化・正規保存・最終確認を対象とする。

## 2. 正本と役割

- 直チャットの保存先・一次記録の正本はGitHubの `直チャット/`。
- Dropboxは受け渡し用の一時保管場所であり、GitHub保存後の正本ではない。
- 巨大ファイルの入口は `.github/workflows/direct-chat-large-intake.yml`。
- 正規保存処理は `.github/workflows/save-request-intake.yml` と `scripts/save_and_currentize.py` が担当する。
- 現在状態の正本は `docs/現在状態.json`。BUD.mdと現在の引き継ぎは生成ビューであり、手編集しない。

## 3. 巨大ファイルの入口

巨大直チャットは、通常の保存経路へ直接押し込まず、まず `direct-chat-large-intake.yml` の `workflow_dispatch` でGitHub Actions runnerへ取得する。

入力するもの：

1. `source_url`：一度だけ使用する原本取得URL。URLや取得内容をログへ出さない。
2. `filename`：保存する `.md` ファイル名。
3. `expected_size`：分かっている場合はDropbox原本のバイト数。0ならサイズ検査を省略。

workflowはrunner上で取得し、ファイルが空でないこと、先頭にDropboxプレビューHTMLが含まれていないこと、expected_sizeを指定した場合のサイズ一致を自動確認した後、`.github/save-queue/` にキューとして置き、キューPRを作る。

## 4. Dropbox原本の確認

巨大ファイルでは、共有URLから取得したものがDropboxのプレビューHTMLになる事故に注意する。

必ず次を確認する。

- 取得したファイルの先頭が実際のMarkdown直チャットであること。
- 期待するタイトル・日時・会話本文が存在すること。
- Dropboxプレビュー用HTML（`<!DOCTYPE html>` 等）ではないこと。
- 可能ならDropbox原本のバイト数と取得ファイルのバイト数を照合する。

なお、プレビューHTMLの検出は人間の目視だけに依存せず、`direct-chat-large-intake.yml` が取得直後に先頭部分を自動検査し、HTMLと判定した場合はキューPRを作らず失敗させる。

**DropboxのプレビューHTMLをGitHubの保存キューへ入れた場合、そのファイルを正規保存してはならない。**

## 5. キューから正規保存まで

`direct-chat-large-intake.yml` が作成した `chat-save-request/direct-large-<run_id>` のキューPRを確認する。

キューPRが正しい実チャット本文を含むことを確認したら、通常の `save-request-intake.yml` がキューPRを入口として正規保存処理を行う。

流れは次のとおり。

`Dropbox原本`
→ `direct-chat-large-intake.yml`
→ `.github/save-queue/<filename>`
→ キューPR
→ `save-request-intake.yml`
→ `scripts/save_and_currentize.py`
→ `直チャット/<timestamp>.md` ＋ `docs/現在状態.json` ＋生成ビュー
→ 保存PR
→ CI・承認・merge
→ canonical readback

## 6. Run workflowを使う条件

`direct-chat-large-intake.yml` は `workflow_dispatch` のため、巨大ファイルの入口ではRun workflowを使う。

ただし、既に同じ巨大直チャットの保存要求が投入済みなら、同じ対象を理由なく再投入しない。

`direct-chat-large-intake.yml` は、同一filenameの未完了な `chat-save-request/direct-large-*` キューPRを自動確認し、該当する場合は新しいキューPRを作らずに失敗する。

通常サイズの直チャットは、既存の通常保存経路を優先する。巨大かどうかの判断は、GitHub Actionsへ安全に受け渡す必要があるファイルサイズ・既存経路の制約を踏まえて行う。

## 7. 完了確認

「キューPRができた」「workflowが成功した」だけでは保存完了としない。

最終的にmainから次を読み戻す。

1. 保存された `直チャット/<timestamp>.md` が存在する。
2. `docs/現在状態.json` の `direct_chat.latest_path` が今回の保存先を指す。
3. `direct_chat.latest_content_sha` と保存ファイルのblob SHAが一致する。
4. 必要な生成ビューがmainに反映されている。
5. 保存PRがmerge済みである。

## 8. 失敗・異常時

- DropboxプレビューHTMLを取得した場合は、そのキューを正規保存しない。
- サイズ不一致なら、原因を確認してから再試行する。
- 同じ保存要求を未完了だからという理由だけで再投入しない。workflow側でも同一filenameの未完了巨大直チャットキューPRを検出して再投入を止める。
- 既存の成功経路を捨てて別方式を試す前に、現在のworkflowと過去の成功例を確認する。
- 保存処理の失敗と主作業の状態を混同しない。

## 9. 次回の実務手順

1. Dropbox原本を特定する。
2. 原本のサイズと実体を確認する。
3. 巨大ファイルなら `direct-chat-large-intake.yml` のRun workflowを使う。
4. 既存の同一filenameの未完了キューPRがないことを確認する。workflow側でも自動確認される。
5. 取得結果が実チャット本文であることを確認する。workflow側でDropboxプレビューHTMLの先頭検出も行う。
6. キューPRを確認する。
7. `save-request-intake.yml` による正規保存を待つ。
8. 保存PRのCI・承認・mergeを確認する。
9. mainの `docs/現在状態.json` と保存ファイルを読み戻す。
10. SHA一致まで確認して保存完了とする。

## 10. 完了条件

- 巨大直チャットの入口と通常保存経路の役割を区別できる。
- DropboxプレビューHTMLを実チャットと誤認しない。workflowの自動検査でもHTML取得を拒否する。
- 同じ保存要求を重複投入しない。workflowの自動検査でも同一filenameの未完了キューPRを拒否する。
- 正規保存PRのmergeだけでなく、mainの保存ファイルと現在状態を読み戻して確認する。
- 次回担当AIがこのマニュアルを読めば、巨大直チャット保存を既存の成功経路に沿って再現できる。
