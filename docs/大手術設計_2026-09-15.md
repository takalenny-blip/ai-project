# 大手術設計 2026-09-15

## 目的

ai-projectの「現在状態が複数箇所に分散し、手動同期とAIの自己規律に依存する」構造を、一次記録を壊さず、機械的に検証できる構造へ改修する。

## 現状棚卸し

確認した問題は次の7点。

1. BUD・現在の引き継ぎ・直チャットに現在状態が重複し、手動同期が必要。
2. 自然言語ルールに依存する部分が多く、既知の失敗を機械的に止められない。
3. 直チャット連番が手動管理で、欠番・衝突・日跨ぎ管理が発生する。
4. `scripts/search_direct_chat.py` がGitHub Contents APIで多数ファイルを個別取得し、未認証レート制限に到達した。
5. 公開リポジトリの秘密情報保護が自己申告中心。
6. EXP/RECと一次記録の追跡性・検索性が弱い。
7. GitHub Actions / Issuesによる継続的な機械検証が不足。

## 設計原則

- 一次記録は不変資産として扱う。
- 現在状態は構造化データを基礎にする。
- **`docs/現在状態.json`を唯一の現在状態正本とし、BUD.mdと現在の引き継ぎは生成ビューにする。**
- 自動生成は「バドが毎回手で書き写す」運用にしない。生成スクリプトの実装主体・実行場所・トリガー・失敗時の扱いを先に定義する。
- 生成フローは `現在状態.json → 生成スクリプト → BUD/引き継ぎ → CI/Actions` の一方向を基本とする。
- 自動生成が完成するまでの移行期間は明示的な暫定状態として扱い、二重管理を恒久化しない。
- BUDは現在状態を読むためのダッシュボードとして残す。
- 現在の引き継ぎは現在状態のビューとして扱う。
- 旧ファイル名は移行のために改名しない。
- 機械判定できる規則はスクリプト/CIへ移す。
- 判断が必要な内容はAI/たかの判断領域として残す。
- VAIO Pでは長文手入力を前提にしない。
- GitHub Contents APIの大量個別取得を通常検索経路にしない。

## 一括改修の定義

**「一括改修」は設計を一括で行うことを意味し、実装を9項目まとめて最後に検証することを意味しない。**

実装は必ず、**変更 → GitHubから読み戻し → 機械判定可能な合格基準を確認 → 次へ**の小さな検証単位で進める。

## 優先順位

1. `docs/現在状態.json`を唯一の現在状態正本にする設計を確定し、生成スクリプトの実装主体・実行場所・トリガー・失敗時の扱いを定義する。
2. 最新直チャットへの単一パス参照を現在状態に持たせ、命名規則から最新判定を切り離す。
3. CIによる機械的ガードを先行して安全網にする。
4. タイムスタンプ保存・命名ルール変更を行う。
5. API大量取得の改修、秘密情報検査、EXP/REC追跡性、Actions/Issues整理を進める。

## 移行期間の扱い

- 大手術の実装・移行が完了するまで、DiMORA本来工程は再開しない。
- 移行期間中に保存が必要な場合は現行の手動同期ルールで必要処理を完了するが、それを新しい恒久運用とはみなさない。
- 自動生成へ移行した後は、BUDと引き継ぎを独立した現在状態として手編集しない。

## 各項目の合格基準

### 1. 唯一の正本・自動生成

- `docs/現在状態.json`だけを現在状態の入力として生成スクリプトがBUD/引き継ぎを再生成できる。
- 生成前後の期待差分を機械的に比較できる。
- 生成失敗時にBUD/引き継ぎを中途半端な状態で更新しない。

### 2. 最新直チャット参照

- `docs/現在状態.json`の最新パスが実在し、実体と一致する。
- 旧連番／新タイムスタンプのどちらでも、パスだけで最新記録を特定できる。

### 3. CIガード

- 命名、重複、リンク、現在状態整合性、秘密情報等の指定検査が自動実行でき、違反時に失敗する。

### 4. タイムスタンプ方式

- 新規ファイルが定義済みのタイムスタンプ規則に適合し、旧連番ファイルを変更しない。

### 5. その他の改修

- API大量取得を通常経路から外した検索手段が実行可能。
- 秘密情報検査が保存前とCIで実行可能。
- EXP/RECの一次記録パス追跡が改善される。
- Actions/Issuesの役割が正本を増やさない形で整理される。

## 採用する改善

- 現在状態の構造化と一次記録の分離。
- `docs/現在状態.json`を唯一の現在状態正本とする。
- BUD/引き継ぎの自動生成ビュー化。
- 最新直チャットの単一パス参照。
- 新旧直チャット命名方式の共存。
- ローカルcloneの `git grep` / `rg` 優先。
- 保存前とCIの秘密情報検査。
- 命名、重複、リンク、状態整合性の機械検査。
- 機械判定可能なルールのスクリプト化。
- EXP/RECの一次記録追跡性改善。
- Actions / Issuesの必要最小限の活用。
