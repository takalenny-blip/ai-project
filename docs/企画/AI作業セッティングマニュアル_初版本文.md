## 第1章　AIで試したいことを、続けられる形で始める

### この章の目的

AIを使って何かを実現したいと思ったとき、最初から大きな仕組みを作る必要はありません。まずは、やってみたいことを一つ選び、小さく試し、その結果をあとから読み返せる形で残すところから始めます。

このマニュアルでは、生成AIの利用から作業環境の準備まで、無料で始められる方法を基本にします。有料プランや有料サービスが必要な手順を、当然の前提にはしません。

この章を終えると、次のことができる状態を目指します。

- AIで試してみたいことを一つ決められる。
- 作業に使う道具と、それぞれの役割を区別できる。
- 最初の小さな試行と、結果の記録方法を決められる。

### 1.1　最初に「実現したいこと」を一つ選ぶ

「AIで何かできないかな？」という段階でも構いません。最初から完成形や専門的な計画を決めず、少し試せば結果を確かめられる題材を選びます。

たとえば、次のような始め方があります。

- 自分の考えをAIと相談し、整理してみる。
- 日々の作業の一部を、AIでやりやすくできるか試す。
- AIとの対話や試行錯誤を記録し、あとで読み返せるようにする。
- 自分が試した方法を、他の人にも伝えられる形にまとめる。

ここで選ぶのは、長期計画ではなく**最初に試す一歩**です。うまくいくかどうかが分からなくても、結果を確認できる大きさにします。

#### 準備シート

次の項目を埋めてください。決まっていない項目は、空欄のまま、または「未定」として構いません。

| 項目 | 記入内容 |
|---|---|
| 試したいこと | 何をやってみたいか |
| なぜ試したいか | 興味、期待、実現したいこと |
| 最初の一歩 | 10〜30分程度で試せそうな作業 |
| 結果の見分け方 | 何が分かれば試した意味があるか |
| 残しておきたい記録 | AIの回答、実際の結果、気づき、失敗など |
| 今回はやらないこと | 最初の試行では扱わない範囲 |

**記入例（例示であり、効果を保証するものではありません）**

| 項目 | 記入例 |
|---|---|
| 試したいこと | AIとの相談内容を、あとで読み返せる記録にする |
| なぜ試したいか | 以前に試したことや、うまくいった方法を忘れたくない |
| 最初の一歩 | 短い相談を一回行い、要点をテキストファイルに残す |
| 結果の見分け方 | 後から読んで、相談内容と結論が分かる |
| 残しておきたい記録 | 相談の目的、試したこと、結果、次に試すこと |
| 今回はやらないこと | 自動保存や複雑な自動化の構築 |

### 1.2　道具の役割を分ける

このマニュアルでは、道具を一つの万能な仕組みとして扱いません。それぞれに役割があります。

| 道具 | このマニュアルでの役割 | 注意点 |
|---|---|---|
| 生成AI | アイデアを広げる、相談する、文章や手順を考える | 回答が正しいとは限らない。重要な事実は別途確認する |
| チャットの記録 | 何を相談し、どんな回答を得たか残す | 会話だけでは、実際に操作した結果まで証明できない |
| Markdownファイル | 経験や手順を、あとで読めるテキストとして残す | どのファイルが正式な原本か分かるようにする |
| GitHub | ファイルの変更履歴や、作業の区切りを管理する | 公開リポジトリに秘密情報や個人情報を置かない |
| Dropbox | ファイルを保管・同期するために使う | Dropboxにあるコピーが、必ずしも正式な原本とは限らない |

初めからすべての機能を使う必要はありません。まずは短い試行とテキストの記録を行い、必要に応じて管理方法を整えていきます。後続の章で各道具の準備と連携を扱います。

### 1.3　AIを選ぶときに確認すること

生成AIは、名前が違うだけで同じ使い方ができるとは限りません。利用できる機能、無料プランの上限、ファイルやリポジトリへのアクセス範囲などは、サービスや時期によって異なります。

利用を始める前に、少なくとも次を確認します。

1. 無料プランで、今回試したい作業ができるか。
2. 利用回数やメッセージ数などの制限があるか。
3. ファイル添付、長い会話、外部サービス連携などが必要か。
4. 入力する情報を、そのサービスに送ってよいか。
5. 制限に達したとき、作業を中断・記録して後で再開できるか。

無料枠の制限に達しても、すぐに有料契約する必要はありません。作業を記録して待つ、入力を小さく分ける、別の無料手段で代替できるか検討する、といった選択肢があります。ただし、別サービスへ移る場合も、機能や情報の扱いが同じとは限らないため確認してください。

### 1.4　最初の相談をしてみる

準備シートに書いた「最初の一歩」を、AIに相談してみます。目的や制約が曖昧なまま大きな作業を依頼するのではなく、まず小さな作業に区切って相談します。

次のテンプレートをコピーし、角括弧の部分を書き換えてください。

```text
目的：
[今回、実現したいこと]

今回やること：
[最初の一歩として試す作業]

今回はやらないこと：
[対象外にする作業]

使えるもの・制約：
[無料プランであること、使えるファイル、時間など]

完了の判断：
[何が分かれば今回の試行を終えられるか]

回答の希望：
- 手順を小さく分けて説明してください。
- 事実、提案、推測、未確認事項を区別してください。
- 不明な点を事実のように断定せず、必要なら質問してください。
- 実行や外部への変更が必要な場合は、操作前に説明してください。
```

このようにAIへ渡す依頼文を、ここでは「プロンプト」と呼びます。最初から完璧なプロンプトを作る必要はありません。回答を見て、足りなかった条件や誤解された点を相談し、少しずつ改善します。

AIの回答をそのまま実行するのではなく、まず内容を読み、今回の目的と合っているか確認してください。アカウント設定、ファイルの削除、公開、権限変更など、影響のある操作は、内容を理解し、必要な承認を得てから行います。

### 1.5　試した結果を短く残す

試行が終わったら、成功・失敗にかかわらず、次の項目をテキストで残します。

```text
# 試行記録

日付：
今回の目的：
実際に試したこと：
得られた結果：
自分で確認できたこと：
AIの回答だけで、まだ確認できていないこと：
うまくいかなかった点・制約：
次に試したいこと：
```

「AIがこう答えた」と「自分で実際に確認できた」は別の情報です。両方を分けて書くことで、後から読み返したときに、何が分かっていて何が未確認なのかを判断しやすくなります。

記録は、最初から整った報告書にする必要はありません。短い箇条書きで十分です。大切なのは、後から自分が読み返して、試したことと結果を思い出せることです。

### この章の確認

次の項目を確認してください。

- [ ] 試したいことを一つ選んだ。
- [ ] 最初の一歩と、結果の見分け方を書いた。
- [ ] 道具ごとの役割を区別できる。
- [ ] AIへの相談で、目的・範囲・制約・完了の判断を伝えた。
- [ ] AIの回答と、自分で確認した結果を区別して記録した。
- [ ] 未確認事項や次に試すことを残した。

まだ全部できていなくても、失敗ではありません。分からなかった項目を記録し、それ自体を次の作業にしてください。

**次章では、AIを継続して使うための利用環境と基本ルールを整えます。**


## 第2章　AIの利用環境と基本ルールを整える

### この章の目的

第1章で決めた「試したいこと」を、AIとの対話で少しずつ進められるようにします。ここでは、特定のAIサービスの画面設定を網羅するのではなく、どのAIを使う場合にも役立つ準備と、作業を安全に進める基本ルールを整えます。

無料プランの機能・利用上限・外部サービス連携は、サービスや時期によって変わります。実際に使う前に、現在の画面と公式の案内で確認してください。この章では、確認していない上限値や機能を固定の事実として扱いません。

### 2.1　AIに任せる役割を決める

AIに「全部任せる」と考えると、何を頼んだのか、何を自分で確認すべきかが曖昧になります。最初は、今回の作業でAIに手伝ってほしい役割を一つか二つ選びます。

- **発想を広げる**：やってみたいことの候補や別の方法を出してもらう。
- **整理する**：自分の考え、メモ、試行結果を読みやすくまとめてもらう。
- **手順を考える**：作業を小さな段階に分け、各段階の確認方法を提案してもらう。
- **文章やコードを作る**：下書きや例を作ってもらい、自分で内容と動作を確認する。
- **レビューする**：抜け、矛盾、危険、未確認事項を指摘してもらう。

役割は途中で変更して構いません。ただし、作業の目的まで変わった場合は、記録に変更理由を書きます。AIが提案しただけの内容と、実際に採用した内容を混同しないでください。

### 2.2　作業を始める前に、条件を伝える

AIへの依頼文を「プロンプト」と呼びます。長く書くこと自体が目的ではありません。AIが判断するために必要な条件を、分かる範囲で伝えます。

最低限、次の項目を用意します。

1. **目的**：何を実現したいか。
2. **今回の範囲**：いま頼む作業は何か。
3. **対象外**：今回は何をしないか。
4. **制約**：無料プラン、使える道具、時間、扱ってはいけない情報など。
5. **完了の判断**：何ができたら、この作業を終えられるか。
6. **確認方法**：結果をどのように確かめるか。

次のテンプレートを使えます。

```text
目的：
[実現したいこと]

今回の作業：
[いま進めたい小さな作業]

今回の対象外：
[いまは扱わないこと]

制約：
[無料プラン、使用できる道具、時間、情報の扱いなど]

完了の判断：
[どの状態になれば今回の作業を終えるか]

確認方法：
[結果をどう確かめるか]

回答のルール：
- 確認できた事実、提案、推測、未確認事項を区別してください。
- 不明な点は断定せず、作業に影響する場合は質問してください。
- 実行前に、外部への変更や取り消しにくい操作の内容を説明してください。
- 私の承認が必要な操作は、承認を得る前に実行しないでください。
- 最後に、実施したこと、確認できたこと、未完了事項、次の一手を分けて示してください。
```

最初の回答が目的に合わなかった場合は、プロンプトを最初から作り直す必要はありません。「どこが違ったか」「どの条件を追加すべきか」をAIに相談し、必要な部分だけを直します。こうして、試した内容と結果に合わせてプロンプトを育てます。

### 2.3　AIの回答を確認する

AIの回答は、読みやすく自信のある文章でも、間違いや古い情報を含む場合があります。特に、アカウント設定、料金、利用上限、権限、公開手順、コマンド、外部サービスの仕様は、回答だけを根拠に確定しないでください。

回答を受け取ったら、次の順で確認します。

1. 自分が依頼した目的と範囲に合っているか。
2. 前提としている機能・画面・ファイルが、実際の環境に存在するか。
3. 事実として書かれた内容に、確認可能な根拠があるか。
4. 操作した場合の影響や、失敗した場合の戻し方が分かるか。
5. まだ確認できていない点が、明示されているか。

確認できないことは「未確認」と記録します。AIが「完了した」と説明したことと、実際に操作が成功したことも別です。必要に応じて、画面、ファイル、実行結果などを自分で確認します。

### 2.4　外部に影響する操作は分けて扱う

AIとの相談、実行する操作、結果の確認を一つのものとして扱わないでください。特に、次の操作は、内容と影響を理解してから進めます。

- ファイルやフォルダーの削除・上書き
- アカウント、権限、認証情報の変更
- リポジトリやWebサイトへの公開
- 外部サービスへの送信や連携
- 有料契約、購入、課金につながる操作
- 元に戻すことが難しい操作

作業を依頼する前に、AIに「実行せず、まず手順と影響だけ説明してください」と伝える方法もあります。外部に影響する操作を実行する場合は、操作対象、変更内容、期待する結果、失敗時の対処を確認し、必要な承認を得てから行います。

また、パスワード、アクセストークン、秘密鍵、セッション情報などの認証情報を、通常の相談文や記録ファイルに貼り付けないでください。公開リポジトリに置いてはいけない情報や、サービスに送信してよいか分からない情報は、入力を止めて扱いを確認します。

### 2.5　無料プランの制限に備える

無料で続けるためには、制限がないことを期待するのではなく、制限に達しても作業を失わない準備をしておきます。

1. 利用中のサービスで、現在の利用上限やリセット条件を確認する。
2. 長い作業は、目的・決定事項・未完了事項を途中で記録する。
3. 添付ファイルや長文が必要な場合は、本当に必要な範囲に絞る。
4. 制限に達したら、無理に続けず、記録して再開できる状態にする。
5. 別のAIに切り替える場合は、機能や回答傾向が同じだと決めつけず、必要な前提だけを渡して結果を確認する。

無料枠の制限を避けるためだけに、記録や確認を省略しないでください。利用可能な機能や制限は変わるため、具体的な数値や対応機能を本文や記録に書く場合は、確認日と確認元も残します。

### 2.6　AIごとの使い方を固定しすぎない

AIサービスごとに、利用できる機能や制限、得意・不得意があります。複数のサービスを使う場合は、同じ依頼をそのまま渡すのではなく、目的に合う役割を決めて使います。

筆者自身の使い分け例としては、ChatGPTの無料利用では画像の貼り付けをできるだけ避け、ドラッグ選択によるコピー＆ペーストなど、テキスト中心でやり取りする方法があります。Claudeは無料利用の上限に達しやすいと感じているため、行き詰まったときに使う予備の手段として温存しています。Geminiは、Claudeが使えない場合などに別の視点を得るための確認役として使うことがあります。

これは筆者の利用経験に基づく例であり、すべての利用者・時期に当てはまる性能比較ではありません。実際に利用するときは、自分の無料枠、作業内容、回答の質を確認し、自分に合う役割分担を記録してください。どのAIも、最終的な正しさを保証するものとして扱わないことが大切です。

### 2.7　作業を再開できる記録を残す

作業を中断する前、または一区切りついたときは、次の項目を残します。会話の全文を毎回まとめ直す必要はありません。次に何をすればよいかが分かる情報を優先します。

```text
# AI作業の区切り記録

目的：
今回の作業：
今回決めたこと：
採用しなかった提案と理由：
実際に確認できた結果：
未確認のこと：
未完了のこと：
次に行う一手：
再開時に最初に確認するファイル・画面：
```

記録をAIに作成してもらう場合も、内容を確認してから保存します。AIが以前の会話を覚えていることを前提にせず、必要な決定事項と現在の状態を記録から再現できるようにします。後続の章では、記録をファイルとして管理し、GitHubなどで変更履歴を扱う方法を説明します。

### この章の確認

- [ ] 今回AIに手伝ってもらう役割を決めた。
- [ ] 目的、作業範囲、対象外、制約、完了の判断を伝えた。
- [ ] 回答の事実・提案・推測・未確認事項を区別した。
- [ ] 外部に影響する操作と、通常の相談を分けた。
- [ ] 無料プランの制限に達しても再開できる記録を用意した。
- [ ] 作業を中断するとき、未完了事項と次の一手を残せる。

次章では、GitHubを使ってMarkdownの記録と変更履歴を管理するための基本を整えます。


## 第3章　GitHubで記録と変更履歴を管理する

### この章の目的

この章では、AIとの試行錯誤で生まれたメモや手順を、後から見つけて再利用できる形で管理するために、GitHubの基本を整えます。ここでは、GitHubを初めて使う人が、Markdownファイルを保存し、変更内容を確認しながら更新するための入口を扱います。

GitHubの画面や無料プランの仕様は変わることがあります。ボタン名や利用可能な機能が本文と違う場合は、現在の画面と公式案内を優先してください。パスワードやトークンなどの認証情報を、リポジトリのファイルに記録してはいけません。

### 3.1　GitHubで管理するものを決める

GitHubは、ファイルを置くだけでなく、変更履歴を確認し、変更案をレビューしてから取り込むためにも使えます。AIとの作業では、次のような記録が候補になります。

- 自分が試したいことと、その目的
- AIに依頼したプロンプトや、再利用したい依頼テンプレート
- 試した手順、得られた結果、うまくいかなかった点
- 自分で確認した事実、まだ確認できていないこと
- 次に行う作業と、再開時に確認する場所

会話全文をすべて公開リポジトリへ入れる必要はありません。個人情報、第三者の情報、秘密情報、公開できない内容を含む記録は、公開リポジトリへ置かないでください。まずは公開しても問題のない短いサンプルから始めます。

### 3.2　アカウントとリポジトリを確認する

すでにGitHubアカウントを持っている場合は、新しく作り直す必要はありません。まず、ログインできることと、今回使うリポジトリを開けることを確認します。

1. ブラウザーでGitHubを開き、自分のアカウントにログインします。
2. 作業に使うリポジトリを開きます。リポジトリは、関連するファイルと変更履歴をまとめて管理する場所です。
3. リポジトリ名と所有者を確認します。似た名前の別リポジトリで作業しないようにします。
4. リポジトリの公開・非公開の状態を確認します。公開リポジトリに追加した内容は、原則として他者から閲覧できる前提で扱います。
5. 自分に変更権限があるか確認します。閲覧できることと、変更できることは同じではありません。

これから初めてリポジトリを作る場合は、用途を一つに絞った分かりやすい名前を付け、公開範囲を作成時に確認します。学習用の公開サンプルに秘密情報や個人情報を含めないことを、作成前に決めてください。リポジトリの公開・非公開を後から変更する場合も、影響を理解してから実施します。

### 3.3　Markdownファイルを一つ作る

Markdownは、見出しや箇条書き、リンク、コードなどを、基本的にはプレーンテキストで記述する形式です。専用の編集ソフトがなくても作成でき、GitHub上でも内容を確認しやすいため、このマニュアルでは原稿の正本形式として使います。

まず、公開しても問題のない小さなファイルを一つ作ります。例えば、ファイル名を `first-trial.md` とし、次の内容を入れます。

```markdown
# 最初のAI試行

## 目的

AIを使って、短い文章を分かりやすく整理する。

## 試したこと

- AIに文章の整理を依頼した。
- 元の意味が保たれているか確認した。

## 結果

ここに自分で確認した結果を書く。

## 未確認・次の一手

- 未確認の点：
- 次に試すこと：
```

GitHubのWeb画面から作成する場合は、対象リポジトリで新規ファイル作成の操作を選び、ファイル名と本文を入力して変更を保存します。画面の操作名が変わっている場合は、現在のGitHub画面の案内を確認してください。

保存後は、ファイルがリポジトリ内に表示されること、見出しや箇条書きが意図した形で読めること、入力した内容が欠けていないことを確認します。ファイルを作ったつもりでも、保存が完了していない場合があります。

### 3.4　変更履歴を確認する

GitHubでは、ファイルを変更すると、その変更を記録として残せます。この記録の単位をコミットと呼びます。コミットのメッセージには、変更の目的が分かる短い説明を付けます。

例えば、試行結果を追記した場合は「最初のAI試行の結果を追記」のように書きます。「更新」だけでは、後から変更内容を見分けにくくなります。

変更後は、次の点を確認します。

1. 変更したファイルが意図したものか。
2. 差分に、今回変更した内容だけが含まれているか。
3. 削除や置換を意図せず行っていないか。
4. コミットメッセージから、変更の目的が分かるか。
5. 保存後のファイルを開き、内容が期待どおりか。

変更履歴は、間違いを必ず自動で防いでくれる仕組みではありません。変更前後を比べることで、何が変わったかを把握しやすくする仕組みです。大きな変更の前には、対象ファイルと差分を特に慎重に確認します。

### 3.5　ブランチとPull Requestを知る

複数の変更を安全に扱いたい場合は、ブランチとPull Requestを利用できます。

- **ブランチ**：既存の状態を基に、変更を分けて進めるための作業線です。
- **Pull Request（PR）**：ブランチ上の変更案を、別の人や自分自身で確認してから取り込むための提案です。
- **レビュー**：変更内容を読み、目的との整合、誤り、漏れ、危険がないかを確認することです。
- **マージ**：確認された変更を、取り込み先のブランチへ統合することです。

一人で作業していても、PRを使うと、変更案を確定する前に差分を確認できます。PRを作成しただけでは、変更が取り込み先へ反映されたとは限りません。レビュー状態、必要なチェック、マージ済みかどうかを別々に確認してください。

このマニュアルのように、既存の正本を変更する作業では、本文をいきなり本番用のブランチへ直接書き換えるのではなく、変更案をPRとして提示し、内容とチェック結果を確認してから取り込む流れを基本にします。リポジトリごとに保護ルールや承認条件が異なるため、そのリポジトリで設定されている条件に従います。

### 3.6　正本とコピーを混同しない

同じ内容が複数の場所にあると、どれが最新なのか分からなくなることがあります。ファイルを作る前に、そのファイルの正本をどこに置くか決めてください。

このマニュアル制作では、Markdown原稿をGitHubリポジトリで管理し、GitHub Pagesを本番公開先とします。Dropboxなど別の場所にコピーを保管する場合も、コピーだけを更新して正本への反映を忘れないようにします。保存したこと、PRで提案したこと、マージしたこと、公開ページへ反映されたことは、それぞれ異なる状態です。

最初の試行では、次のような表を自分の作業用に用意すると、保存場所を確認しやすくなります。

| 種類 | 保存先 | 扱い |
| --- | --- | --- |
| 原稿・手順の正本 | 決めたGitHubリポジトリ | 変更履歴を管理する |
| 一時メモ | 自分が管理できる作業場所 | 必要な内容を確認して正本へ反映する |
| バックアップ・受け渡し用コピー | 必要に応じて別の保管場所 | 正本と混同せず、更新の要否を確認する |
| 公開ページ | GitHub Pagesなどの公開先 | 原稿の保存とは別に表示を確認する |

この表は役割を理解するための例です。実際の保存先は、自分の作業環境と公開範囲に合わせて決めます。

### 3.7　この章の確認

- [ ] 作業するアカウントとリポジトリを確認した。
- [ ] 公開・非公開の状態と変更権限を確認した。
- [ ] 公開して問題のないMarkdownファイルを一つ作成した。
- [ ] 保存後にファイルの内容を開いて確認した。
- [ ] 変更履歴と差分の意味を理解した。
- [ ] ブランチ、Pull Request、レビュー、マージの役割を区別できる。
- [ ] 正本、コピー、公開ページを別の状態として扱っている。

次章では、ChatGPTのチャットをMarkdownで保存するためのブラウザー拡張機能を、権限やプライバシーを確認しながら選ぶ方法を扱います。


## 第4章　ChatGPTのチャットをMarkdownで保存する準備

### この章の目的

AIとのやり取りを後から読み返し、試したことを記録として残せるように、チャットをMarkdown形式で保存する準備をします。ブラウザー拡張機能はチャット内容を読み取れる権限を求める場合があるため、便利さだけで選ばず、提供元・権限・プライバシー説明を確認してから使います。この章では特定の拡張機能を無条件には推奨しません。

### 4.1　保存したい範囲を決める

拡張機能を探す前に、次を決めます。

- 最後の回答だけか、会話全体か。
- Markdown形式で保存できるか。
- ファイルを自分のPCへ保存できるか。
- 見出し、箇条書き、コードブロックを読みやすい形で残す必要があるか。
- 会話に個人情報、認証情報、公開してはいけない内容が含まれていないか。

必要な機能を先に決めると、不要な権限や有料機能を避けやすくなります。最初から大量の会話を一括保存する必要はありません。

### 4.2　公式ストアで候補を確認する

Chromeでは[Chrome ウェブストア](https://chromewebstore.google.com/)、ほかのブラウザーではその公式アドオンストアを使います。提供元不明のサイトからインストーラーを入手しないでください。

候補ごとに、次を確認します。

1. **提供元と更新状況**：開発者名、公式サイト、最終更新日を確認する。
2. **必要な機能**：Markdown保存が明記されているか、無料で使える範囲はどこまでかを確認する。
3. **プライバシー説明**：チャット内容を端末内で処理するのか、外部サービスへ送信する可能性があるのか、収集・利用する情報は何かを読む。
4. **権限**：ChatGPTのページだけでなく、すべてのWebサイトのデータを読み取る権限など、機能に比べて広い権限を求めていないか確認する。
5. **利用条件**：アカウント作成、利用回数制限、追加課金がないか確認する。

ストアに掲載されていることやレビュー評価だけで、安全性が保証されるわけではありません。プライバシー説明が見つからない、内容が曖昧、必要な機能に対して権限が広すぎると感じる場合は、インストールを見送ってください。

参考：
- [Chrome ウェブストアの権限に関する説明](https://support.google.com/chrome_webstore/answer/186213?hl=ja)
- [Chromeで拡張機能のサイトアクセスを管理する](https://support.google.com/chrome/answer/2664769?hl=ja)

### 4.3　アクセス範囲を必要最小限にする

Chromeでは、拡張機能のメニューからサイトへのアクセス範囲を確認できます。表示名はブラウザーや拡張機能によって異なる場合があります。

- 必要なときだけ動かせる場合は、「クリックしたとき」など狭いアクセス設定を検討する。
- ChatGPTだけで動けばよい場合は、すべてのサイトへのアクセスを許可しない。
- シークレットモードやローカルファイルへのアクセスは、必要性を理解できない限り許可しない。
- 権限の理由を説明できない場合は、許可を急がず、無効化または削除を検討する。

アクセス範囲を絞ると機能しないことがあります。その場合も、すぐに広い権限を許可せず、必要な権限と動作の関係を確認します。

### 4.4　機密情報を含まない会話で試す

最初のテストには、個人情報や仕事上の機密を含まない短いサンプル会話を使います。

1. ChatGPTで、見出し・箇条書き・短いコード例を含むテスト用会話を作る。
2. 拡張機能の説明に従ってMarkdown形式で保存する。
3. 保存先とファイル名を確認する。
4. テキストエディターで開き、見出し・箇条書き・コードが読みやすく残っているか確認する。
5. 想定外の情報や不要なデータが含まれていないか確認する。
6. テスト後、必要に応じてアクセス権限を見直す。

ファイルが保存できても、外部へ情報が送信されないことまで証明されたわけではありません。データの取り扱いは、ストアの開示情報とプライバシーポリシーを別に確認します。

### 4.5　拡張機能を使わない方法も残す

権限やデータの取り扱いに納得できない場合は、無理にインストールする必要はありません。チャットから必要な範囲を選択してコピーし、テキストエディターへ貼り付けてMarkdownとして保存できます。見出しやコードの書式は、保存後に手作業で整えます。

拡張機能を使うこと自体が目的ではありません。後から読み返せる記録を、無理なく安全に残せることが目的です。

### 4.6　この章の確認

- [ ] 保存したい範囲とファイル形式を決めた。
- [ ] 公式ストアで提供元・更新状況・機能・無料範囲を確認した。
- [ ] プライバシー説明と要求権限を確認した。
- [ ] アクセス範囲を必要最小限にした。
- [ ] 機密情報を含まない会話で保存テストをした。
- [ ] 保存したMarkdownファイルを開き、内容と書式を確認した。
- [ ] 納得できない場合の代替手段として、選択コピーと手動保存を把握した。

次章では、保存した記録をDropboxなどに整理する前に、正本とコピーの役割、保存先、ファイル名を決めます。


## 第5章　Dropboxで記録を整理する

### この章の目的

AIとの試行錯誤で生まれたファイルを、後から見つけて使い直せるように整理します。ここではDropboxを保管・受け渡し用の場所として扱い、正本とコピーを混同しないための基本を決めます。Dropboxを使わない場合も、同じ考え方を自分の保管場所に適用できます。

### 5.1　保存先の役割を決める

ファイルを保存する前に、それぞれの場所を何のために使うか決めます。保存先を増やすほど安心になるとは限りません。どこが正本か分からなくなり、更新漏れが起きることもあります。

このマニュアル制作での役割分担は、次のとおりです。

| 場所 | 役割 | 注意点 |
| --- | --- | --- |
| GitHubリポジトリ | Markdown原稿・手順の正本と変更履歴 | 正本を変更したら差分と保存結果を確認する |
| Dropbox | 必要な記録の保管、端末間の受け渡し、バックアップ用コピー | コピーを更新しただけで正本も更新されたと思わない |
| PC上の作業フォルダー | 作業中の一時ファイル | 不要な一時ファイルを残し続けない |
| GitHub Pages | 公開されたページの表示先 | 原稿の保存とは別に公開結果を確認する |

これはこの作業での役割例です。自分の構成に合わせて変えてもかまいませんが、正本がどこにあるかは一つに決め、記録しておきます。

### 5.2　Dropboxに保存するものを選ぶ

すべてのAIチャットを無条件に保存する必要はありません。後から再開・再利用する価値があるものを選びます。

- 試した手順と、実際に確認できた結果
- 再利用したいプロンプトや作業テンプレート
- 次に作業を再開するための区切り記録
- 必要な場合の、公開して問題のない会話記録
- 正本とは別に保管しておく必要があるファイル

パスワード、APIトークン、Cookie、セッション情報などの認証情報は保存しないでください。第三者の個人情報や、公開許可のない仕事上の情報も、保存の必要性と適切な保護方法を確認せずに持ち込まないでください。

### 5.3　フォルダーを少なく分かりやすくする

最初から細かい分類を作りすぎず、まずは少数のフォルダーで始めます。例えば、次のような構成です。

```text
AI記録/
├─ 01_作業中/
├─ 02_試行記録/
├─ 03_再利用テンプレート/
└─ 99_一時保管/
```

この構成は例です。分類に迷うファイルは、ひとまず一時保管へ置き、後で必要性を判断します。一時保管を恒久的な置き場にしないよう、定期的に中身を見直します。

フォルダー名は、自分が見て意味を判断できる言葉にします。階層を深くしすぎると保存先を探しにくくなるため、必要が出てから分類を増やします。

### 5.4　ファイル名に日付と内容を入れる

ファイル名だけで内容と時期を大まかに判断できるようにします。例えば、次のような形式です。

```text
YYYY-MM-DD_作業テーマ_記録.md
2026-10-14_文章整理_試行記録.md
2026-10-14_再開用_区切り記録.md
```

日付は実際に作業した日付を使い、日付が分からない場合は推測で付けないでください。同じ名前のファイルを上書きする前に、既存ファイルが必要な記録ではないか確認します。サービスの自動命名がある場合も、保存後にファイル名と中身を確認します。

ファイル名へ個人情報や秘密情報を含めないことも大切です。共有リンクを作る場合、リンク先のファイル名自体が相手に見えることがあります。

### 5.5　保存後に中身と場所を確認する

アップロード操作をしただけでは、目的の場所に正しい内容が保存されたとは限りません。保存後に、次を確認します。

1. 保存先のアカウントとフォルダーが正しい。
2. ファイル名が分かりやすく、既存ファイルを意図せず置き換えていない。
3. ファイルを開けて、内容が欠けていない。
4. Markdownの場合は、見出し・箇条書き・コードなど必要な内容が残っている。
5. 正本とコピーのどちらなのかが分かる。
6. 共有設定が意図した範囲になっている。必要がなければ共有リンクを作らない。

同期アイコンやアップロード表示だけを見て完了と決めつけず、必要なファイルを実際に開いて確認します。大切な記録を複数の場所に置く場合は、どれが正本かを明記しておきます。

### 5.6　コピーを正本へ反映する手順を決める

Dropboxで記録を整理しても、GitHubの正本が自動的に更新されるわけではありません。コピー側で内容を直した場合は、正本へ反映する必要があるかを判断し、必要なら変更案として反映して差分を確認します。

このマニュアル制作の原稿を更新する場合は、GitHub上の変更案を確認し、リポジトリのルールに従ってPR・チェック・マージの状態を確認します。Dropboxへの保存、GitHubへの変更案の提出、マージ、本番ページへの反映は別の段階です。

### 5.7　この章の確認

- [ ] 正本、コピー、作業中ファイル、公開先の役割を区別した。
- [ ] 保存する記録を選び、認証情報や公開できない情報を除外した。
- [ ] 自分が理解できる少数のフォルダーから始めた。
- [ ] 日付と内容が分かるファイル名を付けた。
- [ ] 保存後に保存先とファイルの中身を確認した。
- [ ] 共有設定を確認し、不要な共有を作っていない。
- [ ] コピー側の変更を正本へ反映する方法を決めた。

次章では、AIに何かを試してもらう前に、目的と条件を整理し、再利用できるプロンプトへ育てる方法を扱います。


## 第6章　目的と条件を整理し、プロンプトを育てる

### この章の目的

AIに何かを頼むとき、最初から完璧な指示を書く必要はありません。まず「何を実現したいか」を言葉にし、試した結果を見ながら条件を足していきます。この章では、プロンプトを一度きりの命令文ではなく、試行錯誤を通じて育てるための方法を整理します。

### 6.1　ツールを開く前に、やりたいことを書く

最初に、AIの画面を開く前に、やりたいことを一文で書きます。例えば、次のような形です。

- 長い文章を、意味を変えずに短く整理したい。
- 作業の記録から、次回も使える手順を作りたい。
- 自分の経験を、初めて読む人にも分かる説明にしたい。
- 新しいテーマについて、無料で試せる方法を探したい。

この段階では、解決方法まで決まっていなくてもかまいません。「何かいい感じにして」だけで止めず、どんな結果を得たいのかを少し具体的にします。

### 6.2　最初の依頼に入れる四つの要素

最初のプロンプトには、必要に応じて次の要素を入れます。

1. **目的**：何を実現したいか。
2. **材料**：AIに渡す文章、情報、前提は何か。
3. **条件**：変えてはいけない点、使える道具、長さ、形式など。
4. **確認方法**：どんな結果なら役に立ったと判断できるか。

例えば、文章を整理したい場合は、次のように書けます。

```text
目的：
次の文章を、初めて読む人にも分かりやすく整理したい。

材料：
ここに自分の文章を貼り付ける。

条件：
- 元の意味や事実を変えない。
- 情報が足りない箇所は推測で埋めず、質問または未確認として示す。
- 重要な条件や注意点を削らない。

出力：
整理した文章の後に、変更した点と判断に迷った点を短く示す。
```

これは出発点の例です。毎回すべての項目を埋める必要はありません。作業に関係する条件だけを残し、使いながら調整します。

### 6.3　分からないところは、AIと相談して具体化する

やりたいことが曖昧なときは、いきなり完成版のプロンプトを求めるのではなく、AIに相談相手になってもらいます。

例えば、次のように依頼します。

```text
私は「〇〇をやってみたい」と考えていますが、依頼内容をまだ具体化できていません。
いきなり完成案を出すのではなく、目的・条件・使える材料を整理するために、
一度に一つずつ質問してください。
私の回答を受けて、最後に試せる小さな依頼文を作ってください。
不明なことを勝手に決めず、未確認として残してください。
```

AIが出した質問に答える過程で、自分が本当に望んでいることや、避けたいことが明確になる場合があります。質問が多すぎると感じたら、「まず試すために必要な質問を三つ以内に絞って」と頼んでもかまいません。

### 6.4　一度に全部を解決しようとしない

最初の依頼は、小さく区切ります。大きな成果物を一度に作ろうとすると、どの条件がうまく働いたのか、どこで失敗したのか分かりにくくなります。

例えば「自分の経験を商品にして公開する」なら、最初から商品全体を完成させようとせず、次のように分けます。

- 経験の中から、一つの題材を選ぶ。
- その題材で実際に行ったことを箇条書きにする。
- 初めての人が再現できる順番に並べる。
- 不明点や失敗しやすい点を洗い出す。
- 小さな範囲で手順を試し、結果を記録する。

一段階ずつ試すと、次の依頼に必要な材料が増えます。最初から大きな計画を完成させることより、確かめられる一歩を作ることを優先します。

### 6.5　結果を見て、プロンプトを一か所ずつ直す

AIの回答を読んだら、漠然と「よくない」と判断するのではなく、どこが目的に合わなかったかを分けます。

- **不足**：必要な情報がない。
- **誤り**：事実や条件が間違っている。
- **過剰**：不要な説明が多い。
- **形式違い**：表、箇条書き、手順などの形式が合わない。
- **推測**：確認していない内容を事実のように補っている。
- **目的違い**：求めていた成果から外れている。

直すときは、問題に対応する条件を一つずつ追加します。例えば、説明が長すぎるなら「最初に結論を三点で示し、詳細は必要な場合だけ続ける」と加えます。推測が混じるなら「不明な点は推測で埋めず、未確認と明記する」と加えます。

複数の条件を一度に変更すると、何が改善につながったのか分かりにくくなります。変更したプロンプトと結果を簡単に記録しておくと、次の試行に活用できます。

### 6.6　プロンプトと結果をセットで記録する

再利用したいプロンプトは、文章だけを保存するのではなく、どの場面で使い、何が起きたかも一緒に記録します。

```markdown
# プロンプト試行記録

## 目的
何を実現したかったか：

## 使用したAI・利用条件
ツール名と、その時点で確認できた無料枠・制限：

## プロンプト
実際に入力した依頼文：

## 結果
役に立った点：

## 問題・未確認
期待と違った点、確認できていない事実：

## 次に変えること
次回、一つだけ変更する条件：
```

サービスの機能や無料枠は変更されることがあります。後から記録を読む人が誤解しないよう、分かる場合は確認日も記録し、実際に確かめた経験と一般的な仕様の説明を区別します。自分の経験を他の人にも当てはまる普遍的な結論として書かないようにします。

### 6.7　AIの提案をそのまま正解にしない

AIは、もっともらしい説明や手順を出しても、事実と異なることがあります。特にサービスの現在の仕様、価格、利用制限、権限、公開設定などは、AIの回答だけで確定しないでください。

- 重要な仕様は、公式の案内や実際の画面で確認する。
- 実行する前に、操作の影響と取り消し方法を確認する。
- 自分の経験から分かったことと、AIが提案しただけのことを分けて記録する。
- 期待どおりに動かなかった結果も残し、成功例だけに編集しない。
- 個人情報や認証情報を、必要性を確認せずにプロンプトへ貼り付けない。

AIの提案は、次に何を試すかを考える材料です。確認した結果を記録することで、自分の経験として蓄積できます。

### 6.8　この章の確認

- [ ] 目的・材料・条件・確認方法を必要な範囲で整理した。
