> **原稿状態：執筆中・未検証**
>
> この原稿はMarkdownで管理する。画面操作やサービス仕様など、実際の環境で確認していない内容は、確認済みの事実として扱わない。

## 第1章　AIで実現したいことを決め、使うAIを選ぶ

### この章の目的
#目的 #選定 #無料

AIを使って何かを実現したいとき、最初に必要なのは完璧な計画ではありません。試したいことを一つ選び、無料で始められる候補を比べ、まず何を試すかを決めます。

このマニュアルは、AIを使った経験を積み重ね、必要なら他の人にも伝えられる形にするための実践ガイドです。設定を済ませること自体をゴールにせず、整えた環境で試し、結果を記録できるところまで進みます。有料プランや有料サービスは基本手順の前提にしません。

### このマニュアル群の約束：基本の実践は完全無料で

AIを使い始めること、作業環境を整えること、試行錯誤を記録すること、経験や成果を公開することまで、**基本の実践を有料プランや有料ツールなしで進められる方法**を中心に紹介します。noteの有料記事はこの方針の例外ですが、無料公開する手順や基本の実践に、購入を必須条件として設けません。

「完全無料」は、無料プランに制限がないという意味ではありません。無料枠の回数・容量・機能制限、サービス側の仕様変更、無料ではできないことも明記し、制限に当たったときは作業を小さくする、手動で代替する、別の無料手段を検討するなどの方法を示します。読者が知らないうちに課金を求められる構成にはしません。

### 1.1　実現したいことを一つ選ぶ
#目的 #使い方

「AIで何かできないかな？」という段階でも構いません。結果を確かめられる小さな題材を選びます。

- 自分の考えをAIと相談して整理する。
- 日々の作業の一部を、AIでやりやすくできるか試す。
- AIとの対話や試行錯誤を記録し、あとから読み返せるようにする。
- 自分が試した方法を、他の人にも伝えられる手順にまとめる。

次のシートを埋めてください。決まっていない項目は「未定」で構いません。

| 項目 | 記入内容 |
|---|---|
| 実現したいこと | 何をやってみたいか |
| 試したい理由 | 興味、期待、実現したいこと |
| 最初の一歩 | 小さく試せる作業 |
| 完了条件 | 何を確認できれば今回の試行を終えられるか |
| 残したい記録 | 目的、試したこと、結果、気づき |
| 今回は扱わないこと | 初回の試行から外す範囲 |

**記入例**

| 項目 | 記入例 |
|---|---|
| 実現したいこと | AIとの相談内容を、あとから読み返せる記録にする |
| 試したい理由 | 以前試したことや、うまくいった方法を忘れたくない |
| 最初の一歩 | 短い相談を一回行い、要点をテキストファイルに残す |
| 完了条件 | 後から読んで相談内容と結論が分かる |
| 残したい記録 | 目的、試したこと、結果、次に試すこと |
| 今回は扱わないこと | 自動保存や複雑な自動化 |

### 1.2　AIの候補を挙げ、選んだ理由を残す
#選定 #無料 #確認

このマニュアルでは「好きなAIを選んでください」と読者に丸投げしません。候補を挙げ、今回の目的に合うかを比較し、採用理由を説明してから具体的な使い方へ進みます。

候補は、少なくとも次の観点で確認します。

- 今回の作業に必要な機能があるか。
- 無料利用の範囲で試せるか。回数・容量・機能などに制限はあるか。
- 必要な文章やファイルを扱えるか。
- 個人情報や非公開情報を入力せずに試せるか。
- 公式案内や実際の画面で条件を確認できるか。

比較結果は次の形で残します。

| 候補 | 目的との適合 | 無料利用の条件 | 気になる点 | 判断 |
|---|---|---|---|---|
| 候補A |  |  |  |  |
| 候補B |  |  |  |  |
| 候補C |  |  |  |  |

具体的なツールを推奨するときは、候補名、公式配布先・案内、確認日、採用理由を示します。候補を比較したことと、すべてを実地検証したことは別です。実際に試していないものを「検証済み」とは書きません。

### 1.2.1　筆者の実践例：ChatGPTをメインに、Claudeを切り札にする
#選定 #使い方 #無料

ここでは、筆者が実際に使っている体制を一例として紹介します。全員にとっての正解や、AIの性能順位を示すものではありません。自分に合う構成を考えるときの出発点として読んでください。

- **ChatGPT：メイン担当。** 普段の相談、考えの整理、文章や手順のたたき台作りなど、日常の作業の中心にします。
- **Claude：三枚のおふだ。** メインのAIだけでは行き詰まったときや、別の視点がほしいときに使う切り札として温存します。筆者の利用経験では無料枠の制限を強く感じるため、何でもClaudeに頼むのではなく、必要な場面を選びます。「三枚のおふだ」は、この例ではClaudeだけを指します。
- **自分（使う本人）：最終判断者。** AIの答えをそのまま正解とせず、提案を読み、必要な事実や操作結果を確認し、採用するかどうかを決めます。

この組み合わせが筆者にはうまく機能していますが、使い方、好み、無料枠で足りる範囲、有料プランを許容できるかどうかは人それぞれです。まず一つのAIだけで始めても、別のAIをメインにしても、複数のAIを役割分担させても構いません。有料プランへの加入を前提にせず、自分の条件で続けられる構成を選びます。

無料枠の上限や利用できる機能は変わることがあります。筆者の経験を現在の全利用者に当てはまる仕様として扱わず、使う時点の公式案内と実際の画面で確認してください。候補を増やすこと自体を目的にせず、今の構成で困った場面が出たら、追加のAIを試すか考えます。

### 1.3　AIに任せることと、自分で確認することを分ける
#使い方 #安全 #確認

AIは考えの整理、案出し、文章や手順のたたき台作成を助けます。一方、AIが正しいと答えたことだけでは、事実や操作結果の証明になりません。メインのAIと予備のAIを使い分ける場合も、どちらか一方の答えだけで判断を確定しないことが大切です。

- AIに任せること：相談、案出し、文章整理、手順案の作成。
- 自分で確認すること：実際の操作結果、重要な事実、サービスの現在の仕様、公開・共有の範囲。
- 記録に残すこと：自分が実施したこと、確認できた結果、まだ分からないこと。
- 最終的に決めること：AIの提案を採用するか、追加確認するか、見送るか。

最初から複数のAIを同時に使う必要はありません。まず一つの目的を一つのAIで試し、必要が出てから別の候補を検討します。筆者の「ChatGPTをメインに、Claudeを切り札にする」体制も、そうした選択肢の一つです。

### 1.4　最初の試行を決める
#使い方 #確認

次の形式で、最初の試行を一文にします。

```text
私は［実現したいこと］のために、まず［小さな作業］を試す。
［確認したい条件］を満たせば、今回の試行は完了とする。
結果と未確認事項を記録し、次に試すことを一つ決める。
```

### この章の完了条件
#確認

- [ ] 実現したいことを一つ選んだ。
- [ ] 最初の一歩と完了条件を書いた。
- [ ] AIの候補を比較する観点を理解した。
- [ ] 採用したAIと選んだ理由を記録できる状態にした。
- [ ] AIの提案と、自分で確認した事実を区別した。

この章では目的とAIの選定までを行います。アカウント、保存先、ファイル管理などの具体的な環境設定は、次章以降で手順に沿って進めます。


## 第2章　AIを使う環境を整え、作業を再開できるようにする

### この章の目的
#設定 #使い方 #安全

設定をする理由は、ツールを入れること自体ではありません。試したことを失わず、次に何をすればよいか分かり、必要なときに作業を再開できるようにするためです。

この章では、AIを使う前の基本ルールと、安全に作業するための確認方法を決めます。GitHub、会話のMarkdown保存、Dropboxの具体的な設定と操作は、それぞれの章で扱います。

### 2.1　始める前に作業条件を決める
#設定 #安全

作業を始める前に、必要な範囲で次の条件を確認します。

- 今回の目的と、今回扱わない範囲。
- 使用するAIと、無料利用の条件。
- AIに渡してよい情報と、渡さない情報。
- 結果を保存する場所。
- 完了と判断するための確認方法。

毎回長い説明を用意する必要はありません。今回の作業に関係する条件だけを短く書いておけば十分です。

### 2.2　秘密情報や不要な個人情報を入力しない
#安全 #確認

パスワード、アクセストークン、Cookie、セッション情報、秘密鍵などの認証情報は、AIへの依頼文や公開ファイルへ貼り付けません。他人の個人情報や、共有・公開する権利のない資料も、必要性と扱いを確認せずに入力しないでください。

実際の情報を使わなくても目的を達成できる場合は、架空の例や機密情報を除いた抜粋で試します。記録を保存するときも、秘密情報が混ざっていないか確認します。

### 2.3　AIの回答を実際の結果と混同しない
#使い方 #確認

AIが「完了した」「保存できた」と答えても、それだけで実際の操作が成功したとは限りません。作業の種類に応じて、実際の画面、保存されたファイル、公式情報などで確認します。

記録では、次の状態を分けて書きます。

- **実施したこと：** 自分が実際に行った操作。
- **確認できたこと：** 画面やファイルなどで確かめた結果。
- **未確認：** まだ確かめていない仕様や結果。
- **未完了：** まだ実施していない作業。

分からないことは推測で埋めず、「未確認」として残します。

### 2.4　外部に影響する操作は、内容を確認してから行う
#安全 #確認

ファイルの削除、上書き、公開、共有、権限変更、外部サービスへの送信などは、操作前に対象と影響を確認します。AIの提案をそのまま実行せず、何が変わるか、取り消せるか、どこに反映されるかを確認してください。

作業案を作ること、変更を保存すること、変更をマージすること、公開先に反映されることは別の段階です。各段階の結果を混同しないようにします。

### 2.5　無料プランの制限と仕様変更に備える
#無料 #確認 #代替手段

無料プランでは、利用回数、処理できる量、使える機能などに制限がある場合があります。制限は変更されることがあるため、現在の条件は公式案内や実際の画面で確認し、確認日も記録します。

制限に達した場合は、すぐに課金するのではなく、作業を小さくする、文章中心で進める、手動で代替する、別の無料候補を比較する方法を検討します。特定のAIが常に同じ機能や上限を持つとは断定しません。

### 2.6　中断しても再開できる記録を残す
#使い方 #確認

作業を中断するときは、会話全文だけでなく、次の要点を残します。

```markdown
# AI作業の区切り記録

## 目的
何を実現しようとしているか：

## 今回実施したこと
実際に行った操作：

## 結果
確認できたこと：

## 未確認・未完了
まだ確かめていないこと、終わっていないこと：

## 次の一手
次に行う作業を一つ：
```

この記録を使えば、時間が空いても同じ確認を最初から繰り返さずに再開しやすくなります。必要な情報だけを含め、秘密情報を入れないでください。

### この章の完了条件
#確認

- [ ] 今回の目的と作業範囲を決めた。
- [ ] 使用するAIの無料利用条件を確認する方法が分かった。
- [ ] 入力してはいけない情報を理解した。
- [ ] AIの提案、実施した操作、確認結果を区別できる。
- [ ] 外部に影響する操作は内容を確認してから行うと理解した。
- [ ] 作業を中断するときの記録ひな形を用意した。

次章では、実際の記録をGitHubで管理し、ファイルの保存と変更履歴を確認する手順へ進みます。


## 第3章　GitHubで記録と変更履歴を管理する

### この章の目的

この章では、AIとの試行錯誤で生まれたメモや手順を、後から見つけて再利用できる形で管理するために、GitHubの基本を整えます。ここでは、GitHubを初めて使う人が、Markdownファイルを保存し、変更内容を確認しながら更新するための入口を扱います。

GitHubの画面や無料プランの仕様は変わることがあります。ボタン名や利用可能な機能が本文と違う場合は、現在の画面と公式案内を優先してください。パスワードやトークンなどの認証情報を、リポジトリのファイルに記録してはいけません。

### 3.1　GitHubで管理するものを決める

GitHubは、ファイルを置くだけでなく、変更履歴を確認し、変更案をレビューしてから取り込むためにも使えます。AIとの作業では、次のような記録が候補になります。

- 自分が試したいことと、その目的
- AIに依頼したプロンプトや、再利用したい依頼テンプレート
- 試した手順、得られた結果、うまくいかなかった点
- 自分で確認した事実、まだ確認できていないこと
- 次に行う作業と、再開時に確認する場所

会話全文をすべて公開リポジトリへ入れる必要はありません。個人情報、第三者の情報、秘密情報、公開できない内容を含む記録は、公開リポジトリへ置かないでください。まずは公開しても問題のない短いサンプルから始めます。

### 3.2　アカウントとリポジトリを確認する

すでにGitHubアカウントを持っている場合は、新しく作り直す必要はありません。まず、ログインできることと、今回使うリポジトリを開けることを確認します。

1. ブラウザーでGitHubを開き、自分のアカウントにログインします。
2. 作業に使うリポジトリを開きます。リポジトリは、関連するファイルと変更履歴をまとめて管理する場所です。
3. リポジトリ名と所有者を確認します。似た名前の別リポジトリで作業しないようにします。
4. リポジトリの公開・非公開の状態を確認します。公開リポジトリに追加した内容は、原則として他者から閲覧できる前提で扱います。
5. 自分に変更権限があるか確認します。閲覧できることと、変更できることは同じではありません。

これから初めてリポジトリを作る場合は、用途を一つに絞った分かりやすい名前を付け、公開範囲を作成時に確認します。学習用の公開サンプルに秘密情報や個人情報を含めないことを、作成前に決めてください。リポジトリの公開・非公開を後から変更する場合も、影響を理解してから実施します。

### 3.3　Markdownファイルを一つ作る

Markdownは、見出しや箇条書き、リンク、コードなどを、基本的にはプレーンテキストで記述する形式です。専用の編集ソフトがなくても作成でき、GitHub上でも内容を確認しやすいため、このマニュアルでは原稿の正本形式として使います。

まず、公開しても問題のない小さなファイルを一つ作ります。例えば、ファイル名を `first-trial.md` とし、次の内容を入れます。

```markdown
# 最初のAI試行

## 目的

AIを使って、短い文章を分かりやすく整理する。

## 試したこと

- AIに文章の整理を依頼した。
- 元の意味が保たれているか確認した。

## 結果

ここに自分で確認した結果を書く。

## 未確認・次の一手

- 未確認の点：
- 次に試すこと：
```

GitHubのWeb画面から作成する場合は、対象リポジトリで新規ファイル作成の操作を選び、ファイル名と本文を入力して変更を保存します。画面の操作名が変わっている場合は、現在のGitHub画面の案内を確認してください。

保存後は、ファイルがリポジトリ内に表示されること、見出しや箇条書きが意図した形で読めること、入力した内容が欠けていないことを確認します。ファイルを作ったつもりでも、保存が完了していない場合があります。

### 3.4　変更履歴を確認する

GitHubでは、ファイルを変更すると、その変更を記録として残せます。この記録の単位をコミットと呼びます。コミットのメッセージには、変更の目的が分かる短い説明を付けます。

例えば、試行結果を追記した場合は「最初のAI試行の結果を追記」のように書きます。「更新」だけでは、後から変更内容を見分けにくくなります。

変更後は、次の点を確認します。

1. 変更したファイルが意図したものか。
2. 差分に、今回変更した内容だけが含まれているか。
3. 削除や置換を意図せず行っていないか。
4. コミットメッセージから、変更の目的が分かるか。
5. 保存後のファイルを開き、内容が期待どおりか。

変更履歴は、間違いを必ず自動で防いでくれる仕組みではありません。変更前後を比べることで、何が変わったかを把握しやすくする仕組みです。大きな変更の前には、対象ファイルと差分を特に慎重に確認します。

### 3.5　ブランチとPull Requestを知る

複数の変更を安全に扱いたい場合は、ブランチとPull Requestを利用できます。

- **ブランチ**：既存の状態を基に、変更を分けて進めるための作業線です。
- **Pull Request（PR）**：ブランチ上の変更案を、別の人や自分自身で確認してから取り込むための提案です。
- **レビュー**：変更内容を読み、目的との整合、誤り、漏れ、危険がないかを確認することです。
- **マージ**：確認された変更を、取り込み先のブランチへ統合することです。

一人で作業していても、PRを使うと、変更案を確定する前に差分を確認できます。PRを作成しただけでは、変更が取り込み先へ反映されたとは限りません。レビュー状態、必要なチェック、マージ済みかどうかを別々に確認してください。

このマニュアルのように、既存の正本を変更する作業では、本文をいきなり本番用のブランチへ直接書き換えるのではなく、変更案をPRとして提示し、内容とチェック結果を確認してから取り込む流れを基本にします。リポジトリごとに保護ルールや承認条件が異なるため、そのリポジトリで設定されている条件に従います。

### 3.6　正本とコピーを混同しない

同じ内容が複数の場所にあると、どれが最新なのか分からなくなることがあります。ファイルを作る前に、そのファイルの正本をどこに置くか決めてください。

このマニュアル制作では、Markdown原稿をGitHubリポジトリで管理し、GitHub Pagesを本番公開先とします。Dropboxなど別の場所にコピーを保管する場合も、コピーだけを更新して正本への反映を忘れないようにします。保存したこと、PRで提案したこと、マージしたこと、公開ページへ反映されたことは、それぞれ異なる状態です。

最初の試行では、次のような表を自分の作業用に用意すると、保存場所を確認しやすくなります。

| 種類 | 保存先 | 扱い |
| --- | --- | --- |
| 原稿・手順の正本 | 決めたGitHubリポジトリ | 変更履歴を管理する |
| 一時メモ | 自分が管理できる作業場所 | 必要な内容を確認して正本へ反映する |

| 公開ページ | GitHub Pagesなどの公開先 | 原稿の保存とは別に表示を確認する |

この表は役割を理解するための例です。実際の保存先は、自分の作業環境と公開範囲に合わせて決めます。

## 第5章　Dropboxで記録を整理する

### この章の目的

AIとの試行錯誤で生まれたファイルを、後から見つけて使い直せるように整理します。ここではDropboxを保管・受け渡し用の場所として扱い、正本とコピーを混同しないための基本を決めます。Dropboxを使わない場合も、同じ考え方を自分の保管場所に適用できます。

### 5.1　保存先の役割を決める

ファイルを保存する前に、それぞれの場所を何のために使うか決めます。保存先を増やすほど安心になるとは限りません。どこが正本か分からなくなり、更新漏れが起きることもあります。

このマニュアル制作での役割分担は、次のとおりです。

| 場所 | 役割 | 注意点 |
| --- | --- | --- |
| GitHubリポジトリ | Markdown原稿・手順の正本と変更履歴 | 正本を変更したら差分と保存結果を確認する |
| Dropbox | 必要な記録の保管、端末間の受け渡し、バックアップ用コピー | コピーを更新しただけで正本も更新されたと思わない |
| PC上の作業フォルダー | 作業中の一時ファイル | 不要な一時ファイルを残し続けない |
| GitHub Pages | 公開されたページの表示先 | 原稿の保存とは別に公開結果を確認する |

これはこの作業での役割例です。自分の構成に合わせて変えてもかまいませんが、正本がどこにあるかは一つに決め、記録しておきます。

### 5.2　Dropboxに保存するものを選ぶ

すべてのAIチャットを無条件に保存する必要はありません。後から再開・再利用する価値があるものを選びます。

- 試した手順と、実際に確認できた結果
- 再利用したいプロンプトや作業テンプレート
- 次に作業を再開するための区切り記録
- 必要な場合の、公開して問題のない会話記録
- 正本とは別に保管しておく必要があるファイル

パスワード、APIトークン、Cookie、セッション情報などの認証情報は保存しないでください。第三者の個人情報や、公開許可のない仕事上の情報も、保存の必要性と適切な保護方法を確認せずに持ち込まないでください。

### 5.3　フォルダーを少なく分かりやすくする

最初から細かい分類を作りすぎず、まずは少数のフォルダーで始めます。例えば、次のような構成です。

```text
AI記録/
├─ 01_作業中/
├─ 02_試行記録/
├─ 03_再利用テンプレート/
└─ 99_一時保管/
```

この構成は例です。分類に迷うファイルは、ひとまず一時保管へ置き、後で必要性を判断します。一時保管を恒久的な置き場にしないよう、定期的に中身を見直します。

フォルダー名は、自分が見て意味を判断できる言葉にします。階層を深くしすぎると保存先を探しにくくなるため、必要が出てから分類を増やします。

### 5.4　ファイル名に日付と内容を入れる

ファイル名だけで内容と時期を大まかに判断できるようにします。例えば、次のような形式です。

```text
YYYY-MM-DD_作業テーマ_記録.md
2026-10-14_文章整理_試行記録.md
2026-10-14_再開用_区切り記録.md
```

日付は実際に作業した日付を使い、日付が分からない場合は推測で付けないでください。同じ名前のファイルを上書きする前に、既存ファイルが必要な記録ではないか確認します。サービスの自動命名がある場合も、保存後にファイル名と中身を確認します。

ファイル名へ個人情報や秘密情報を含めないことも大切です。共有リンクを作る場合、リンク先のファイル名自体が相手に見えることがあります。

### 5.5　保存後に中身と場所を確認する

アップロード操作をしただけでは、目的の場所に正しい内容が保存されたとは限りません。保存後に、次を確認します。

1. 保存先のアカウントとフォルダーが正しい。
2. ファイル名が分かりやすく、既存ファイルを意図せず置き換えていない。
3. ファイルを開けて、内容が欠けていない。
4. Markdownの場合は、見出し・箇条書き・コードなど必要な内容が残っている。
5. 正本とコピーのどちらなのかが分かる。
6. 共有設定が意図した範囲になっている。必要がなければ共有リンクを作らない。

同期アイコンやアップロード表示だけを見て完了と決めつけず、必要なファイルを実際に開いて確認します。大切な記録を複数の場所に置く場合は、どれが正本かを明記しておきます。

### 5.6　コピーを正本へ反映する手順を決める

Dropboxで記録を整理しても、GitHubの正本が自動的に更新されるわけではありません。コピー側で内容を直した場合は、正本へ反映する必要があるかを判断し、必要なら変更案として反映して差分を確認します。

このマニュアル制作の原稿を更新する場合は、GitHub上の変更案を確認し、リポジトリのルールに従ってPR・チェック・マージの状態を確認します。Dropboxへの保存、GitHubへの変更案の提出、マージ、本番ページへの反映は別の段階です。

### 5.7　この章の確認

- [ ] 正本、コピー、作業中ファイル、公開先の役割を区別した。
- [ ] 保存する記録を選び、認証情報や公開できない情報を除外した。
- [ ] 自分が理解できる少数のフォルダーから始めた。
- [ ] 日付と内容が分かるファイル名を付けた。
- [ ] 保存後に保存先とファイルの中身を確認した。
- [ ] 共有設定を確認し、不要な共有を作っていない。
- [ ] コピー側の変更を正本へ反映する方法を決めた。

次章では、AIに何かを試してもらう前に、目的と条件を整理し、再利用できるプロンプトへ育てる方法を扱います。


## 第6章　目的と条件を整理し、プロンプトを育てる

### この章の目的

AIに何かを頼むとき、最初から完璧な指示を書く必要はありません。まず「何を実現したいか」を言葉にし、試した結果を見ながら条件を足していきます。この章では、プロンプトを一度きりの命令文ではなく、試行錯誤を通じて育てるための方法を整理します。

### 6.1　ツールを開く前に、やりたいことを書く

最初に、AIの画面を開く前に、やりたいことを一文で書きます。例えば、次のような形です。

- 長い文章を、意味を変えずに短く整理したい。
- 作業の記録から、次回も使える手順を作りたい。
- 自分の経験を、初めて読む人にも分かる説明にしたい。
- 新しいテーマについて、無料で試せる方法を探したい。

この段階では、解決方法まで決まっていなくてもかまいません。「何かいい感じにして」だけで止めず、どんな結果を得たいのかを少し具体的にします。

### 6.2　最初の依頼に入れる四つの要素

最初のプロンプトには、必要に応じて次の要素を入れます。

1. **目的**：何を実現したいか。
2. **材料**：AIに渡す文章、情報、前提は何か。
3. **条件**：変えてはいけない点、使える道具、長さ、形式など。
4. **確認方法**：どんな結果なら役に立ったと判断できるか。

例えば、文章を整理したい場合は、次のように書けます。

```text
目的：
次の文章を、初めて読む人にも分かりやすく整理したい。

材料：
ここに自分の文章を貼り付ける。

条件：
- 元の意味や事実を変えない。
- 情報が足りない箇所は推測で埋めず、質問または未確認として示す。
- 重要な条件や注意点を削らない。

出力：
整理した文章の後に、変更した点と判断に迷った点を短く示す。
```

これは出発点の例です。毎回すべての項目を埋める必要はありません。作業に関係する条件だけを残し、使いながら調整します。

### 6.3　分からないところは、AIと相談して具体化する

やりたいことが曖昧なときは、いきなり完成版のプロンプトを求めるのではなく、AIに相談相手になってもらいます。

例えば、次のように依頼します。

```text
私は「〇〇をやってみたい」と考えていますが、依頼内容をまだ具体化できていません。
いきなり完成案を出すのではなく、目的・条件・使える材料を整理するために、
一度に一つずつ質問してください。
私の回答を受けて、最後に試せる小さな依頼文を作ってください。
不明なことを勝手に決めず、未確認として残してください。
```

AIが出した質問に答える過程で、自分が本当に望んでいることや、避けたいことが明確になる場合があります。質問が多すぎると感じたら、「まず試すために必要な質問を三つ以内に絞って」と頼んでもかまいません。

### 6.4　一度に全部を解決しようとしない

最初の依頼は、小さく区切ります。大きな成果物を一度に作ろうとすると、どの条件がうまく働いたのか、どこで失敗したのか分かりにくくなります。

例えば「自分の経験を商品にして公開する」なら、最初から商品全体を完成させようとせず、次のように分けます。

- 経験の中から、一つの題材を選ぶ。
- その題材で実際に行ったことを箇条書きにする。
- 初めての人が再現できる順番に並べる。
- 不明点や失敗しやすい点を洗い出す。
- 小さな範囲で手順を試し、結果を記録する。

一段階ずつ試すと、次の依頼に必要な材料が増えます。最初から大きな計画を完成させることより、確かめられる一歩を作ることを優先します。

### 6.5　結果を見て、プロンプトを一か所ずつ直す

AIの回答を読んだら、漠然と「よくない」と判断するのではなく、どこが目的に合わなかったかを分けます。

- **不足**：必要な情報がない。
- **誤り**：事実や条件が間違っている。
- **過剰**：不要な説明が多い。
- **形式違い**：表、箇条書き、手順などの形式が合わない。
- **推測**：確認していない内容を事実のように補っている。
- **目的違い**：求めていた成果から外れている。

直すときは、問題に対応する条件を一つずつ追加します。例えば、説明が長すぎるなら「最初に結論を三点で示し、詳細は必要な場合だけ続ける」と加えます。推測が混じるなら「不明な点は推測で埋めず、未確認と明記する」と加えます。

複数の条件を一度に変更すると、何が改善につながったのか分かりにくくなります。変更したプロンプトと結果を簡単に記録しておくと、次の試行に活用できます。

### 6.6　プロンプトと結果をセットで記録する

再利用したいプロンプトは、文章だけを保存するのではなく、どの場面で使い、何が起きたかも一緒に記録します。

```markdown
# プロンプト試行記録

## 目的
何を実現したかったか：

## 使用したAI・利用条件
ツール名と、その時点で確認できた無料枠・制限：

## プロンプト
実際に入力した依頼文：

## 結果
役に立った点：

## 問題・未確認
期待と違った点、確認できていない事実：

## 次に変えること
次回、一つだけ変更する条件：
```

サービスの機能や無料枠は変更されることがあります。後から記録を読む人が誤解しないよう、分かる場合は確認日も記録し、実際に確かめた経験と一般的な仕様の説明を区別します。自分の経験を他の人にも当てはまる普遍的な結論として書かないようにします。

### 6.7　AIの提案をそのまま正解にしない

AIは、もっともらしい説明や手順を出しても、事実と異なることがあります。特にサービスの現在の仕様、価格、利用制限、権限、公開設定などは、AIの回答だけで確定しないでください。

- 重要な仕様は、公式の案内や実際の画面で確認する。
- 実行する前に、操作の影響と取り消し方法を確認する。
- 自分の経験から分かったことと、AIが提案しただけのことを分けて記録する。
- 期待どおりに動かなかった結果も残し、成功例だけに編集しない。
- 個人情報や認証情報を、必要性を確認せずにプロンプトへ貼り付けない。

AIの提案は、次に何を試すかを考える材料です。確認した結果を記録することで、自分の経験として蓄積できます。

### 6.8　この章の確認

- [ ] AIを開く前に、実現したいことを一文で書いた。
- [ ] 目的・材料・条件・確認方法を必要な範囲で整理した。
- [ ] 曖昧な点はAIとの相談で具体化した。
- [ ] 最初の依頼を、小さく試せる範囲に区切った。
- [ ] 結果の問題点を分け、プロンプトを一か所ずつ調整した。
- [ ] プロンプトだけでなく、結果・問題・次の変更も記録した。
- [ ] AIの提案と、自分で確認できた事実を区別した。

次章では、ここまでに用意したAI・GitHub・記録保存の仕組みを使って、小さなテーマを実際に試し、経験として残す手順に進みます。


## 第7章　小さなテーマを試し、経験として残す

### この章の目的

ここまでで、AIを使うための基本的な準備、記録を保存する場所、目的と条件を整理する方法を用意しました。この章では、それらを使って小さなテーマを一つ試し、結果を自分の経験として残します。

ここで目指すのは、最初から大きな成果を完成させることではありません。「何を試したか」「何が起きたか」「次に何を変えるか」が分かる記録を一つ作ることです。

### 7.1　今回試すテーマを一つ選ぶ

まず、今の自分が試してみたいことを一つ選びます。数時間かかる大きな計画ではなく、結果を見て良し悪しを判断できる大きさにします。

例えば、次のようなテーマです。

- 自分が書いた短い文章を、意味を変えずに読みやすくする。
- 作業メモを、次回も使える手順に整理する。
- 興味のあるテーマについて、無料で試せる方法を調べ、確認先を整理する。
- 自分の経験を、初めて読む人向けの説明に書き直す。

テーマを選んだら、次の三点を書きます。

- **やりたいこと：** 今回、何を実現したいか。
- **今回の範囲：** どこまでできれば試行を終えるか。
- **確認基準：** 結果の何を見て、役に立ったか判断するか。

例えば「文章を読みやすくする」なら、範囲は「段落一つを整理する」、確認基準は「意味が変わっていないこと、重要な情報が残っていること、初見で理解しやすいこと」とできます。

### 7.2　使うAIと無料利用の条件を確認する

テーマが決まったら、その作業に合いそうなAIを選びます。AIを一つに決め打ちせず、文章の整理、調査の補助、案の比較など、今回の目的に合うものを選びます。

使い始める前に、公式の案内や実際の画面で次を確認します。

- 無料で今回の作業を試せるか。
- 利用回数・容量・機能などに制限があるか。
- 入力した情報がどのように扱われるか。
- 必要な機能やファイル形式を使えるか。

無料枠や画面、利用条件は変わることがあります。過去の記録やAIの説明だけで現在の条件を決めず、確認した日と確認先を記録します。無料で試せる範囲が足りない場合は、課金を前提にせず、作業を小さくするか、別の無料手段を検討します。

### 7.3　入力する情報を整える

AIへ渡す前に、材料を確認します。今回の目的に不要な情報は渡さず、個人情報、パスワード、アクセストークン、Cookie、非公開の認証情報などは入力しません。実際のデータを使う必要がない場合は、架空の例や機密情報を除いた抜粋で試します。

次に、第6章で整理したプロンプトを使い、目的・材料・条件・確認方法を伝えます。最初から長い指示を作る必要はありません。小さく試して、結果を確認できる形にします。

### 7.4　一回試し、結果を確認する

プロンプトを入力したら、結果をそのまま採用する前に、最初に決めた確認基準と照らし合わせます。

- 目的に沿った結果になっているか。
- 元の情報や重要な条件が保たれているか。
- 事実のように書かれた未確認情報が混じっていないか。
- 実際に使う場合に、危険な操作や望まない公開につながらないか。

必要な事実やサービス仕様は、公式情報や実際の画面など、適切な情報源で確認します。AIが「できた」と答えたことと、実際に確認できたことを区別します。

結果が期待どおりでなくても、試行は失敗として捨てず、どこが違ったかを記録します。問題が分かったら、第6章の方法でプロンプトの条件を一つだけ変え、必要な範囲で再試行します。何度も試すこと自体を目的にせず、今回の範囲で得られたことを残します。

### 7.5　試行記録を作る

試行が終わったら、次のひな形で記録します。AIとの会話全文を保存するだけでなく、後から読み返したときに、目的・実際に行ったこと・結果・次の一歩が分かるようにします。

```markdown
# AI試行記録

## 実施日
YYYY-MM-DD

## 今回の目的
何を実現したかったか：

## 試した範囲・確認基準
どこまで試すか：
何を見て結果を判断するか：

## 使用したAI・利用条件
ツール名：
無料利用の条件・制限：
確認日・確認先：

## 実際に行ったこと
入力した材料：
使用したプロンプト：
実行した手順：

## 結果
実際に得られたもの：
確認基準に照らした結果：

## 分かったこと・未確認
うまくいった点：
期待と違った点：
まだ確認できていない点：

## 次に試すこと
次回に変えること、または次の小さなテーマ：
```

記録には、必要な範囲でプロンプトと結果を残します。ただし、秘密情報や他人の個人情報、保存する必要のない会話内容をそのまま転記しないでください。公開を考える場合は、記録をそのまま公開せず、個人情報・権利・未確認情報を確認してから公開用に整えます。

### 7.6　GitHubとDropboxに役割に沿って保存する

記録を作ったら、保存先の役割を混同しないようにします。

- **GitHub：** 継続して管理する正本や、手順・成果物の変更履歴を扱う場所。
- **Dropbox：** 会話記録や作業資料など、補助的な記録を整理しておく場所。

Dropboxへコピーしただけで、GitHubの正本が更新されたことにはなりません。GitHub側の変更は、リポジトリで定められた保存手順に従い、反映後に対象ファイルを読み戻して確認します。保存したつもりで終わらせず、どこに何を保存したかを記録に残します。

### 7.7　次の一歩を一つだけ決める

試行記録の最後に、次の行動を一つだけ書きます。例えば、次のような選択肢があります。

- 今回のプロンプトを少し直して、別の短い材料で試す。
- 公式情報を確認し、未確認だった点を埋める。
- 今回の手順を、初めての人でも再現できる説明に整える。
- 似たテーマを試し、結果の違いを記録する。
- いったん終了し、今回分かったことを整理する。

すべてを一度に進める必要はありません。一つの試行から得られた経験を次の試行につなげることで、自分に合う使い方や再利用できる手順が少しずつ蓄積されます。

### 7.8　この章の確認

- [ ] 今回試すテーマを一つに絞った。
- [ ] 目的・範囲・確認基準を書いた。
- [ ] 使用するAIの無料利用条件を確認した。
- [ ] 入力する情報から秘密情報や不要な個人情報を除いた。
- [ ] 結果を確認基準と照らし合わせ、未確認事項を区別した。
- [ ] 実際の操作・結果・問題・次の一歩を記録した。
- [ ] GitHubとDropboxの役割を分けて保存を確認した。
- [ ] 次に試すことを一つ決めた。

この章で作った試行記録が、次の挑戦の出発点になります。試行を継続して管理する方法や、記録を再利用しやすくする方法は、運用マニュアルで詳しく扱う範囲です。初版のセッティングマニュアルでは、まず一度試し、経験を残すところまでを目指します。
