# BLOG-0003 GitHub一次資料 深掘り調査メモ v03

## 今回の追加確認

既存のBLOG-0003成果物（構成骨組み、深掘り後案、全量作業稿、インタビュー整理）を先に確認したうえで、2026-09-18〜09-21の直チャット保存記録とGit履歴を追加確認した。

### 1. 保存時刻問題は「保存したつもり」と実体確認のズレの具体例になる

2026-09-18の直チャットでは、保存時刻生成の不整合、旧+0000記録、CIの最新判定、保存経路の正本同期まで実際の会話として残っている。

確認できた流れ：
- 保存時刻の不整合を発見
- 旧データを安易に改名せず、履歴で裏取りする方針
- 生成側の時刻をAsia/Tokyoの単一nowへ統一
- 旧+0000記録は現行判定から分離
- CI成功後も「本番経路で何を実証したか」を区別
- 保存経路と正本同期の漏れを修正

これは「GitHubに保存する」だけでは完了にならず、実体・CI・正本readbackまで確認する考え方が形成された具体例。

### 2. 「主作業」と「保存作業」を分ける必要が生まれた

2026-09-19〜20のGit履歴では、
- 主作業と保存タスクを分離
- 保存受付と報告を主作業のブロック要因にしない
- 重複した保存要求を防止
- 保存キューの入口をcanonical stateに保持
が段階的に実装されている。

2026-09-20の直チャットでは、たかが「必要な報告が足りないのと、作業が進まなくなる。大問題」と指摘し、バドが「【作業】と【保存】を分けて報告する」と修正している。

したがって、保存システムの発展は単なる技術改善ではなく、「保存のための処理が本来の作業を止める」という新しい問題への対応でもある。

### 3. 「保存できた」と「正本が現在化された」は別問題だった

2026-09-21の直チャットでは、
- 保存PR #247はmerge済み
- しかしdocs/現在状態.jsonは古いまま
という不一致が確認されている。

ここから、保存PRのmergeだけでなく、保存→CI→承認→merge→正本readbackまでを一続きで確認する必要が明確になる。

### 4. 「次に進む」と言いながら周辺作業だけ進むループも問題化した

2026-09-21には、たかから「やるやる詐欺。何ターン目だ？」との指摘があり、本線を進めると言いながら状態更新・検証・保存の周辺作業だけが続く問題が明示された。

これに対して、
- work/*で実質的な作業がないPRをCIで止める
- 状態・生成ビューだけの更新は保存トラックへ分離
という本線ループ防止ゲートが実装された。

これは後の「現在状態・work_items・再開チェック」につながる重要な転換点。

### 5. 現在状態を「再開時の判断材料」にする方向が具体化した

2026-09-20〜21のGit履歴では、
- resume_check
- resume manifest
- current-state guard
- generated BUD / handoff
- retired environmentの除外
などが整備されている。

つまりcurrent-state.jsonは単なる進捗メモではなく、「次にAIが再開するとき、何を現在として扱うか」を制御する役割へ変化している。

### 6. AIの役割変化も一次資料で確認できる

2026-09-21のクロウ監査記録では、たかが現状監査を依頼し、クロウは確認できる範囲と未確認を分けて報告している。

インタビュー整理にある
- たか＋バドが主作業
- JUNがレビュー役
- クロウがお目付役
という後日の本人説明と、実際の監査記録がつながる。

ただし「役割がいつ確定したか」はまだ細かい時系列確認が必要。
