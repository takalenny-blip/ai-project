- インタビューの回答をそのまま記事の地の文に置き換えない。

## 第1章の流れ

### 1. 最初の目的

インタビュー：
- 「まずは、自分とAIとのやりとりを消さずに残すことが一番はじめ。ブログを想定していたから。」
- 「ブログにして情報を発信したかったから。」

記事での役割：
- 物語の出発点。
- 最初から「経験DB」や「GitHubの仕組み」を作ろうとしていたわけではないことを示す。

引用状態：
- インタビュー原文は確認済み。
- 本文では、インタビュー引用と一次会話を区別する。

### 2. なぜ「チャットそのもの」だったのか

インタビュー：
- チャットには、そのときの感情が出る。
- 喜び、悲しみ、怒りが残る。
- AIとのキャッチボールから気づきが生まれたり、展開が分かる。
- 「その場にいるがごとく。それを後からでもよみがえらせたい。」
- 「自分が何を考えていたか、AIとどうやりとりしていたかをたかとAIで思い出して共有するため。」

既存一次会話の中心候補：
> 「こういうチャットのやりとりも、githubの直チャットに保存しようとしてほしいんだ。」

> 「今日も大事な作業やったんだからさ。もったいないじゃん。消えていくのは。」

記事での役割：
- 「保存したい」が単なる成果物保存ではなく、会話・感情・キャッチボールを残したいという意味だったことを示す。

確認状態：
- 既存の構成骨子に引用候補として登録済み。
- 本文採用時に一次資料原文を再確認する。

### 3. 「経験そのものをログとして」への転換

インタビュー：
- バドから「経験そのものをログとして」という発想が出た。
- 「これってすごい！やりたい！ワクワクする」と感じた。
- そうであるなら、まとめた記事ではなく生の会話でないと伝わらないと思った。
- 残したいものは「AIとのキャッチボール、そこから生まれた気づき」。

既存一次会話の候補：
> 「まとめなくていいのだ。チャットそのままでないと。」

> 「ばかタレ！直チャット案は、チャットそのものだろーが！」

記事での役割：
- 第1章から第3章への橋渡し。
- 「残したい」→「何を残すのか」が明確になる転換点。

### 4. 第1章ではまだ技術を説明しすぎない

第1章で見せるもの：
1. 残したい。
2. ブログとして発信したい。
3. チャットには、その時の感情・キャッチボール・気づきが残る。
4. だから後からその場をよみがえらせたい。
5. 「経験そのものをログとして」という発想で、残す対象がさらに明確になった。

第1章でまだ詳しく説明しないもの：
- GitHubの具体的な保存実装。
- CI、承認、merge、readback。
- 正本の設計。
- Dropboxとの境界。
- 保存失敗のコミット履歴一覧。

これらは第2章以降へ送る。
