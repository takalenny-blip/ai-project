# BLOG-0003 GitHub一次資料 深掘り調査メモ v1

## 目的

BLOG-0003の構成を先に固定せず、GitHub上の一次資料と保存・運用の変化を広く追い、実際の時系列と因果関係を確認する。

## 調査範囲

- 対象リポジトリ: `takalenny-blip/ai-project`
- 対象: `直チャット/`、関連する運用ルール・現在状態・GitHubコミット履歴
- 期間: 2026-09-01〜2026-09-28時点まで
- `直チャット/` のGit tree上のblob総数: 481
- 9/1〜9/8のGitHub関連・保存関連の明示的な直チャットを実ファイルで確認
- 9/9〜9/28は、明示的な個別直チャットに加えて、保存・current-state・queue・Dropbox等に関するGitHubコミット履歴を追跡

## 重要な確認

「検索でヒットした断片」を一次資料とみなしていない。
実ファイルを取得できたものは、会話の流れを含めて確認した。
一方、9/9以降の大量の「直チャット即時保存」ファイルには数十万〜数百万文字級のものがあり、現在のGitHub connectorでは一部の巨大ファイル本文を取得できない。したがって、現時点で「全直チャットを全文確認済み」とは言わない。

この未確認範囲は、記事本文に断定的に使わず、追加確認対象として残す。

## 実ファイルで確認した主な流れ

### 2026-09-04: GitHubを共有情報庫として試す

`2026-09-04-直チャット-JUN-github` では、GitHubリンクをJUNに読ませ、リポジトリの構成や共有情報を確認しようとしている。

同じ会話の後半で、たかはJUNに「こういうチャットのやりとりも、githubの直チャットに保存しようとしてほしい」と求めている。

さらに、
- 「今日も大事な作業やったんだからさ。もったいないじゃん。消えていくのは。」
- 「まとめなくていいのだ。チャットそのままでないと。」
- 「ばかタレ！直チャット案は、チャットそのものだろーが！」

という流れが確認できる。

ここで、共有情報庫と「生の会話を残す場所」が接続する。

### 2026-09-05: 記録する仕組みそのものが経験になる

`2026-09-05_直チャット_バド_経験DBそのものが経験になっていることへの気づき.md` が存在する。
「経験DBそのものが経験になっている」という認識は、後半のBLOG-0003の着地点候補になる。

### 2026-09-07: GitHubを再読込し、共有情報庫として再認識

`2026-09-07_直チャット_バド_たか_GitHub再読込` では、GitHubを読み直し、
- `docs`
- `指針等`
- `直チャット`
- `経験ログ`
を共有情報領域として確認している。

また、GitHubとVAIO Pを混同する問題が実際に起きており、後の「GitHub上の事実」と「実機で確認した事実」を分ける必要性につながる材料になっている。

### 2026-09-07〜09-08: 「保存した」と「実際に保存された」の差が問題化

`2026-09-08_直チャット_バド_保存監査とリカバリ` では、保存完了報告とGitHub上の実体確認が一致していなかった問題が明示されている。

重要な原則として、
「保存できていないものを、保存したことにしない。」
が確認されている。

また、過去の保存報告をGitHubのコミット履歴と照合し、
1. 対象特定
2. 対応コミット確認
3. 実ファイル確認
4. 内容対応確認
5. 欠落・不一致をリカバリ
という監査手順へ進んでいる。

同時期の`2026-09-08_直チャット_バド_運用フロー再設計とクローズ`では、
「保存したつもり」ではなく、
完了条件→関連更新→保存→読み戻し→整合性確認→クローズ
という考え方が標準化されている。

### 2026-09-09以降: 保存が「ファイル追加」から「システム」へ

GitHubコミット履歴から、以下の変化が確認できる。

- 9/17: chat save request intake workflow
- 9/17: repository_dispatch / workflow_dispatchによる正規直チャット保存経路
- 9/20: save intakeと本作業を分離し、失敗したqueueを保持
- 9/20: 重複したdirect-chat save requestを防止
- 9/20〜22: current-state、生成ビュー、CI guard、atomic save等の整備
- 9/22: save syncがcanonical directionを上書きしないための修正
- 9/23: save-request self-reference loopを防ぐcategory boundary
- 9/26: large save queue entryをgit blob APIで読む修正

これは、最初から設計された完成形ではなく、「保存しようとした結果、次々に問題が見つかり、仕組みを追加していった」ことを示す。

### Dropbox境界

9/21にはDiMORAのwork_pc＋Dropbox入口チェックが追加され、9/22以降はcanonical directionと保存同期の整合性が問題になる。

9/25〜28にはDropbox原本を含む大容量保存や保存経路の問題が続いている。
現在の運用上は、
Dropbox = 受け渡し・原本側
GitHub = 正規保存・正本側
という境界が明確になっている。

ただし、この境界が会話上いつ・なぜ確定したのかは、該当巨大直チャットの本文追加確認が必要。

## 現時点で見えてきた本当のストーリー

現行構成では「AIの役割変化」を5章に置いているが、一次資料を追うと、先に大きく起きているのは「保存したい」→「保存できない」→「保存を仕組みにする」→「正本が必要になる」という変化。

AIの役割変化は、その仕組みを作る過程から生じた結果として後半に置いたほうが、時系列と因果関係を追いやすい可能性が高い。

また、現行構成の「GitHubに置けば終わりではなかった」は重要だが、後半の保存失敗・監査・workflow・queue・canonical stateまで含めると、ここは独立した大きな流れとして扱う必要がある。

## 構成変更候補

1. 「AIとのやりとりを残したい」から始まった
   - ブログ／情報発信

   - 直チャット

   - 会話から生まれる気づき

   - 保存漏れ
   - 保存したつもり
   - 実体確認
   - 監査・リカバリ

5. 保存の仕組みを作ったら、また問題が出た

   - queue
   - duplicate
   - current-state同期
   - CI
   - atomic save
   - self-reference
   - 大容量

   - generated views
   - GitHub正本
   - 現在と過去の分離

7. Dropboxとの境界を決める
   - 受け渡し
   - 正本ではない
   - GitHubへ正規保存

8. その過程で、AIとの役割も変わった
   - たか＋バド中心
   - JUNの第三者的確認
   - クロウの別視点
   - たか自身がAIをつなぎ、手綱を取る役割へ
