# Noteマニュアル群の企画・制作・公開・需要検証の統合管理設計

- 状態：運用設計案
- 対象：AI活用に関するマニュアル群、経験ノウハウ、無料公開物、Noteでの需要検証
- 現在の先行対象：AI作業のセッティングマニュアル
- 現在の本番公開先：GitHub Pages
- Noteの位置づけ：需要検証・販売の候補経路。販売開始や有料化を既定路線にしない
- 対象読者・無料前提：セッティングマニュアルの決定済み対象読者ファイルを参照し、再決定しない

## 1. 設計目的

個別の決定や作業を場当たり的に追加するのではなく、企画から知識の蓄積、制作、実地検証、無料公開、需要検証、販売判断、更新までを一つのライフサイクルとして管理する。チャットや担当AIが変わっても、決定済み事項の巻き戻り、工程飛ばし、完了の誤認、資料間の矛盾を起こさない。

## 2. 管理対象を分ける

1. **方針・決定**：対象読者、無料を大前提とすること、本番公開先、誇大な効果保証をしないことなど。決定事項と未決事項を明確に分離する。
2. **知識資産**：経験ログ、試行内容、成功・失敗、事実と仮説、未解決点、再利用可能な知見。
3. **制作物**：各マニュアル、記事、テンプレート、チェックリスト、サンプル。制作物ごとに正本と版を明確にする。
4. **配布・検証経路**：GitHub Pagesでの無料公開、Note等での反応・購入意向の検証。経路の候補と採用決定を混同しない。
5. **作業状態**：工程、依存関係、完了条件、証拠、未完了事項、次の一手。現在状態は `docs/現在状態.json` の `work_items` を正本とする。

## 3. 共通ライフサイクル

各工程は「作業した」だけでは完了にせず、成果物・検証証拠・完了条件で判定する。

1. **経験を収集する**：実際の対話・試行・失敗・結果を残す。推測を事実として記録しない。
2. **知識化する**：再利用可能な手順・判断基準・注意点へ変換し、適用条件と限界を記す。
3. **企画する**：対象読者・基本方針などの既決事項を参照し、読者が実現したいこと・満たしたい欲求、提供価値、対象範囲、成功判定を定義する。困りごとの解決は提供価値の一つとして扱い、すべての企画の出発点と決めつけない。
4. **仕様を設計する**：目次、手順、必要な素材、成果物、テスト、完了条件、公開形態の候補を定義する。
5. **本文・素材を制作する**：章や成果物単位で進め、根拠と未検証事項を残す。
6. **実地検証する**：想定した環境で手順を実行し、再現性、失敗、制約、必要な修正を記録する。
7. **無料公開する**：GitHub Pagesを本拠地とし、公開物の実表示・リンク・手順を確認する。保存済みと公開済みを区別する。
8. **反応を検証する**：記事閲覧や反応、問い合わせ、利用者の実行結果など、取得できる証拠を見て仮説を更新する。
9. **Noteで需要を検証する**：販売を決定済みとみなさず、無料記事・サンプル・告知・利用者反応等の検証方法を段階的に選ぶ。実際に販売・課金する場合は、その前にたかの明示的承認を得る。
10. **継続・改訂・中止を判断する**：証拠、制作・更新コスト、利用者の反応を踏まえて次の投資を判断する。需要が確認できる前に大規模開発や有料サービスへの投資を前提にしない。
11. **保守する**：仕様変更、リンク切れ、利用環境の変化、誤りの発見を記録し、影響範囲を確認して更新する。

## 4. 工程ゲート（次工程へ進む条件）

- **企画 → 仕様**：既決事項を再検討していない。読者が実現したいこと・満たしたい欲求、提供価値、対象範囲、成功判定が記述されている。困りごとを起点とする場合は、その根拠がある。
- **仕様 → 制作**：章・手順・必要素材・テスト・完了条件がある。
- **制作 → 実地検証**：検証対象となる具体的な成果物があり、未完成箇所が明示されている。
- **実地検証 → 無料公開**：実行結果、失敗、限界、未検証箇所を誇張なく記載し、公開対象を確認している。
- **無料公開 → Note需要検証**：公開物が実際に見られる状態で、検証したい仮説・観測方法・判断基準が定義されている。
- **需要検証 → 販売判断**：反応や購入意向の証拠をまとめ、制作・更新コストも評価している。証拠不足なら未決のまま継続または保留する。
- **販売・配布 → 保守**：更新責任、問い合わせ・修正の扱い、既知の制約が明記されている。

前工程が未完了の場合、次工程の準備や小規模試行はできるが、前工程を完了扱いにしてはならない。工程の例外的な順序変更は、理由・影響・承認を記録する。

## 5. 既決・未決の扱い

### 5-1. 制作形式・文体の決定

先行するセッティングマニュアルの制作形式・文体は、[制作形式・文体仕様](AI作業セッティングマニュアル_制作形式・文体仕様.md) を正本として決定済みとする。Markdown（`.md`）を原稿の正本とし、GitHub Pagesで無料公開する。文章・番号付き手順・具体例・コピー可能なコマンドやテンプレートを中心にし、Wordファイルや図・イラストは初版で原則作成しない。図や画像は文章だけでは説明が難しい場合に限り検討する。この仕様は、対象読者・無料前提と同様、チャット切替や工程進行を理由に再検討へ戻さない。

- 決定済み事項は、チャット切替、作業項目の再編、別AIの提案を理由に未決へ戻さない。
- 変更が必要な場合は、変更理由、影響する資料・制作物・作業項目を示し、たかの明示的承認を得てから変更する。
- 未決事項は論点ごとに管理し、既決事項と混ぜない。未決であることを理由に作業全体を止めず、依存しない工程を進める。
- 「決定」「実装」「検証」「公開」「需要確認」「販売開始」は別の状態として扱う。
- AIが作った案・草稿・レビュー指摘は、採用・検証・承認が済むまで確定情報としない。

## 6. マニュアル群のポートフォリオ

現在の構想では、以下を一つの知識活用の流れとして管理する。各冊の詳細仕様や有料化は別途検証し、未決のまま扱う。

- **セッティングマニュアル**：AI作業を始める環境と運用ルールを整える。先行制作対象。
- **運用マニュアル**：実際の作業を継続し、状態・判断・引き継ぎを管理する方法を扱う。
- **公開マニュアル**：経験・成果を整理し、他者に公開するまでを扱う。
- **経験ノウハウ集**：実際の経験と検証結果を蓄積し、各マニュアルの根拠・事例として再利用する。
- **運用キット／トラブル解決キット**：実践と検証で裏付けられた部分から将来候補として検討する。

冊子ごとに独立した重複ルールを増やすのではなく、共通ライフサイクルとゲートを共有し、固有の差分だけを個別仕様として持つ。

## 7. GitHubでの管理契約

- `docs/現在状態.json` の `work_items` を作業キューの正本とし、`next_step` はそこから導出される互換ビューとして扱う。
- 大きな企画は、全体の目的と段階を追える継続用work itemを保持し、個々の工程完了でプロジェクト全体を削除しない。
- `progress.steps` は工程ごとに `pending` / `in_progress` / `waiting_external` / `done` を持ち、完了根拠を記録する。
- 作業項目には、対象、前提・依存関係、完了条件、証拠、未決事項、現在工程、次の一手を含める。大きな工程は成果物単位へ分解する。
- 正本の更新と生成ビュー（`BUD.md`、`docs/引き継ぎ/現在の引き継ぎ.md`）の同期を同じ変更単位で行い、CIで整合を検証する。
- 作業終了時は、決定・変更・保留・未完了・未確認・未解決・次の一手を確認し、正本・企画資料・生成ビューの矛盾を残さない。
- 状態を変更した場合、実際のGitHub反映・CI検証・必要な実環境確認を別々に記録する。

## 8. 先行マニュアルに適用する当面の流れ

1. 章別設計の完了を保持する。
2. 決定済み対象読者・無料前提を読み込み、再決定工程を閉じる。
3. 初版の目的・提供範囲・完成条件を、読者が実現したいこととマニュアル群内での役割に沿って定義する。既存の7章構成と、ChatGPTチャットをMarkdownで保存するブラウザー拡張機能の選択肢を照合する。
4. 初版の完成条件はマニュアル成果物と読者が実際にできることに限定し、公開後の運用・反応観測・需要検証は別工程に分ける。
5. 初版の範囲確定後に本文を作成し、章別の手順・成果物・テストを実地検証する。
6. 効果と限界を明記し、GitHub Pagesで無料公開できる範囲を整える。
7. 公開・表示確認後、無料サンプルや記事を使って反応を検証する。
8. Noteでの需要検証方法を設計する。販売・価格・正式仕様・開始時期は、証拠と明示的判断がそろうまで未決のまま保持する。

## 9. 完了判定

この管理方式の導入完了は、設計書を追加しただけでは宣言しない。少なくとも、(a) 正本と運用ルールが相互参照されている、(b) 先行マニュアルのwork itemと工程状態が実態に一致する、(c) 生成ビューが一致する、(d) CIが通る、(e) 次回再開時に既決事項と現在工程から再開できる、を確認して判定する。
