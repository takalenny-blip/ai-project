これはテスト。

そして、

「AIと一緒なら、こんな自動化の仕組みを本当に作れるのか？」

そこを試してみたかった。

## 今度はWi-Fi

Debianが起動した。

次はネットワークだ。

ところが、今度はWi-Fiにつながらない。

「え？また？まじかよー」

フロントのワイヤレスランプもつかない。

「なんでランプつかないんだー」

またバドに相談する。

まず状態を確認する。

```
rfkill list
```

次にネットワークインターフェースを見る。

```
ip link
```

NetworkManagerも入れて、

```
sudo nmtui
```

を開いてみる。

でも、Wi-Fiが見えない。

有線でつないでみようかと思っても、このVAIO PにはLANの口がない。

ここでも、また一つずつ試していく。

iPhoneのUSBテザリングも使いながら、必要なものを入れていく。

調べていくと、どうも無線LANそのものが壊れているわけではなさそうだった。

最終的には、/etc/network/interfaces に残っていた無線LANの設定がNetworkManagerの管理を邪魔していた。

そこを修正して、NetworkManagerを再起動する。

```
sudo systemctl restart NetworkManager
```

すると、

おお、ついた！

ワイヤレスランプが点いた。

Wi-Fiも見えるようになった。

最後に、

```
ping -c 3 8.8.8.8
```

で確認。

「オケ」

つながった。

## DIGA／DiMORAを使った自動化テスト

VAIO Pをサーバーにする話とは別に、以前からDIGAの録画管理についてClaudeといろいろ試していた。

このころは、まだ自動化しようなんて考えていなかった。

スプレッドシートとGASを使って、DIGA 3台の予約情報を管理する仕組みを作っていた。

最初にClaudeに投げたのは、こんな相談だった。

> 「Diga3台の予約情報を見て、録画の管理データベースを作りたい。ネットからもってくる一例はこちら。データは機種ごとにグーグルドライブ内のグーグルドキュメントに貼り付けようと思う。日時変更など警告メールを出すようにしてほしい。また、次回の予約がないよ、とか。現在の録画話数の自動更新もほしい。シリーズ終了の連絡もほしい。今までの録画志向から、番組おすすめもほしい。あと他に提案とか質問とかある？」

Claudeと相談しながら、貼り付けたDIGAの情報を使って、予約の変化をチェックする仕組みを作っていった。

お気に入り番組についても、最初はDiMORAからコピーした内容をGoogleドキュメントの機種毎ファイルに必ず貼り付け、それを「その時点のお気に入り」として扱う方式だった。

ところが、実際に使っていると、手を抜きたくなる。

たとえば、お気に入りが変わった場合だけGoogleドキュメントに貼り付け、変更が無い場合は貼り付けない。

そこでClaudeに対して、

> 「待って。お気に入りの中身が空の場合は、内部で持ったお気に入り情報で進める。中身があるときだけ、お気に入りの加除チェックをする。これは機種ごとに制御したい。（例えば、diga1,2のお気に入りは空だったから加除チェックは走らない。diga3に入ってるから加除チェックを走らす。）内部情報でお気に入りに機種情報も加える必要あり。」

と仕様を修正した。

Claudeとのやりとりは、作って終わりではない。

実際にメールを受け取ってみると、今度は表示内容が気になった。

> 「これは、今日のチェック結果メール。内容はいいんだけど、いつの放送分なのか、日時と曜日を加えてほしい。」

修正してもらう。

すると今度は、

> 「ゴメン。あとチャンネルも必須。可能であれば機種も。」

となった。

こうやって、

「作る」
↓
「実際に使う」
↓
「気になる」
↓
「AIに伝える」
↓
「直す」

を繰り返していた。

DIGAの録画管理は、少しずつ自分が欲しい形になっていった。

ただし、一つだけ面倒なことが残っていた。

**毎回、DiMORAの画面をコピーして貼り付けること。**

ここは単純に面倒だった。

この時点では、DIGAの自動化を考えていたわけではない。

そんな中で、別のところから「ブラウザを使って情報を取得する」という発想を知った。

Claudeのブラウザ連携を知り、それをきっかけにGeminiにも聞いてみた。

Pythonでブラウザから情報を取得する。

それを知ったとき、急につながった。

「あ、これDIGAでも使えるかも」

そう思った。

コピペしなくて済む。

**うまくしたらラクになるぞー。**

でも、すぐに次の疑問が出てきた。

**DiMORAからうまく情報とれるの？**

そこで、AIから指示をもらいながら、実際のDiMORAのページを調べ始めた。

まず目を付けたのが、お気に入り番組一覧の「もっと見る」だった。

画面には番組が並んでいて、さらに先を見るための「もっと見る」がある。

「次の10件」がどうやって表示されているのか。

ここを追えば、DiMORAがどこから番組情報を持ってきているのか分かるかもしれない。

そこで、実際のHTMLを調べ、さらにJavaScriptまで追っていった。

すると、「もっと見る」は単純に次の10件をサーバーから取り直しているわけではなかった。

`favoriteProgram-14.6.0.js`

の処理を追うと、`FavoriteProgramController.prototype.addFavPgm()` が呼ばれ、その中で、

`GL_FAVPGM_DATA.record`

というデータが使われていた。

つまり、ページにはお気に入り番組の情報がすでに入っている。

「もっと見る」は、そのデータを10件ずつ表示していた。

ここが分かった瞬間だった。

実際にお気に入り番組の情報を取得してみる。

そして、

**「おお、取れた！」**

画面からコピーして貼り付けなくても、DiMORAの中にあるお気に入り番組のデータを直接扱える可能性が見えてきた。

しかも、そのデータには、番組の日付や時間、放送局、タイトル、録画モード、曜日、番組URLなど、録画管理に使えそうな情報が入っている。

ここまで来ると、最初に作ったGASの仕組みと、まったく別の道がつながってくる。

これまで、

DiMORAを開く  
↓  
お気に入りをコピーする  
↓  
Googleドキュメントに貼る  
↓  
GASでチェックする

だったものが、

DiMORA  
↓  
ブラウザから情報を取得  
↓  
必要なデータを取り出す  
↓  
保存・比較する

という形にできそうだった。

ただし、この時点で「VAIO Pですべて自動化できた」わけではない。

まず別のPCでDiMORAのHTMLとJavaScriptを調べ、どこにデータがあるのかを突き止めた段階だった。

次に必要なのは、ログインしたDiMORAのページからそのデータを安全に読み出し、それをVAIO P上のPythonで扱えるようにすること。

最初はただ「コピペが面倒だな」と思っていただけだった。

それが、Claude、Gemini、Python、ブラウザ、DiMORAと話をつないでいくうちに、いつの間にかWebページの中身まで掘ることになっていた。
