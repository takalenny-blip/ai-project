# そういえば、VAIO Pがあった

## VAIO Pをサーバーに、という流れになった経緯

BLOG-0001では、AIとのやりとりから「ブログを作ってみよう」と思ったところまでを書いた。

そういえば、家にVAIO Pがあった。以前はサーバーとして使っていたが、いつの間にか使わなくなっていた。

せっかくあるのだから、もう一度何かに使えないだろうか。

最初に考えていたのは、AIとのやりとりでブログ記事を作り、それをBloggerなどにアップロードする仕組みだった。

最初のChatGPTへの相談は、こうだった。

「AIとのやりとりで手軽にブログ記事を作成し、それを無料のワードプレスやブロガーなどにアップロードする仕組みを作りたい。何かよい方法はあるか？」

この時点では、AIに記事を書いてもらい、自分が確認して公開する。その一連の作業を、自宅のPCなどからできるようにする、というイメージだった。

その方法を考えていく中で、LinuxやPython、Blogger APIなどの話が出てきた。そこで、以前サーバーとして使っていたVAIO Pを、もう一度使ってみたらどうかと考えた。

「使えるかな？」

「お、いけるかも」

そんな感じで、VAIO Pをもう一度サーバーとして使ってみることになった。

そこで、次に気になったのがストレージだった。

「vaiopのssd換装だけど、前にlarkboxというミニpcで使ったssdならあるんだけど、再利用可能かな？」

LarkBoxで使っていたSSDをVAIO Pに移せるのか。

せっかくならSSDに換装して、VAIO Pを少しでも快適にできないかと考えた。

ただ、実際に確認していくと、SSD換装には失敗する可能性もある。そこで、最初からSSD換装に賭けるのではなく、まずは現在のHDDを使ってDebianを入れ、動かしてみることにした。

「動くかどうか試したい」

VAIO PにDebianを入れて、実際に使えるところまで持っていけるのか。

まずは、そこから始めることにした。

## Debianを入れて、VAIO Pを動かしていく

いよいよVAIO Pを実際に動かしてみる。

使っているのはVGN-P70H/W。Atom Z520の32bit機なので、Debianもi386版を選ぶことになった。

ここからは、母艦PCでDebianのインストールメディアを作り、VAIO Pにインストールしていく。

このとき、JUNから「写真で残したら？」というアドバイスもあった。

そこで、たかはこう返している。

「写真で残したら？のアドバイスもよろしく！母艦PCはある。debianのダウンロードからだね。ここから一緒にやろうぜ！」

ただ、単に作業の写真を残すだけではなく、その経験そのものをあとから記事にできないか、ということも考えていた。

まずはDebianをダウンロードする。

「今、Debianダウンロード中」

ダウンロードしたのは、Debian 12.12.0のi386版netinstイメージ。

次にRufusを使って、USBメモリに書き込む。

画面を見ながら進めていると、AIが一度、Windowsの通常のフォーマット画面だと勘違いした。

「ん？rufasだよ」

AIもすぐに勘違いを認めた。

Rufusの画面には、ボリュームラベルとして「Debian 12.12.0 i386 n」と表示されていた。

USBメディアができた。

いよいよVAIO Pを起動する。

ところが、ここで最初のトラブル。

「何だろ？電源入らん」

電源が入らない。

充電ランプを見ると赤点滅している。

古いVAIOなので、バッテリーの状態も気になる。

そこで、バッテリーを外してACアダプターだけで起動してみることになった。

「バッテリー外したら起動。」

さっきまで電源が入らなかったVAIO Pが起動した。

しかも、USBからDebianのインストーラーまで立ち上がった。

いきなり「古いPCだから壊れているのか？」と思ったが、実際にはバッテリーを外すことで先へ進めた。

ここからDebianのインストールが始まる。

言語やキーボード、ネットワークなどを、画面に従って設定していく。

途中で、VAIO Pの無線LANも認識された。

インストール先のストレージについては、以前のSSD換装の話があったため、ここでも確認が必要だった。

実際には、SSD換装は見送り、今回は元のHDDにDebianを入れることにした。

ところが、ここでAIが以前の状況を取り違えた。

JUNが、VAIO PにはKingdataの64GB SSDが入っているという前提で話し始めた。

そこで、たかが訂正する。

「換装は見送り、HDDにインストールする方針にしたんだぜ？SSDは外付けで活用しようかって話したじゃん」

この場面は、単なるインストール手順では終わらなかった。

AIと一緒に作業していると、以前の会話を正確に引き継げているとは限らない。

だから、実際の作業をしている人間が「今どうなっているか」を確認しながら進める必要がある。

今回は、その訂正をして、元のHDDへのインストールを続けた。

「今はベースシステムのインストール中」

あとは待つしかない。

HDDなので、とにかく時間がかかる。

「ソフトウェアの選択とインストール、5%」

少しずつ数字が進む。

「今はソフトウェアの選択とインストール、50%」

途中で、インストールそのものだけでなく、この先の最終的なゴールについても気になってきた。

「それってインストールでしょ？そうじゃなくて、最終ゴールまでの。」

Debianを入れること自体が目的ではない。

VAIO Pをサーバーとして使い、その先でブログや自動化につなげていきたい。

そのための最初の一歩が、今やっているDebianのインストールである。

インストールはさらに進んでいく。

57%。

94%。

そしてGRUBの設定。

「インストールを終了しています」が25%まで進んだところで、ようやく終わりが見えてきた。

長かった。

そして、ついにインストールが完了した。

再起動する。

ここまで来ても、本当にHDDからDebianが起動するのかはまだ分からない。

そして、「うまく起動したぜ！」

VAIO Pが起動した。

デスクトップにはLXDEが表示された。

「LXDEシンプルでいいな！」

古いVAIO Pに、DebianとLXDEが動いている。

まずは成功だ。

ただ、ここで終わりではなかった。

次に確認したかったのは、ネットワークだった。

ところが、Wi-Fiが使えない。

「Wi-Fiない？」

無線LANが見えない。

ここからは、画面を見ながらコマンドを一つずつ試していく。

まず、ネットワークインターフェースを確認する。

    rfkill list

続いて、

    ip link

ネットワーク管理にはNetworkManagerを使うことにして、

    sudo nmtui

を起動する。

しかし、Wi-Fiが出てこない。

「見えねー」

そこで、NetworkManagerの状態を確認する。

    nmcli device

すると、無線LANインターフェース wlp2s0 が「unmanaged」、つまり「管理なし」になっていた。

たか：

「管理なし」

ここから原因を切り分ける。

まずNetworkManagerに管理させてみる。

    sudo nmcli device set wlp2s0 managed yes

それでも変わらない。

そこで、設定ファイルを確認する。

    cat /etc/network/interfaces

すると、wlp2s0 に関する設定が残っていることが分かった。

NetworkManagerと、以前のネットワーク設定がぶつかっているらしい。

そこで、無線LAN関連の設定をコメントアウトする。

    sudo sed -i '/wlp2s0/s/^/#/' /etc/network/interfaces

    sudo sed -i '/wpa-ssid/s/^/#/' /etc/network/interfaces

    sudo sed -i '/wpa-psk/s/^/#/' /etc/network/interfaces

続いてNetworkManagerを再起動。

    sudo systemctl restart NetworkManager

そして、もう一度確認する。

    nmcli device

今度は wlp2s0 が「管理なし」ではなく、「切断済み」に変わった。

少なくとも、NetworkManagerが無線LANを管理できる状態になった。

そして、

    sudo nmtui

を起動する。

今度はWi-FiのSSIDが表示された。

「出たーーー」

ここからWi-Fiを選択して、接続する。

接続後、iPhoneのUSBテザリングを外して、Wi-Fiだけで本当にインターネットにつながっているか確認する。

    ping -c 3 8.8.8.8

そして、

「繋がった。画面はとじていいの？」

画面を閉じて、最後に確認する。

「オケ」

これで、Wi-Fiも復旧した。

ここまで来ると、VAIO Pが少しずつ「使える機械」になってきた。

ただ、実際に使ってみると、また問題が出てきた。

そこで、Firefoxを起動する。

「firefoxは変わらず重い。。。」

Debianは起動した。

LXDEも動いた。

Wi-Fiもつながった。

でも、Firefoxは重い。

そこで、次は軽量なブラウザを探すことになった。

こうしてVAIO Pは、

**電源が入らない → バッテリーを外す → Debianを入れる → Wi-Fiが見えない → コマンドで原因を切り分ける → NetworkManagerで復旧 → Firefoxが重い**

という具合に、一つ問題を解決すると、また次の問題が出てくる。

それでも、最初に「VAIO Pをサーバーにしてみたい」と考えたところから、かなり前に進んだ。

そして、この一連の作業をAIとの会話と一緒に記録していくことが、あとになって重要な意味を持つ。

## DIGA／DiMORAを使った自動化テスト

VAIO Pを動かしていく一方で、以前からDIGAの録画管理についてもClaudeと試していた。

このころは、まだ自動化まで考えていなかった。

スプレッドシートとGASを使って、DIGA 3台の予約情報を管理していた。

最初にClaudeに相談したのは、こんな内容だった。

> 「Diga3台の予約情報を見て、録画の管理データベースを作りたい。ネットからもってくる一例はこちら。データは機種ごとにグーグルドライブ内のグーグルドキュメントに貼り付けようと思う。日時変更など警告メールを出すようにしてほしい。また、次回の予約がないよ、とか。現在の録画話数の自動更新もほしい。シリーズ終了の連絡もほしい。今までの録画志向から、番組おすすめもほしい。あと他に提案とか質問とかある？」

Claudeと相談しながら、貼り付けたDIGAの情報を使って、予約の変化をチェックしていった。

お気に入り番組についても、最初はDiMORAからコピーした内容を、機種ごとのGoogleドキュメントに必ず貼り付け、それを「その時点のお気に入り」として扱っていた。

ところが、実際に使っていると、もっと手間を減らしたくなってきた。

たとえば、お気に入りが変わった場合だけGoogleドキュメントに貼り付け、変更がない場合は貼り付けないようにした。

そこでClaudeに、仕様を修正してもらった。

> 「待って。お気に入りの中身が空の場合は、内部で持ったお気に入り情報で進める。中身があるときだけ、お気に入りの加除チェックをする。これは機種ごとに制御したい。（例えば、diga1,2のお気に入りは空だったから加除チェックは走らない。diga3に入ってるから加除チェックを走らす。）内部情報でお気に入りに機種情報も加える必要あり。」

さらに、実際にチェック結果のメールを見ると、別のところも気になった。

> 「これは、今日のチェック結果メール。内容はいいんだけど、いつの放送分なのか、日時と曜日を加えてほしい。」

Claudeに修正してもらった。

すると次に、

> 「ゴメン。あとチャンネルも必須。可能であれば機種も。」

となった。

こうやって、作って、使って、気になったところを直していった。

DIGAの録画管理は、少しずつ自分が使いやすい形になっていった。

ただ、一つだけ面倒なことが残っていた。

**毎回、DiMORAの画面をコピーして貼り付けること。**

ここが単純に面倒だった。

この時点では、まだDIGAの自動化を考えていたわけではない。

そんな中で、別のところから「ブラウザを使って情報を取得する」という発想を知ることになった。

Claudeのブラウザ連携を知ったことをきっかけに、Geminiにも聞いてみた。

Pythonでブラウザから情報を取得できる。

それを知ったとき、DIGAのことと急につながった。

「あ、これDIGAでも使えるかも」

そう思った。

これなら、コピペしなくて済む。

**うまくしたらラクになるぞー。**

でも、すぐに次の疑問が出てきた。

**DiMORAからうまく情報とれるの？**

そこで、AIと一緒にDiMORAの画面を調べることにした。

まず目を付けたのは、お気に入り番組一覧の「もっと見る」だった。

画面には番組が並んでいて、さらに先を見るための「もっと見る」が表示されている。

「次の10件」がどうやって表示されているのかを調べる。

ここを追えば、DiMORAがどこから番組情報を持ってきているのか分かるかもしれない。

AIから指示をもらいながら、実際のHTMLを確認していった。

すると、ページの中に、

`favoriteProgram-14.6.0.js`

というJavaScriptが読み込まれていることが分かった。

「このJavaScriptを見てみよう」

そんな具合に、一つ分かると、次を調べる。

その中で、「もっと見る」の処理を追っていくと、

`FavoriteProgramController.prototype.addFavPgm()`

が出てきた。

さらに追っていく。

すると、その処理が参照していたのは、

`GL_FAVPGM_DATA.record`

だった。

ここで、だんだん仕組みが見えてきた。

「もっと見る」を押したから、次の10件を新しくサーバーから取りに行っているのではない。

ページには、すでにお気に入り番組のデータが入っている。

「もっと見る」は、そのデータを10件ずつ表示している。

そこでAIから、ページ内に持っているデータを実際に確認する方法を教えてもらい、実行してみる。

結果をAIに返してみる。

AIがまた「ここを見てみよう」と指示してくる。

そんなやりとりを何度か繰り返して、ようやくお気に入り番組のデータが見えてきた。

そして、

**「おお、取れた！」**

実際に、DiMORAのお気に入り番組の情報を取得できた。

そこには、番組の日付や時間、放送局、タイトル、録画モード、曜日、番組URLなど、録画管理に使えそうな情報が入っている。

ここで初めて、「コピペしなくてもいけるかもしれない」ということを、実際のデータを見て確認できた。

最初に作ったGASの仕組みは、

DiMORAを開く

↓

お気に入りをコピーする

↓

Googleドキュメントに貼る

↓

GASでチェックする

だった。

それが今度は、こう変わり始めた。

DiMORA

↓

ブラウザから情報を取得

↓

必要なデータを取り出す

↓

保存・比較する

という形に変わり始めた。

ただ、この時点では「VAIO Pですべて自動化できた」わけではない。

まず別のPCでDiMORAのHTMLとJavaScriptを調べ、AIの指示を受けながらページ内部のデータを追いかけ、実際にお気に入り番組の情報を取得するところまで来た。

次に必要なのは、ログインしたDiMORAのページからそのデータを安全に読み出し、VAIO P上のPythonで扱えるようにすることだった。

最初はただ、「コピペが面倒だな」と思っていただけだった。

それが、Claude、Gemini、Python、ブラウザ、DiMORAと話をつないでいくうちに、いつの間にかWebページの中身まで掘ることになった。
