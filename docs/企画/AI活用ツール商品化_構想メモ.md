# AI活用ツールの商品化構想メモ

- 検討日：2026-10-13
- 状態：構想段階
- 需要検証：未実施
- 販売・開発の決定：未決定
- 現時点の進め方：セッティングマニュアルを先行し、経験ノウハウを別の知識資産として蓄積する

## 1. 方向性

AIとの実作業や試行錯誤から得た経験を、記事として発信するだけでなく、他の人が困りごとを解決するために使えるマニュアル、テンプレート、手順キットへ変換し、商品化できる可能性を探る。

中心に置くのは、AIに文章を大量生成させることではなく、実際の作業で問題に遭遇し、方法を試し、失敗や改善も記録してきた経験である。

商品化は、完成した制御手法が既にあるかのように売り出すのではなく、現在わかっていること・実際に試したこと・まだ解決できていないことを区別して進める。特にAIの迷走・暴走は現在も完全には制御できていないため、「完全に防げる」と約束しない。

## 2. 商品と知識資産の構成

### 2.1 先行候補：AI作業のセッティングマニュアル

最初に形にする候補。AIとの長期作業を始めるときに、役割、目的、作業範囲、情報の正本、承認、状態管理、開始・終了手順などをどう設定するかを説明する。

想定する内容：
- AIに役割・目的・作業範囲・完了条件を伝える
- 実行前の承認ポイントと、AIが独断で実行してはいけない範囲を定める
- 事実・提案・未確認事項を区別する
- 正本、作業キュー、決定・保留・未完了事項をどこに記録するか決める
- 作業開始時に現在状態を読み、完了済み工程を繰り返さず再開する
- 作業終了時に実績・決定・変更・保留・未完了・未確認・次回事項を整理する
- 設定が実際に守られるかを小さく確認し、守られなかった場合も記録する
- 設定だけで防げない問題や、この方法の限界を明記する

提供形態の案：導入ガイド、設定テンプレート、チェックリスト、動作確認用のテスト例。

位置づけ：AIを完全に制御する保証ではなく、作業環境と運用ルールを整え、確認・記録・引き継ぎを再現可能にするためのマニュアル。

### 2.2 別の知識資産：AI活用の経験ノウハウ集

セッティングマニュアルとは分けて、実際に使った経験から得られた知見を蓄積する。これは単独の商品と決めず、記事、無料サンプル、後続商品の根拠にも使う。

想定する内容：
- 実際の対話・試行錯誤・成功・失敗
- 起きた事実と原因についての仮説の区別
- 何を試し、何が変わり、何が未解決のままか
- 判断理由と、次回も使える知見
- 経験から手順書・チェックリスト・テンプレートへ変換した例

### 2.3 将来候補：AI作業の運用キット

目的・完了条件・承認・事実と提案の分離・未完了管理・引き継ぎなどを支えるテンプレート一式。セッティングマニュアルと経験ノウハウを実運用で検証し、効果と限界がわかった部分から整える。

現在も迷走・暴走が起きており、完全な制御はできていない。したがって、現時点で「暴走を防げる完成品」として販売するのではなく、マニュアルの実践と検証を通じて育てる後続候補とする。

### 2.4 将来候補：AIトラブル解決キット

AI作業で問題が起きたときに、症状・原因候補・確認結果・対処・結果を整理し、次回の切り分けに再利用するための診断シートや手順。

実体験の記録を増やし、どの問題をどこまで再現・解決できるかを確かめたうえで、範囲を絞って検討する。

### 2.5 経験管理と手順化は、当面は一つの流れとして扱う

以前の候補「AI × GitHub 経験管理キット」と「試行錯誤を再利用可能な手順に変えるキット」は、別商品として細かく分けず、当面は一つの知識活用の流れとして扱う。

1. AIとの対話や試行錯誤を経験として残す。
2. 事実・判断・失敗・結果を整理する。
3. GitHub等で正本・履歴・未解決事項を管理する。
4. 再利用できる手順書・チェックリスト・テンプレートへ変換する。
5. 次の作業で使い、結果に応じて改善する。

この流れは経験ノウハウ集と後続商品の基盤とする。独立した有料商品にするかどうかは、利用者の反応を見て判断する。

## 3. 先行マニュアルの基本方針

最初の制作対象は「AI作業のセッティングマニュアル」とする方向で進める。ただし、正式な商品仕様・販売形態・価格が確定したわけではない。

マニュアルでは、たか自身が実際に運用している方法を具体例にしつつ、GitHub固有の設定と、他の環境でも応用できる考え方を区別する。

マニュアルの完成条件候補：
- 読者が導入前に必要な準備を把握できる
- 設定項目とその目的が説明されている
- 導入手順を順番に実行できる
- 設定後の動作確認方法がある
- 指示が守られない場合の記録・停止・再開方法がある
- できること、できないこと、未検証の点が明記されている
- 実際の使用例と失敗例を区別して掲載する

## 4. 商品化の進め方

1. 先行マニュアルの対象読者と、最初に解決する困りごとを絞る。
2. 目次と最小限の導入手順を作る。
3. たか自身の運用で各項目を確認し、効果と限界を記録する。
4. 無料で読める記事やサンプルを通じて、読者がどこに関心を持つか確かめる。
5. 経験ノウハウを並行して蓄積し、実証できた内容をマニュアルに反映する。
6. 反応と検証結果を見て、運用キットやトラブル解決キットの優先順位を決める。
7. 需要が確認できるまでは、大規模開発や有料サービスへの投資を急がない。

## 5. 発信・販売経路の位置づけ（仮説）

- **GitHub Pages**：経験の蓄積、無料の説明記事、実例、ツールの案内を置く本拠地として維持する。
- **note**：テンプレートや実用キットなどの有料販売を試す候補。記事や商品が実際に購入されるかは未検証。
- **独自ドメイン・Google AdSense**：GitHub Pagesで読者の反応が見えた後に検討する選択肢。ドメイン取得や申請を現時点で決定したわけではない。
- **はてなブログ、YouTube、Instagram等**：現時点では優先経路として決定せず、必要性を見て再検討する。

## 6. 検証すべきこと

- 誰が、どのような状況で困っているのか。
- セッティングマニュアルを読めば、読者は実際に設定を完了できるか。
- 設定によって何が改善し、どの問題は改善しないのか。
- 無料サンプルや記事のどこに反応があるか。
- 利用者はテンプレート、手順書、リポジトリひな型のどれを求めるのか。
- 有料で購入する意思があるか。
- 作成・サポート・更新にかかる手間に見合うか。

## 7. 現時点の決定と未決定

### 今回採用する進め方
- 最初に出す候補を「AI作業のセッティングマニュアル」とする。
- AI活用の経験ノウハウ集は、マニュアルとは分けて蓄積する。
- 経験管理と手順化は、当面は別商品にせず、経験を再利用可能な知見に変える一つの流れとして扱う。
- AI作業の運用キットとAIトラブル解決キットは、実践・検証を重ねた後の発展候補とする。
- AIの迷走・暴走を完全に防げると約束せず、実証済みの内容と未解決の限界を明示する。
- GitHub Pagesを本拠地とする発信方針と、需要検証前に大規模投資を急がない方針を維持する。

### 未決定・未確認
- 想定する読者をどこまで絞るか
- マニュアルの正式名称・目次・完成仕様
- 無料公開範囲と有料部分の境界
- 価格と販売形式、note等での販売開始時期
- 独自ドメインやGoogle AdSenseの導入
- 実際の需要・購入率・収益性
- 運用キットとトラブル解決キットの具体的な仕様・提供時期

## 8. マニュアルに盛り込む実体験：AIの使い分けと利用制限

この節は一般的なAI比較やネット上の節約術を集めるものではない。たか自身が実際に使って経験したことだけを記録し、未経験の方法で穴埋めしない。サービスの仕様一般ではなく、本人の利用環境での経験・評価として扱う。

### 8.1 ChatGPT：画像を極力貼らず、テキストでやりとりする

たかの経験では、ChatGPTには画像利用の制限がある。そのため、画像の貼り付けを極力避け、可能な場面では画面や資料の内容をドラッグしてコピーし、テキストでやりとりする。画像そのものを確認する必要がある場合と、テキストで代替できる場合を分ける。

### 8.2 Gemini：Claudeが使えないときに頼る、期待しすぎないレビューアー

Claudeが利用できないとき、Geminiにダメ元でレビューを頼る。ただし、たかの経験ではGitHubへのアクセスがほぼできず、イエスマンになりがちで、レビューの結果にあまり期待できない。指摘がないことを、内容が正しいことの証明として扱わない。渡した資料やアクセス可能な範囲に制約がある場合は、その制約を踏まえて評価する。

### 8.3 Claude：利用制限を意識し、最後の切り札として温存する

たかの経験ではClaudeは利用制限が特に厳しい。そのため、日常的に何でも頼むのではなく、どうしても困ったときに頼る最後の切り札として温存する。この使い方を「三枚のおふだ」のイメージとして表現する。「三枚のおふだ」は3つのAI全体の呼び名ではなく、Claudeを切り札として温存する考え方を指す。

### 8.4 掲載ルール

- ここに載せる利用制限対策は、たかが実際に経験したものに限る。
- 一般論、未経験の節約術、根拠を確かめていない回避策は追加しない。
- 経験上の評価と、サービス全体について確認された事実を混同しない。
- 利用制限や機能は変わり得るため、必要に応じて経験した時期・条件を添え、恒久的な仕様として断定しない。
- 「絶対に制限にかからない方法」とは表現せず、経験から得た使い分けとして紹介する。
