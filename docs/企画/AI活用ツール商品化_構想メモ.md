## 1. 方向性

AIとの実作業や試行錯誤から得た経験を、記事として発信するだけでなく、AIで何かを実現したい人が実際に始め、試行錯誤し、成果を積み上げるために使えるマニュアル、テンプレート、手順キットへ変換する。困りごとの解決は提供価値の一つとして扱い、読者の欲求を唯一の問題解決へ狭めない。

中心に置くのは、AIに文章を大量生成させることではなく、実際の作業で問題に遭遇し、方法を試し、失敗や改善も記録してきた経験である。

商品化は、完成した制御手法が既にあるかのように売り出すのではなく、現在わかっていること・実際に試したこと・まだ解決できていないことを区別して進める。特にAIの迷走・暴走は現在も完全には制御できていないため、「完全に防げる」と約束しない。

## 2. 商品と知識資産の構成

### 2.1 先行候補：AI作業のセッティングマニュアル

最初に形にする候補。AIとの長期作業を始めるときに、役割、目的、作業範囲、情報の正本、承認、状態管理、開始・終了手順などをどう設定するかを説明する。

想定する内容：
- AIに役割・目的・作業範囲・完了条件を伝える
- 実行前の承認ポイントと、AIが独断で実行してはいけない範囲を定める
- 事実・提案・未確認事項を区別する
- 正本、作業キュー、決定・保留・未完了事項をどこに記録するか決める
- 作業開始時に現在状態を読み、完了済み工程を繰り返さず再開する
- 作業終了時に実績・決定・変更・保留・未完了・未確認・次回事項を整理する
- 設定が実際に守られるかを小さく確認し、守られなかった場合も記録する
- 設定だけで防げない問題や、この方法の限界を明記する

提供形態の案：導入ガイド、設定テンプレート、チェックリスト、動作確認用のテスト例。

位置づけ：AIを完全に制御する保証ではなく、作業環境と運用ルールを整え、確認・記録・引き継ぎを再現可能にするためのマニュアル。

### 2.2 別の知識資産：AI活用の経験ノウハウ集

セッティングマニュアルとは分けて、実際に使った経験から得られた知見を蓄積する。これは単独の商品と決めず、記事、無料サンプル、後続商品の根拠にも使う。

想定する内容：
- 実際の対話・試行錯誤・成功・失敗
- 起きた事実と原因についての仮説の区別
- 何を試し、何が変わり、何が未解決のままか
- 判断理由と、次回も使える知見
- 経験から手順書・チェックリスト・テンプレートへ変換した例

### 2.3 将来候補：AI作業の運用キット

目的・完了条件・承認・事実と提案の分離・未完了管理・引き継ぎなどを支えるテンプレート一式。セッティングマニュアルと経験ノウハウを実運用で検証し、効果と限界がわかった部分から整える。

現在も迷走・暴走が起きており、完全な制御はできていない。したがって、現時点で「暴走を防げる完成品」として販売するのではなく、マニュアルの実践と検証を通じて育てる後続候補とする。

### 2.4 将来候補：AIトラブル解決キット

AI作業で問題が起きたときに、症状・原因候補・確認結果・対処・結果を整理し、次回の切り分けに再利用するための診断シートや手順。

実体験の記録を増やし、どの問題をどこまで再現・解決できるかを確かめたうえで、範囲を絞って検討する。

### 2.5 経験管理と手順化は、当面は一つの流れとして扱う

以前の候補「AI × GitHub 経験管理キット」と「試行錯誤を再利用可能な手順に変えるキット」は、別商品として細かく分けず、当面は一つの知識活用の流れとして扱う。

1. AIとの対話や試行錯誤を経験として残す。
2. 事実・判断・失敗・結果を整理する。
3. GitHub等で正本・履歴・未解決事項を管理する。
4. 再利用できる手順書・チェックリスト・テンプレートへ変換する。
5. 次の作業で使い、結果に応じて改善する。

この流れは経験ノウハウ集と後続商品の基盤とする。独立した有料商品にするかどうかは、利用者の反応を見て判断する。

## 3. 先行マニュアルの基本方針

最初の制作対象は「AI作業のセッティングマニュアル」とする方向で進める。ただし、正式な商品仕様・販売形態・価格が確定したわけではない。

マニュアルでは、たか自身が実際に運用している方法を具体例にしつつ、GitHub固有の設定と、他の環境でも応用できる考え方を区別する。

初版の目的・提供範囲・完成条件案は、[初版の目的・提供範囲案](AI作業セッティングマニュアル_初版目的・提供範囲案.md) を参照する。公開後の運用・反応観測・需要検証は、初版マニュアルそのものの完成条件と分けて管理する。

## 4. 商品化の進め方

対象読者・基本方針は [AI作業セッティングマニュアルの決定済み対象読者](AI作業セッティングマニュアル_決定済み対象読者.md) を正本とし、再検討しない。出発点は読者がAIで実現したいこと・広げたい可能性であり、具体的な困りごとはその実現過程で必要な場合に扱う。

1. 決定済み対象読者と、マニュアル群の中で先行マニュアルが担う段階を確認する。
2. 初版の目的・提供範囲・完成条件を整理する。詳細は [初版の目的・提供範囲案](AI作業セッティングマニュアル_初版目的・提供範囲案.md) を参照する。
3. 目次と手順に沿って本文を作成し、たか自身の運用で各項目を確認して効果と限界を記録する。
4. 無料で読める記事やサンプルを通じて、読者がどこに関心を持つか確かめる。
5. 経験ノウハウを並行して蓄積し、実証できた内容をマニュアルに反映する。
6. 反応と検証結果を見て、運用キットやトラブル解決キットの優先順位を決める。
7. 需要が確認できるまでは、大規模開発や有料サービスへの投資を急がない。

## 5. 発信・販売経路の位置づけ（仮説）

- **GitHub Pages**：経験の蓄積、無料の説明記事、実例、ツールの案内を置く本拠地として維持する。
- **note**：テンプレートや実用キットなどの有料販売を試す候補。記事や商品が実際に購入されるかは未検証。
- **独自ドメイン・Google AdSense**：GitHub Pagesで読者の反応が見えた後に検討する選択肢。ドメイン取得や申請を現時点で決定したわけではない。
- **はてなブログ、YouTube、Instagram等**：現時点では優先経路として決定せず、必要性を見て再検討する。

## 6. 検証すべきこと

- 読者はAIで何を実現したいのか、どのような可能性を試したいのか。
- どのような困りごとが実現の妨げになっているか（困りごとがある場合）。
- セッティングマニュアルを読めば、読者は実際に設定を完了できるか。
- 設定によって何が改善し、どの問題は改善しないのか。
- 無料サンプルや記事のどこに反応があるか。
- 利用者はテンプレート、手順書、リポジトリひな型のどれを求めるのか。
- 有料で購入する意思があるか。
- 作成・サポート・更新にかかる手間に見合うか。

## 8. マニュアルに盛り込む実体験：AIの使い分けと利用制限

この節は一般的なAI比較やネット上の節約術を集めるものではない。たか自身が実際に使って経験したことだけを記録し、未経験の方法で穴埋めしない。サービスの仕様一般ではなく、本人の利用環境での経験・評価として扱う。

### 8.1 ChatGPT：画像を極力貼らず、テキストでやりとりする

たかの経験では、ChatGPTには画像利用の制限がある。そのため、画像の貼り付けを極力避け、可能な場面では画面や資料の内容をドラッグしてコピーし、テキストでやりとりする。画像そのものを確認する必要がある場合と、テキストで代替できる場合を分ける。

### 8.2 Gemini：Claudeが使えないときに頼る、期待しすぎないレビューアー

Claudeが利用できないとき、Geminiにダメ元でレビューを頼る。ただし、たかの経験ではGitHubへのアクセスがほぼできず、イエスマンになりがちで、レビューの結果にあまり期待できない。指摘がないことを、内容が正しいことの証明として扱わない。渡した資料やアクセス可能な範囲に制約がある場合は、その制約を踏まえて評価する。

### 8.3 Claude：利用制限を意識し、最後の切り札として温存する

たかの経験ではClaudeは利用制限が特に厳しい。そのため、日常的に何でも頼むのではなく、どうしても困ったときに頼る最後の切り札として温存する。この使い方を「三枚のおふだ」のイメージとして表現する。「三枚のおふだ」は3つのAI全体の呼び名ではなく、Claudeを切り札として温存する考え方を指す。

### 8.4 掲載ルール

- ここに載せる利用制限対策は、たかが実際に経験したものに限る。
- 一般論、未経験の節約術、根拠を確かめていない回避策は追加しない。
- 経験上の評価と、サービス全体について確認された事実を混同しない。
- 利用制限や機能は変わり得るため、必要に応じて経験した時期・条件を添え、恒久的な仕様として断定しない。
- 「絶対に制限にかからない方法」とは表現せず、経験から得た使い分けとして紹介する。

## 9. 次の検討単位

先行する「AI作業のセッティングマニュアル」を中心に、3冊の役割分担を整理したうえで、各冊の目次・手順・完了条件を具体化する。まずはセッティングマニュアルを優先し、読者が環境を実際に準備して動作確認できる最小構成を作る。

## 10. 3冊のマニュアル構成と役割分担

3冊は独立した説明の寄せ集めではなく、環境準備から実践、成果公開までをつなぐ構成とする。正式名称・詳細仕様・価格・販売形態は未確定であり、需要検証前に確定事項として扱わない。

### 10.1 セッティングマニュアル（先行制作）

**目的：AIを使った作業を始められる環境を整える。**

想定目次：
1. セッティングの目的と全体像
2. AIの利用環境と基本ルール
3. GitHubの基本設定と記録管理
4. ChatGPTのチャットをMarkdown形式でダウンロードするブラウザ拡張機能
5. Dropboxの設定とファイル管理
6. 各ツールの役割分担と連携
7. 設定完了テスト

GitHubは記録・履歴・ファイル管理の手段として扱い、GitHub Pagesのサイト構築・公開設定をこの冊子の独立章にはしない。拡張機能は製品名を決め打ちせず、提供元・必要な権限・プライバシー上の注意を確認してから候補を選ぶ。DropboxはGitHubと同じ役割にせず、原本・作業ファイル・正本の置き場所を区別する。

**完了条件：** 読者が必要なツールを準備し、基本ルールに沿って記録・保管・引き継ぎを行えることをテストで確認できる。

### 10.2 運用マニュアル

**目的：AIを使って試行錯誤し、経験と結果を次の作業へつなげる。**

想定目次：
1. 課題・アイデアを整理する
2. AIに相談して進め方を決める
3. 小さく試して結果を確認する
4. 成功・失敗・判断理由を記録する
5. 経験から再利用できる手順を作る
6. 未解決事項と次の課題を管理する
7. 次の試行へつなげる

基本サイクルは「アイデア → AIに相談 → 小さく実験 → 結果・体験を記録 → 成果を公開 → 次の課題」とする。実際に確認した事実、原因についての仮説、未確認事項を混同しない。

**完了条件：** 読者が試行の目的・手順・結果・判断・次の課題を記録し、次回に再利用できること。

### 10.3 公開マニュアル

**目的：蓄積した経験や成果を、読者が利用できる形で公開する。**

想定目次：
1. 公開する成果を選ぶ
2. 読者と記事の目的を決める
3. 経験・根拠・未確認事項を整理する
4. 記事を構成して執筆する
5. 画像・引用・リンクを整える
6. GitHub Pagesを公開先として設定する
7. 記事を配置して公開する
8. 公開後の表示・リンク・SEOを確認する
9. 読者の反応を次の改善につなげる

GitHub Pagesは本番公開先として扱い、WordPressを本番公開先に戻さない。GitHubの基本操作はセッティングマニュアル、サイト構築・公開設定と記事公開手順は公開マニュアルで扱い、重複説明を避ける。

**完了条件：** 読者が成果を記事にまとめ、GitHub Pagesで公開し、公開後の表示・リンクなどを確認できること。

### 10.4 3冊の接続

1. セッティング：作業環境を使える状態にする。
2. 運用：AIを使って試行し、経験・結果を記録する。
3. 公開：経験から得た成果をGitHub Pagesで公開する。
4. 公開後の反応や新しい課題を、次の運用サイクルへ戻す。

各冊は単独でも使えるようにしつつ、連続して読むことで「環境準備 → 実践・記録 → 公開・改善」の流れが成立する構成を目指す。無料で始められる方法を優先し、無料枠の制限や未検証の点を隠さない。

### 10.5 先行制作：セッティングマニュアルの章別設計

以下は本文執筆前の作業設計である。読者が実際に操作できるよう、各章を「目的 → 前提 → 手順 → 期待結果 → 失敗時の確認 → 完了チェック」の順で書く。画面やサービスの仕様は執筆時点で再確認し、未確認の画面名・ボタン名を断定しない。

#### 第1章：セッティングの目的と全体像
- **手順：** 読者がAIで試したいこと・実現したいことを一つ選び、AI・GitHub・チャット記録・Dropboxそれぞれの役割を一覧で確認する。
- **成果物：** 自分の作業目的、使うツール、保存先を記入した「準備シート」。
- **確認テスト：** どの情報をどこに保存するか、読者自身の言葉で説明できる。

#### 第2章：AIの利用環境と基本ルール
- **手順：** 使用するAIへのログインと基本操作を確認し、AIの役割・目的・作業範囲・完了条件・承認が必要な操作を短い開始指示にまとめる。
- **成果物：** 再利用可能な「作業開始テンプレート」と、事実・提案・未確認事項を分ける記録ルール。
- **確認テスト：** AIに小さな作業を依頼し、依頼範囲と完了条件を応答から照合できる。AIの回答を無条件に正しいと扱わない注意点も説明できる。

#### 第3章：GitHubの基本設定と記録管理
- **手順：** GitHubアカウントと対象リポジトリを確認し、リポジトリ・ファイル・コミット・ブランチ・Pull Requestの役割を学ぶ。正本と生成ビューを区別し、変更は差分と検証結果を確認してからレビューへ出す。
- **成果物：** 作業対象リポジトリの記録、正本の場所、変更・レビュー手順をまとめた「GitHub運用メモ」。
- **確認テスト：** 正本ファイルと生成ビューを見分けられ、変更内容・検証結果・承認状態を確認する場所を説明できる。権限や保護ルールに応じた操作だけを案内する。

#### 第4章：ChatGPTチャットをMarkdownで保存する拡張機能
- **手順：** 候補を選ぶ前に提供元・更新状況・必要権限・プライバシーポリシー・保存データの扱いを確認する。比較結果を記録し、採用候補を決めた後、テスト用チャットをMarkdownで出力し、見出し・コード・リンク・日本語が保持されるか確認する。
- **成果物：** 拡張機能の選定理由、確認した権限、保存方法、既知の制約を記録した「拡張機能確認票」。
- **確認テスト：** テストチャットを保存して開き、内容が読めることを確認する。権限や提供元を確認できない場合は導入を保留する。特定製品は比較と安全性確認が終わるまで決め打ちしない。

#### 第5章：Dropboxの設定とファイル管理
- **手順：** Dropboxのアカウントと同期状態を確認し、原本・作業中ファイル・公開用成果物・バックアップの置き場所を決める。GitHub上の正本とDropboxの保管ファイルを混同しない。
- **成果物：** フォルダ構成表と、ファイル名・更新日・正本の所在を記録するルール。
- **確認テスト：** テストファイルを所定のフォルダに保存して再度開ける。同期状態を確認し、どのファイルが正本か説明できる。

#### 第6章：各ツールの役割分担と連携
- **手順：** 小さな模擬作業を一件選び、AIとの対話、Markdown記録、GitHubでの管理、Dropboxでの原本保管を順番に実施する。各ツールに同じ正本を手動で二重管理しない。
- **成果物：** 作業の流れ図と、各段階で参照・更新するファイルの一覧。
- **確認テスト：** 「どこを更新すれば正式な状態が変わるか」「作業を再開するとき最初に何を読むか」を説明できる。

#### 第7章：設定完了テスト
- **手順：** 模擬作業を開始し、目的・完了条件を記録し、短い試行を行い、結果と未解決事項を保存し、次回の開始位置を記録する。
- **成果物：** 完了チェックリスト、模擬作業の記録、次回再開メモ。
- **確認テスト：** 別の日に記録だけを読み、何を行い、何が確認済みで、何が未完了かを再現できる。未確認の結果を完了扱いにしない。

#### 執筆・検証の完了条件
- 各章に目的、前提条件、操作手順、期待結果、失敗時の確認、完了チェックがある。
- 画面操作は執筆時点の実画面で確認し、確認できない場合は未確認と明記する。
- 読者がチェックリストに沿って準備を完了できるか、実際に一度通して検証する。
- 実体験、確認済みの事実、仮説、未検証の提案を明確に区別する。
- この章別設計の完成は、本文執筆・実地テスト・公開・販売の完了を意味しない。
