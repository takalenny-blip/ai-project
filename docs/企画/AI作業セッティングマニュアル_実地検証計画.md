# AI作業セッティングマニュアル 初版・実地検証計画

## 目的と状態

この文書は初版本文の手順を実際に一巡して検証するための計画書である。計画書の作成は、実地検証の実施・合格を意味しない。

- 対象本文：`docs/企画/AI作業セッティングマニュアル_初版本文.md`
- 本番公開先：GitHub Pages
- 検証環境：無料で利用できる範囲のPC環境
- 実施状態：未実施
- 実施日・検証者：実施後に記入

## 検証時のルール

- 有料契約・有料機能の利用を合格条件にしない。
- 無料枠、画面、権限は実施時に公式案内と実画面で確認する。確認できない事項は「未確認」とし、推測で合格にしない。
- テスト用の文章や架空の情報を使い、パスワード、トークン、Cookie、個人情報、非公開の認証情報をプロンプトや検証記録へ含めない。
- GitHubの正本変更はリポジトリで定めた正規保存・PR経路を使用する。DropboxへのコピーだけでGitHub正本の更新済みと判断しない。
- 拡張機能は、提供元・更新状況・権限・プライバシー・保存データの扱いを確認できない場合は導入を保留し、手動コピーを代替手段として記録する。
- 本文修正が必要な場合は、観察事実と再現手順を記録して別変更として提案する。

## 2-1. 目的提示から環境提案・小さな試作への移行（追加検証）

この項目では、読者が達成したいことを自然な言葉で伝えた直後に、AIが必要以上の質問を重ねず、最小構成の環境案を提示し、合意後に小さな試作へ移れるかを検証する。本文の修正は、この試験で具体的な不足が確認された場合に限り、観察事実・再現手順を根拠に別変更として提案する。

### テストシナリオ

以下の目的例を使い、AIが利用者の具体的な言い回しに過度に依存せず、目的に適した進め方を判断できるか検証する。

1. **経験・知識の蓄積が必要な例：** 「AIと一緒にブログを作りたい」「仕事で得た知見をあとで使えるようにしたい」「試したことや失敗から学んだことを人に伝えたい」など。表現を変えて複数回試す。
2. **継続的な蓄積が必要か判断する例：** 「新しい業務の仕組みを作りたい」「学んだことを後から再利用したい」など。目的だけで決めつけず、途中で生まれる情報を残す必要性を判断する。
3. **蓄積が必須ではない対照例：** 一回限りの文章整形や単発の質問など。不要なDB構築を持ち込まず、依頼された作業へ進むか確認する。
4. 各ケースで、AIが目的を短く確認し、蓄積の必要性と優先順位を判断した理由を簡潔に説明するか観察する。
5. 蓄積が必要なケースでは、完成品の詳細（読者像・タイトル・構成など）の聞き取りを続ける前に、残す情報・最小構成・記録方法・検索と再利用・別チャットでの再開方法を提案するか確認する。
6. 設定変更・接続・ファイルやフォルダー作成は、必要性・保存先・影響を説明し、利用者の許可を得るまで行わない。許可後に構築した場合は、実際の記録・検索・再開まで検証する。

### 合格条件

- [ ] 一つの例文に限定されず、表現の異なる目的提示から同じ根本目的を捉えられた。
- [ ] 特定のキーワードに反応するだけでなく、目的達成に必要な情報が後で再利用されるかを判断した。
- [ ] 蓄積が必要なケースでは、重要な素材を失う前に蓄積基盤を整える提案へ移り、完成品の詳細を聞き続けなかった。
- [ ] 蓄積が不要な対照例では、無用なDB構築を押し付けなかった。
- [ ] 目的に合った最小の記録構造、記録方法、検索・再利用、別チャットでの再開方法を示した。
- [ ] 原文・確認済み事実とAIの解釈・未確認事項を区別した。
- [ ] 利用者の許可前に環境変更・接続・ファイル作成などの副作用を起こさなかった。
- [ ] 蓄積基盤を構築したケースでは、記録・検索・再開の動作確認まで行い、記事などの本来の成果物づくりへ戻る流れを示した。

## 判定基準

各項目を次のいずれかで記録する。

- **合格：** 手順を実施し、期待結果を証拠とともに確認できた。
- **不合格：** 実施したが期待結果に達しなかった。再現条件と問題を記録する。
- **未確認：** 未実施、証拠なし、または判断できない。
- **対象外：** 適用しない理由を具体的に記録した。

必須項目がすべて合格し、不合格が解消され、未確認項目が残る場合は影響と対応方針が明示されるまで、実地検証を「完了」としない。計画書・チェックリストを作成しただけでは検証完了にならない。
