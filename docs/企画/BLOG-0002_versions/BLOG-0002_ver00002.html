「うまく起動したぜ！」

VAIO Pが起動した。

デスクトップにはLXDEが表示された。

「LXDEシンプルでいいな！」

古いVAIO Pに、DebianとLXDEが動いている。

まずは成功だ。

ただし、ここで終わりではなかった。

次に確認したかったのはネットワーク。

ところが、Wi-Fiが使えない。

「Wi-Fiない？」

無線LANが見えない。

ここからは、画面を見ながらコマンドを一つずつ試していく。

まず、ネットワークインターフェースを確認する。

rfkill list

続いて、

ip link

ネットワーク管理にはNetworkManagerを使うことにして、

sudo nmtui

を起動する。

しかし、Wi-Fiが出てこない。

「見えねー」

そこで、NetworkManagerの状態を確認する。

nmcli device

すると、無線LANインターフェース wlp2s0 が「unmanaged」、つまり「管理なし」になっていた。

「管理なし」

ここから原因を切り分ける。

まずNetworkManagerに管理させてみる。

sudo nmcli device set wlp2s0 managed yes

それでも変わらない。

そこで、設定ファイルを確認する。

cat /etc/network/interfaces

すると、wlp2s0 に関する設定が残っていることが分かった。

NetworkManagerと、以前のネットワーク設定がぶつかっているらしい。

そこで、無線LAN関連の設定をコメントアウトする。

sudo sed -i '/wlp2s0/s/^/#/' /etc/network/interfaces

sudo sed -i '/wpa-ssid/s/^/#/' /etc/network/interfaces

sudo sed -i '/wpa-psk/s/^/#/' /etc/network/interfaces

続いてNetworkManagerを再起動。

sudo systemctl restart NetworkManager

そして、もう一度確認する。

nmcli device

今度は wlp2s0 が「管理なし」ではなく、「切断済み」に変わった。

少なくとも、NetworkManagerが無線LANを管理できる状態になった。

そして、

sudo nmtui

を起動する。

今度はWi-FiのSSIDが表示された。

「出たーーー」

ここからWi-Fiを選択して接続。

接続後、iPhoneのUSBテザリングを外して、Wi-Fiだけで本当にインターネットにつながっているか確認する。

ping -c 3 8.8.8.8

そして、

「繋がった。画面はとじていいの？」

画面を閉じて、最終確認。

「オケ」

Wi-Fiも復旧した。

ここまで来ると、VAIO Pが少しずつ「使える機械」になってきた感じがする。

ただ、実際に使ってみると、また問題が出た。

Firefoxを起動する。

「firefoxは変わらず重い。。。」

Debianは起動した。

LXDEも動いた。

Wi-Fiもつながった。

でも、Firefoxは重い。

そこで次は、軽量なブラウザを探すことになった。

こうしてVAIO Pは、

↓

↓

↓

↓

という具合に、一つ問題を解決すると、また次の問題が出てくる状態になった。

それでも、最初の「VAIO Pをサーバーにしてみたい」というところから考えれば、かなり前に進んでいる。

そして、この一連の作業をAIとの会話と一緒に記録していくこと自体が、あとになって重要な意味を持つことになる。

VAIO Pを動かしたい

↓

↓

DIGA／DiMORAを使った自動化テスト

VAIO Pを動かしていく一方で、以前からDIGAの録画管理についてClaudeといろいろ試していた。

このころは、まだ自動化しようなんて考えていなかった。

スプレッドシートとGASを使って、DIGA 3台の予約情報を管理する仕組みを作っていた。

最初にClaudeに投げたのは、こんな相談だった。

「Diga3台の予約情報を見て、録画の管理データベースを作りたい。ネットからもってくる一例はこちら。データは機種ごとにグーグルドライブ内のグーグルドキュメントに貼り付けようと思う。日時変更など警告メールを出すようにしてほしい。また、次回の予約がないよ、とか。現在の録画話数の自動更新もほしい。シリーズ終了の連絡もほしい。今までの録画志向から、番組おすすめもほしい。あと他に提案とか質問とかある？」

Claudeと相談しながら、貼り付けたDIGAの情報を使って、予約の変化をチェックする仕組みを作っていった。

お気に入り番組についても、最初はDiMORAからコピーした内容をGoogleドキュメントの機種毎ファイルに必ず貼り付け、それを「その時点のお気に入り」として扱う方式だった。

ところが、実際に使っていると、手を抜きたくなる。

たとえば、お気に入りが変わった場合だけGoogleドキュメントに貼り付け、変更が無い場合は貼り付けない。

そこでClaudeに対して、

「待って。お気に入りの中身が空の場合は、内部で持ったお気に入り情報で進める。中身があるときだけ、お気に入りの加除チェックをする。これは機種ごとに制御したい。（例えば、diga1,2のお気に入りは空だったから加除チェックは走らない。diga3に入ってるから加除チェックを走らす。）内部情報でお気に入りに機種情報も加える必要あり。」

と仕様を修正した。

さらに、実際にチェック結果のメールを見ると、今度は別のところが気になった。

「これは、今日のチェック結果メール。内容はいいんだけど、いつの放送分なのか、日時と曜日を加えてほしい。」

Claudeに修正してもらう。

すると次には、

「ゴメン。あとチャンネルも必須。可能であれば機種も。」

となった。

こうやって、作って、使って、気になったところを直す。

DIGAの録画管理は、少しずつ自分が欲しい形になっていった。

ただし、一つだけ面倒なことが残っていた。

毎回、DiMORAの画面をコピーして貼り付けること。

ここは単純に面倒だった。

この時点では、DIGAの自動化を考えていたわけではない。

そんな中で、別のところから「ブラウザを使って情報を取得する」という発想を知った。

Claudeのブラウザ連携を知り、それをきっかけにGeminiにも聞いてみたときである。

Pythonでブラウザから情報を取得する。

それを知ったとき、急につながった。

「あ、これDIGAでも使えるかも」

そう思った。

コピペしなくて済む。

うまくしたらラクになるぞー。

でも、すぐに次の疑問が出てきた。

DiMORAからうまく情報とれるの？

そこで、AIと一緒にDiMORAの画面を調べ始めた。

まず目を付けたのが、お気に入り番組一覧の「もっと見る」だった。

画面には番組が並んでいて、さらに先を見るための「もっと見る」がある。

「次の10件」がどうやって表示されているのか。

ここを追えば、DiMORAがどこから番組情報を持ってきているのか分かるかもしれない。

AIから指示をもらいながら、実際のHTMLを確認していく。

すると、ページの中には、

favoriteProgram-14.6.0.js

というJavaScriptが読み込まれていることが分かった。

「このJavaScriptを見てみよう」

そんな具合に、一つ分かると次を調べる。

その中で「もっと見る」の処理を追っていくと、

FavoriteProgramController.prototype.addFavPgm()

さらに追う。

すると、その処理が参照していたのが、

GL_FAVPGM_DATA.record

ここで、だんだん見えてきた。

「もっと見る」を押したから、次の10件を新しくサーバーから取りに行っているのではない。

ページには、すでにお気に入り番組のデータが入っている。

「もっと見る」は、そのデータを10件ずつ表示している。

そこでAIから、ページ内に持っているデータを実際に確認する方法を教えてもらい、それを実行してみる。

結果をAIに返す。

AIがまた「ここを見てみよう」と指示する。

実際にDiMORAのお気に入り番組の情報を取得できた。

そこには、番組の日付や時間、放送局、タイトル、録画モード、曜日、番組URLなど、録画管理に使えそうな情報が入っていた。

ここで初めて、「コピペしなくてもいけるかもしれない」が、実際のデータを見て確認できた。

ただ、この時点で「VAIO Pですべて自動化できた」わけではない。

まず別のPCでDiMORAのHTMLとJavaScriptを調べ、AIの指示を受けながらページ内部のデータを追いかけ、実際にお気に入り番組の情報を取得できるところまで来た。

次に必要なのは、ログインしたDiMORAのページからそのデータを安全に読み出し、それをVAIO P上のPythonで扱えるようにすることだった。

最初はただ「コピペが面倒だな」と思っていただけだった。

それが、Claude、Gemini、Python、ブラウザ、DiMORAと話をつないでいくうちに、いつの間にかWebページの中身まで掘ることになっていた。
