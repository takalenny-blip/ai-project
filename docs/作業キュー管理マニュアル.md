# 作業キュー管理マニュアル

## 1. 目的

このマニュアルは、`docs/現在状態.json` の `work_items` を使って、現在の作業を漏れなく、同じ方法で管理するための標準手順を定める。

目的は次の3点。

- 作業漏れを防ぐ
- セッションや担当AIが変わっても、同じ手順で再開できるようにする
- 「ついでに確認する」「後で覚えておく」といったチャット依存の管理をなくす

## 2. 正本と管理対象

- 現在の作業キューの正本は `docs/現在状態.json` の `work_items`。
- `work_items` は現在進行中・待機中・未着手の作業だけを管理する。
- 完了した作業は、完了確認後にキューから削除する。
- 廃止・統合・重複・方針変更で不要になった作業も削除する。
- 過去の作業履歴は `work_items` に残さない。必要な履歴は Git / PR 等で確認する。
- 作業IDは履歴番号ではないため、空いた番号を再利用してよい。

## 3. 作業を登録するタイミング

次のいずれかに該当したら、独立した作業としてキューへの登録を検討する。

1. たかから新しい作業依頼があった。
2. 作業中に、新しい確認・調査・修正・判断が必要だと判明した。
3. 外部サービスの結果から、別途対応が必要になった。
4. 既存作業の前提条件として、別作業の完了が必要になった。
5. レビューで独立した対応事項が見つかった。

特に、作業中に発見した新しい作業を「今やっている作業の一部」として曖昧に残してはならない。

## 4. 独立作業への分解

次の条件に当てはまる場合は、親作業とは別の `work_item` にする。

- 独立して確認できる
- 独立して完了判定できる
- 担当者や実施タイミングが異なる
- 他の作業を待つ必要がある
- 完了しないと次の作業へ進めない
- 後から別作業として再開する可能性がある

「Xの作業の中でYも確認する」だけでは、Yの作業管理として不十分である。

### 例

GSCについて、

- `GSC-確認` = インデックス状況の確認
- `GSC-サイトマップ確認` = `/sitemap.xml` の取得状況・原因確認

のように、独立して完了判定できるものは別作業として登録する。

## 5. 作業登録時の基本項目

既存の `work_items` の形式に合わせ、少なくとも次を明確にする。

- `id`
- `title`
- `priority`
- `status`
- `depends_on`
- `not_before`
- `scope`
- `target`
- `evidence`
- `readiness`
- `unblock_action`
- `environment`
- `created_at`
- `updated_at`
- `prerequisites`

既存形式にない新しい項目を独自判断で増やすのではなく、まず現在の `docs/現在状態.json` と運用ルールを確認する。

## 6. 作業開始前の手順

作業を開始する前に、必ず次の順番で確認する。

1. `docs/現在状態.json` を読む。
2. `work_items` の現在の一覧を見る。
3. 今回の目的に関係する作業を特定する。
4. `depends_on`、`not_before`、`readiness` を確認する。
5. すでに登録されている作業を重複登録しない。
6. 未登録の独立作業が見つかった場合は、先にキューへ追加する。
7. 実行対象を明確にしてから着手する。

チャットの記憶だけを見て「次はこれだったはず」と作業を始めない。

## 7. 作業中の管理

作業中に新しい独立作業が発生した場合は、その時点でキューに登録する。

「後で `work_items` に追加する」は原則として行わない。後回しにすると、今回のような作業漏れにつながるためである。

また、次の状態変化があった場合は、必要に応じて `status`、`readiness`、`evidence`、`not_before`、依存関係などを更新する。

- 着手可能になった
- 他作業待ちになった
- 外部サービス待ちになった
- 実施した
- 結果が判明した
- 方針が変わった
- 不要になった

## 8. 依存関係の管理

作業Aが終わらないと作業Bを開始できない場合、Bの `depends_on` 等に明示する。

依存関係を文章だけに埋め込んで管理してはならない。

### 例

- `GSC-サイトマップ確認` が完了してからBLOG-0004を進める場合
- BLOG-0004の `depends_on` に `GSC-サイトマップ確認` を設定する

「先にGSCを確認する」とだけ書いて終わりにしない。

## 9. 完了時の処理

作業を実施しただけでは、直ちに完了扱いにしない。

次の順番で処理する。

1. 完了条件を確認する。
2. 実際に完了したことを確認する。
3. 必要な証拠を `evidence` 等に反映する。
4. 正本への反映が必要なら更新する。
5. CI、レビュー、マージ等が必要な作業では、それらを含めて完了を確認する。
6. 完了確認後、`work_items` から削除する。

「PRを作った」「マージした」だけで、正本への反映や確認が必要な作業を完了扱いにしない。

## 10. 不要になった作業

次の場合は、現在キューから削除する。

- 完了した
- 別の作業へ統合された
- 重複していた
- 方針変更で不要になった
- 対象外になった

削除したこと自体を履歴として `work_items` に残す必要はない。

## 11. 作業IDの扱い

作業IDは現在キュー上の識別子であり、歴史上の固定番号ではない。

したがって、

- 完了したIDは空ける
- 空いた番号は再利用してよい
- 過去のIDの意味を追跡するために現在キューへ履歴を残さない

という扱いにする。

## 12. GSCの作業管理例

GSCに複数の独立した確認事項がある場合、それぞれを作業として登録する。

例：

- `GSC-確認`
  - URL検査結果、インデックス状況などを確認
  - 実際のGSC操作はたかが行う
- `GSC-サイトマップ確認`
  - `/sitemap.xml` の実体を確認
  - GSCの取得状況・原因を確認
  - 必要な対処を決定
  - 再送信の要否を判断

「GSC-確認の一部としてサイトマップも見る」とだけ書いて、独立した作業をキューから隠してはならない。

## 13. 作業発見から完了までの標準フロー

```
作業を発見
  ↓
独立作業か判定
  ↓
work_itemsへ登録
  ↓
依存関係・待機条件を設定
  ↓
現在キューから着手対象を選定
  ↓
作業実施
  ↓
新しい独立作業が発生？
  ├─ Yes → その場でwork_itemsへ登録
  └─ No
  ↓
完了条件を確認
  ↓
完了確認
  ↓
work_itemsから削除
  ↓
残っている現在作業を再確認
```

## 14. 作業終了時チェックリスト

作業を一区切りにする前に、次を確認する。

- [ ] 今回発生した独立作業がすべて `work_items` にある
- [ ] 「ついでに確認する」だけで隠れている作業がない
- [ ] 重複した作業がない
- [ ] 完了済み作業が現在キューに残っていない
- [ ] 不要になった作業が残っていない
- [ ] 待機中の作業には待機理由がある
- [ ] blockedな作業には解除条件がある
- [ ] 依存関係が正しい
- [ ] 次に着手すべき作業が現在キューから判断できる
- [ ] `docs/現在状態.json` の現在状態と矛盾していない

## 15. 完了条件

このマニュアルの運用が成立している状態とは、

> `docs/現在状態.json` の `work_items` を見れば、たかが言わなくても、現在存在する作業・待機中の作業・その解除条件・次に着手すべき作業が分かる状態

である。

チャット履歴を読み直さなければ「実はこれも作業だった」と分からない状態は、作業キュー管理として未完成とする。
