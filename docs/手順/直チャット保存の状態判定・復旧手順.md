# 直チャット保存の状態判定・復旧手順

## 目的

保存要求の途中にあるPRの状態と、GitHubの正規保存が完了したかを混同しない。特に、キューPRが閉じている／ブランチが削除されている／手動再実行が失敗した、という単独の事実から保存全体を「未完了」と判定しない。

## 状態モデル

保存は次の独立した状態を持つ。前段の状態だけから後段の状態を推測しない。

1. **受け渡し元**：Dropbox等に原本がある。
2. **キュー投入**：.github/save-queue/ の内容を持つ chat-save-request/* PRが作成された。
3. **正規保存PR**：直チャット保存＋現在状態と生成ビューを一括同期 PRが作成された。
4. **マージ**：正規保存PRが merged=true になった。
5. **保存実体**：直チャット/ の保存ファイルをGitHubから再取得できる。
6. **完全性**：保存ファイルの本文が受け渡し元の原文と一致する。保存スクリプトがタイトル行を自動付与した場合は、その生成タイトル行だけを除外して比較する。
7. **現在化**：docs/現在状態.json の direct_chat.latest_saved、direct_chat.latest_path、direct_chat.latest_content_sha が実ファイルと一致し、BUD.md と docs/引き継ぎ/現在の引き継ぎ.md も同じ保存を示す。

「完了」は、4〜7を証拠で確認した場合だけ使用する。1〜3のどれか、キューPRのopen/closed状態、Actionsの単独run結果は、保存全体の完了・未完了を決める証拠ではない。

## 標準確認手順

### A. 保存要求の識別

1. 対象ファイル名、原本の所在、可能なら原本サイズ／SHAを記録する。
2. キューPR番号とキューファイルパスを特定する。open PRだけでなく、closed PR、削除済みブランチ、同じファイルを含む過去PRも検索する。
3. キューPRの状態は「キュー工程の状態」として記録する。正規保存の状態と混ぜない。

### B. 正規保存の下流確認（必須）

1. 「直チャット保存＋現在状態と生成ビューを一括同期」という正規保存PRを、open・closed・mergedの全状態から探す。
2. 見つかった各PRについて、変更ファイル、マージ状態、マージコミット、実行ログ／チェックを確認する。
3. マージ済みなら保存ファイルの実体をmainから読み戻す。
4. 未マージPRがある場合は、同一対象の保存PRがすでに存在するか、重複した実行が進行中かを確認する。
5. 正規保存PRが見つからない場合に限り、未保存と断定せず「正規保存の証拠をまだ確認できない」と報告し、履歴・Actions・保存状態JSONを追加調査する。

### C. 内容と現在化の照合（必須）

1. GitHubの保存ファイルを再取得する。
2. 原本と保存本文を比較する。スクリプトが生成した先頭タイトル行のみを除外してよい。本文を要約・整形・言い換えして比較してはならない。
3. docs/現在状態.json の direct_chat.latest_path がその保存ファイルを指していることを確認する。
4. direct_chat.latest_saved が保存時刻と一致することを確認する。
5. direct_chat.latest_content_sha と、保存ファイルのGit blob SHAまたは保存スクリプトが定義する内容SHAを、同じSHA定義で照合する。異なるSHA定義を比較しない。
6. BUD.md と docs/引き継ぎ/現在の引き継ぎ.md の最新保存パス・時刻が正本と一致することを確認する。
7. 各チェックを「合格／不合格／未確認」で記録する。未確認を合格として扱わない。

## 状態別の判断

| 観測した状態 | 正しい判断 | 次の行動 |
|---|---|---|
| キューPRがclosed、正規保存PRはmerged | 保存済みの可能性が高い。キューPRの状態だけで失敗扱いにしない | 保存実体・原文一致・現在化を確認 |
| キューPRがclosed、正規保存PRがopen | 正規保存処理中 | そのPRのCI・承認・マージを追跡。キューを重複投入しない |
| キューPRがclosed、正規保存PRが見つからない | 未完了と断定せず、下流の証拠が未確認 | Actions履歴・全状態のPR・保存状態JSONを調査 |
| 手動再実行が失敗 | そのrunが失敗した | エラーログの失敗点を特定し、正規保存が別経路で完了していないか先に確認 |
| 正規保存PRがmerged、保存ファイルが見つからない／本文不一致 | 保存検証不合格 | 完了報告しない。原本を保持して原因調査・安全な復旧へ |
| 保存ファイルは存在するが状態JSON／生成ビューが不一致 | 保存実体はあるが現在化は不合格 | 既存ファイルを重複保存せず、正規の状態同期手順を使う |

## 復旧手順

1. **再投入前に重複確認**：同じ原本・キューPR・キュー本文に対応する正規保存PRが既に作成済みまたはマージ済みでないか確認する。
2. **正規保存PRが既にmerged**：再保存しない。原文一致と現在化の不足だけを特定し、該当する検証／同期工程を復旧する。
3. **正規保存PRがopen**：同じキューを新規作成しない。既存PRのチェック・レビュー・マージ状態を確認する。
4. **正規保存PRが存在しないと証拠付きで確認できた**：既存キューPR番号を使って Save request intake を手動実行する。現在のワークフローでは queue_pr_number を指定でき、open/closedの状態にかかわらず既存PRから安全にキュー本文を解決する。PR番号が分からずファイル名で探す場合、候補が複数なら推測で選ばず、PR番号を指定する。
5. **手動再実行が失敗**：失敗ログの最初の実エラーを記録し、失敗工程だけを直す。別の正規保存PRができていないか再確認するまで、同じ要求を再投入しない。
6. Dropbox原本と既存GitHub保存ファイルは読み取り専用の証拠として扱う。原本を編集・上書き・削除して復旧しない。

### 正規保存PRが古いmainを基点にして競合した場合

正規保存PRがopenのままmainの更新により競合した場合、同じキューを再投入したり、古いPRの状態JSON・生成ビューをマージしたりしない。

1. 既存PRの変更ファイルから、唯一の `直チャット/*.md` 保存ファイルを特定する。
2. その保存ファイルのGit blobを読み取り、本文を変更せずに保持する。
3. 最新mainを親として、保存ファイルだけを追加する履歴補完コミットを作る。
4. 追加ファイル名の保存時刻がmainの `direct_chat.latest_saved` より古い場合に限り、状態JSONと生成ビューは変更しない。現在の最新保存ポインタはそのまま維持する。
5. 保存時刻が最新ポインタより新しい場合は、通常の4ファイル一括保存として状態JSON・生成ビューも同期する。
6. 履歴補完コミットは、既存ファイルの変更・上書きではなく、新規追加であること、既存最新ファイルが親コミットに存在すること、状態JSONが不変であることを専用ガードで検証する。
7. 既存の正規保存PRのブランチを、確認した旧head SHAを条件に最新main基点へ更新する。更新後は通常のCI・承認・マージ工程を通す。

この経路は、古い保存時刻の記録を後からmainへ取り込むための例外であり、最新状態を古い記録へ巻き戻すことを許可しない。

## 報告フォーマット

- キュー工程：PR番号／open・closed・merged／証拠
- 正規保存工程：PR番号／open・closed・merged／マージコミット
- 保存実体：パス／読み戻し結果
- 原文一致：合格・不合格・未確認（比較時に除外した生成物があれば明記）
- 現在化：JSONのpath・timestamp・SHA、BUD／引き継ぎビューの一致
- 判定：完了／未完了／証拠不足
- 次の行動：失敗工程に限定した具体策

## 禁止事項

- キューPRのclosedだけを根拠に、保存全体を未完了と報告する。
- ひとつのActions runの失敗だけで、別経路の正規保存結果を確認せず全体失敗と判定する。
- 正規保存PR・保存実体・原文一致・現在化を確認する前に「完了」と断定する。
- 状態が不明なまま新しいキューPRを重複作成する。
- 原本を修正して比較を通す、または未確認の内容一致を主張する。
