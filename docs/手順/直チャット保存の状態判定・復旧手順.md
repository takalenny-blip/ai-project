# 直チャット保存の状態判定・復旧手順

## 目的

保存要求の途中にあるキューPRの状態と、正規保存が完了したかを混同しない。キューPRの状態だけで保存全体を「未完了」と判定しない。

## 状態モデル

1. **受け渡し元**：Dropbox等に保存対象の原本がある。
2. **キュー投入**：`.github/save-queue/` の内容を持つ `chat-save-request/*` PRが作成された。
3. **正規保存PR**：新規の直チャットファイル1件だけを追加する保存PRが作成された。
4. **マージ**：正規保存PRがmerged=trueになった。
5. **保存実体**：`直チャット/` の保存ファイルをGitHubから再取得できる。
6. **完全性**：保存ファイルの本文が受け渡し元の原文と一致する。生成された先頭タイトル行だけを除外して比較してよい。

「完了」は4〜6を証拠で確認した場合だけ使用する。キューPRのopen/closed状態やActionsの単独run結果だけで保存全体の完了・未完了を決めない。

## 標準確認手順

### A. 保存要求の識別

1. 対象ファイル名、原本の所在、可能なら原本サイズ／SHAを記録する。
2. キューPR番号とキューファイルパスを特定する。open PRだけでなくclosed PR、削除済みブランチ、同じファイルを含む過去PRも検索する。
3. キューPRの状態は「キュー工程の状態」として記録する。正規保存の状態と混ぜない。

### B. 正規保存の下流確認

1. 正規保存PRをopen・closed・mergedの全状態から探す。
2. 見つかった各PRについて、変更ファイル、マージ状態、マージコミット、実行ログ／チェックを確認する。
3. マージ済みなら、保存ファイルの実体をmainから読み戻す。
4. 未マージPRがある場合は、同一対象の保存PRがすでに存在するか、重複した実行が進行中かを確認する。
5. 正規保存PRが見つからない場合は「正規保存の証拠をまだ確認できない」とし、未保存と断定しない。

### C. 内容と保存実体の照合

1. GitHubの保存ファイルを再取得する。
2. 原本と保存本文を比較する。生成された先頭タイトル行だけを除外してよい。本文を要約・整形・言い換えして比較してはならない。
3. 保存ファイルのパス・コミットSHA・Git blob SHAまたはSHA-256を記録する。
4. 各チェックを「合格／不合格／未確認」で記録する。未確認を合格として扱わない。

## 状態別の判断

| 観測した状態 | 正しい判断 | 次の行動 |
|---|---|---|
| キューPRがclosed、正規保存PRはmerged | 保存済みの可能性が高い | 保存実体・原文一致を確認 |
| キューPRがclosed、正規保存PRがopen | 正規保存処理中 | そのPRのCI・承認・マージを追跡。キューを重複投入しない |
| キューPRがclosed、正規保存PRが見つからない | 正規保存の証拠が未確認 | Actions履歴・全状態のPRを調査 |
| 手動再実行が失敗 | そのrunが失敗した | 別経路の正規保存結果がないか先に確認 |
| 正規保存PRがmerged、保存ファイルが見つからない／本文不一致 | 保存検証不合格 | 完了報告しない。原本を保持して原因調査・安全な復旧へ |

## 復旧手順

1. **再投入前に重複確認**：同じ原本・キューPR・キュー本文に対応する正規保存PRが作成済みまたはマージ済みでないか確認する。
2. **正規保存PRが既にmerged**：再保存しない。原文一致の不足だけを特定し、該当する検証工程を復旧する。
3. **正規保存PRがopen**：同じキューを新規作成しない。既存PRのチェック・レビュー・マージ状態を確認する。
4. **正規保存PRが存在しないと証拠付きで確認できた**：既存キューPR番号を使ってSave request intakeを実行する。
5. **手動再実行が失敗**：失敗ログの最初の実エラーを記録し、失敗工程だけを直す。別の正規保存PRができていないか再確認するまで、同じ要求を再投入しない。
6. Dropbox原本と既存GitHub保存ファイルは読み取り専用の証拠として扱う。原本を編集・上書き・削除して復旧しない。

### 正規保存PRの直列化・新規受付停止

正規保存PR（`save/direct-chat-*`）は同時に1件だけopenとする。先行PRのmerge完了前に次の正規保存PRを作成してはならない。

保存branchを作成する前にopen中の正規保存PRを確認する。該当PRがある場合は新しい正規保存PRを作らず、既存キュー要求を保留する。先行PRのmergeまたは安全な解決後、同じキューPR番号でintakeを再開し、新しいキューPRを重複作成しない。

## 報告フォーマット

- キュー工程：PR番号／open・closed・merged／証拠
- 正規保存工程：PR番号／open・closed・merged／マージコミット
- 保存実体：パス／読み戻し結果
- 原文一致：合格・不合格・未確認
- 内容ハッシュ：定義／値／照合結果
- 判定：完了／未完了／証拠不足
- 次の行動：失敗工程に限定した具体策

## 禁止事項

- キューPRのclosedだけを根拠に、保存全体を未完了と報告する。
- ひとつのActions runの失敗だけで、別経路の正規保存結果を確認せず全体失敗と判定する。
- 正規保存PR・保存実体・原文一致を確認する前に「完了」と断定する。
- 状態が不明なまま新しいキューPRを重複作成する。
- 原本を修正して比較を通す、または未確認の内容一致を主張する。
- 廃止済みの現在状態スナップショットや生成ビューの同期を、直チャット保存の完了条件に含めない。
