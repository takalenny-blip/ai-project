# VAIOP運用環境構築 JUN向け指示書

## 1. この指示書の目的

VAIO Type P（VAIO P）を、今後の自動化処理を継続的に動かすための実運用基盤として整備する。

最終ゴールは、たかの経験ログからAIが記事素材を発見・整理・文章化し、Bloggerへブログ記事を自動作成・投稿する仕組みを作ること。その途中段階として、まずVAIO P上に安全で安定した自動化運用環境を作る。

たかはVAIO Pの構築をJUNと進める。Claudeには主としてコード作成を依頼し、バドは全体設計・仕様整理・進捗確認・経験の整理を担当する。

## 2. 現在の位置づけ

現在までに以下を進めている。

- プロジェクト全体の方向性・進め方を整理済み
- GitHub `takalenny-blip/ai-project` を情報共有・記録の土台として運用
- `直チャット` にAIとの実作業ログを保存
- `経験ログ` に実際の経験・実験・改善を資産として保存
- VAIO PへのDebian導入・初期環境構築を進行
- マスタープランを `docs/マスタープラン.md` に保存

次は、VAIO Pを「単にDebianが入ったPC」から「継続的に自動化を動かす運用基盤」へ進める段階。

## 3. まず作る運用基盤

以下を順番に確認・整備する。

### A. 基本環境

- Debianの状態確認
- ユーザー・権限の確認
- ネットワーク接続確認
- 時刻・タイムゾーン確認
- パッケージ更新方法の確認
- Python実行環境の確認
- Git利用環境の確認

### B. ディレクトリ構成

自動化プログラム、設定、データ、ログを混在させない。

例：

```text
~/ai-project/
├── apps/       # 自動化プログラム
├── data/       # 一時データ・処理データ
├── logs/       # 実行ログ・エラーログ
├── config/     # 設定（秘密情報は置かない）
└── work/       # 作業用
```

実際のパスや構成は、VAIO Pの容量・権限・既存環境を確認してJUNと相談して決める。

### C. 定期実行

将来、以下のような処理を定期実行できるようにする。

- DIGA予約情報取得
- データ整理・変換
- Google側への連携
- その他の自動化
- 定期的な状態確認

候補としてcron / systemd timer等を検討する。最初から複雑にせず、1つの簡単な定期処理で実行・失敗・再実行を確認する。

### D. ログ・エラー管理

自動化は「動いた」だけでなく、「失敗したときに分かる」ことを重視する。

最低限、以下を確認できるようにする。

- 実行開始時刻
- 実行終了時刻
- 成功／失敗
- エラー内容
- 必要に応じて処理対象件数

将来的にはエラー発生時のメール通知も検討する。

### E. GitHub連携

GitHubはプロジェクトの共有情報・記録場所として使う。

ただし公開リポジトリなので、以下は絶対に保存しない。

- パスワード
- APIキー
- アクセストークン
- Cookie等の認証情報
- Wi-Fi等の秘密情報
- 個人情報
- 仕事上の機密情報

VAIO P側の秘密情報はGitHubとは分離する。

## 4. DIGA自動取得への接続を意識する

運用環境完成後の最初の主要テーマは、現在手動で行っているDIGA予約情報のコピペを自動化すること。

目標イメージ：

```text
DIGA
 ↓
VAIO Pが予約情報を取得
 ↓
必要な形式へ整理・正規化
 ↓
保存
 ↓
Google Drive / Google Sheets / GASへ連携
 ↓
録画管理・通知
```

DIGAは3台あり、機種・デバイスを区別して扱う前提。予約情報だけでなく、録画管理・お気に入り・変更検知・通知などへ発展できる構造を意識する。

ただし、いきなり全部作らない。まず「VAIO PからDIGA情報を取得できるか」を小さく検証する。

## 5. Google / GASとの役割分担

現時点では以下を基本案とする。

### VAIO P側

- DIGA等からの情報取得
- データ加工・正規化
- 定期実行
- ローカルログ
- エラー検知

### Google側

- Google Drive / Sheetsでのデータ管理
- GASによるメール通知・Web/Form等、人間が操作する部分
- 必要に応じた共有・閲覧

実際の境界は、小さな実験をしながら決定する。

## 6. 進め方の原則

1. 一度に全部作らない。
2. 実際に動かして確認する。
3. 問題が出たら、それを失敗ではなく仕様追加の材料として扱う。
4. 変更した内容と結果を記録する。
5. 秘密情報をGitHubに入れない。
6. VAIO Pに何でも詰め込まず、Google/GASと役割分担する。
7. 最終ゴール（経験ログ→Blogger自動化）から逆算する。
8. ただし、今すぐ役に立つ運用から優先する。

## 7. バドへの連携ポイント

作業中に以下が発生したら、バドへ共有する。

- VAIO Pの構成を決定した
- 新しいサービスや常駐処理を追加した
- 定期実行方式を決定した
- ディレクトリ構成を変更した
- DIGAとの接続方法が分かった
- エラーや問題が発生した
- 「この方法でよいか？」という設計判断が必要になった

バドはそれを全体構想・マスタープラン・経験ログとの関係から整理する。

## 8. 記録の考え方

このプロジェクトでは、完成したシステムだけでなく、構築途中の経験も重要な資産とする。

基本的な流れ：

```text
JUNとVAIO Pを構築
 ↓
実際に試す
 ↓
問題・発見・工夫・判断が出る
 ↓
直チャット等に記録
 ↓
バドが整理
 ↓
必要なものを経験ログ（EXP/REC）へ保存
 ↓
将来の記事素材になる
```

## 9. 現在の最優先事項

まずは「VAIO P運用環境の最小構成」を作る。

優先順位は以下。

1. Debian / ネットワーク / Python / Gitの基本確認
2. 自動化用ディレクトリ構成
3. ログを残せる実行環境
4. 定期実行の仕組み
5. 簡単なテストプログラムで正常系・異常系を確認
6. GitHubとの安全な連携方法を確認
7. その後、DIGA予約情報の自動取得へ進む

## 10. 完了条件（第一段階）

以下を満たしたら、VAIO P運用環境の第一段階完了とする。

- VAIO Pが安定して起動・通信できる
- Pythonプログラムを実行できる
- 決めた場所にプログラム・データ・ログを分離して置ける
- 定期実行できる
- 実行結果を確認できる
- エラー時に原因を追える
- GitHubに秘密情報を置かずに連携できる
- 次のDIGA自動取得を載せられる状態になっている

この段階ではDIGA本体の自動取得まで完成させる必要はない。
