# 経験DB運用憲法

## 目的

たかの経験を、まず事実として記録・蓄積する。  
価値判断・選別は後から行う。

## AI協働体制

経験DBは、たかを中心に複数のAIが協働する前提で運用する。AIごとに得意分野や役割は異なるが、役割を最初から固定しすぎず、実運用を通して必要に応じて見直す。

- **たか**＝決める・実際に経験する・最終判断する・バドと協議して経験DBへの登録方針を決める
- **JUN**＝利用可能な場合、現場情報の捕捉・リアルタイム記録・たかの反応の記録などを補助する。経験DBの作成・ID発行・GitHubへの書き込みは行わない
- **Claude**＝個別の実装・試行・問題解決などを補助する。現時点では役割を固定せず、実際の利用を通して適切な役割を確認していく
- **バド**＝たかと協議して全体設計・過去ログの発掘・整理・EXP/RECの判定・経験DBへの整理・GitHubへの書き込み・ID管理・記事化を行う

## 重要原則

- 迷ったら、まず記録する。
- 経験を価値や重要度で格付けしない。価値判断・選別は後から行う。
- RECは発生した順に時系列で積み上げる。既存RECを書き換えて過去を修正しない。
- 過去ログの発掘・整理はバドが行う。
- AIに過去ログ発掘を依存させない。必要な情報はバドが整理する。
- 既存RECは変更・削除しない。訂正・追加が必要な場合は、新しいRECとして記録する。
- 事実と推測・解釈を分ける。AIが推測・解釈した内容を、たかの経験や事実として記録しない。
- たかが実際に経験・発言した事実を、AIが創作・補完してはならない。不明な場合は不明のまま扱う。
- EXP/RECのIDは「ID管理台帳」のルールに従う。
- 経験ログの作成・更新、GitHubへの書き込み、ID管理・台帳更新は、バドが担当する。
- **直チャットを登録すると決めた場合、直チャットは要約・編集せず、原文そのものを保存する。**
- **直チャットを受け取ったら、まず生ログとして保存し、その後に既存EXPの確認とEXP/REC化を行う。**
- **現時点の基本フローは、たか → バドと協議 → バドが実行、とする。**
- AIが利用できないことを前提にしても経験DBの運用が止まらない構造とする。
- AIの役割は実運用から学び、必要に応じて憲法・企画書を更新する。
